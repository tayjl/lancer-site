# Pilot and mech pages

## Pilot page (dossier)

- **my pilot is built** as a COMP/CON-style sheet in the centred page column (`src/views/PilotManageView.vue`; redesigned 2026-11-15):
  - **Breadcrumb** on records and GM review (`registry / WARDEN`, `pending /`, `memorial /` by status, or `gm: pilots /`); no big page title, the callsign is the title. The global `.crumbs` style (`style.css`) is shared with `PageHeader.vue`.
  - **Cover** (2026-11-20, replacing the old header; `PilotCover.vue`, mockup `docs/redesign/dossier/`): a banner strip (the picture, else a plain gradient from the pilot colour into `--void` with one soft glow, no stripes; the cover body is a flow-root so its faint grid starts under the banner, never across it), the portrait in pilot-colour corner brackets, a small mono classification line ("Pilot file · `pilotSerial(id)`") with the pilot's status `.badge` at its right end (before any GM links, alone in the corner without them; it wraps to its own line on phones, still visible), the callsign big with the name beside it on the same baseline (24px `--text-dim`, 20px / 18px on phones, wrapping under the callsign when there isn't room; both inline fields where editable; the name isn't repeated when there's no callsign), the motto (20px italic in pilot-colour quotation marks drawn by CSS, never stored; the editable textarea has no underline, only an outline on hover and focus), then a foot row with the medals (`CommendationBadges.vue`) and "Player: x" small and dim at its right end, under the actions (its own left-aligned line on phones), then the figures strip: Level, Licence level, Grit, HP and, only for the pilot's player and GMs, Manna left. While editing, the cover's `tools` slot holds the Portrait, Banner (`ImageUpload`, plus `Position banner`) and Colour (`PilotColourField`, `Reset colour` on the same line as the boxes) controls along its foot, three equal top-aligned columns under one rule (stacked on phones). **Banner positioning** (`Position banner`, and straight after a new banner saves): the strip comes in front of the portrait and is dragged (pointer events, so mouse and touch; `touch-action: none` while positioning) or nudged with the arrow keys when focused (Shift for bigger steps, Escape cancels); a panel over its foot holds a `Zoom` slider (1 to 3), `Save position` and `Cancel`. The position is `object-position` in percent plus `scale(zoom)` from the same point, so it covers the strip at any width. The faint grid and the corner brackets in `--pilot` are decoration. GMs get `GM review` (pending only) and `Edit as GM` at the right of the classification line, after the status badge.
  - **"What happens next" bar**: a `--void` band joined to the header's foot, on your own sheet and any dead pilot's: a sentence-case sentence (a badge only for a change, since the cover already shows the pilot's own status), the save status ("Saving…", "Saved", red "Not saved: …"; `useSaveStatus()` in `src/saveStatus.ts`, drawn by `SaveStatus.vue`, which the mech page, GM edit bar and lore editor use too), then `.small` buttons at the right (secondary first, at most one `.primary`): a new pilot as a draft ("Draft": "GMs see it once you submit it.", `Submit pilot`), submitted ("Pending": "Waiting on a GM.", read-only, `Edit pilot` takes it back to a draft, no confirm), sent back ("Sent back", the GM's note, editable, `Resubmit pilot`), approved (`Propose changes`), drafting ("Draft": `Withdraw change`, `Submit change`), a change a GM sent back ("Sent back", the GM's note, editable, `Withdraw change`, `Submit change`), submitted ("Submitted": `Edit change`, `Withdraw change`), dead (read-only). On phones the sentence takes a row and the buttons share the next. Long notes sit in a `.notice` under it with a `.notice-title` ("Note from the GM", with the quiet `Clear note` once approved; also for a sent-back change), then the rule check.
  - **One scrolling file, no tabs** (2026-11-20): numbered sections (numbers come from position among the visible ones), `#identity`, `#pilot-id`, `#service-record`, `#capabilities`, `#qualifications`, `#equipment`, `#hangar`, `#gm-only` (GM edit mode, or a dead pilot for GMs), `#gm-review` (a pending pilot on the review route), `#gallery` (`FileSection.vue`: mono number, title, a short pilot-colour dash on a hairline, extras at the right; on phones under 40rem the hairline hides and the extras sit at the right of the title, wrapping as one group; a section's own component teleports its buttons and count into `#<id>-extra`, as `PilotIdCard`, `ServiceRecord`, `MechHangar` and `PilotGallery` do). `FileIndex.vue`: a sticky list beside the file on wide screens, under 56rem one sticky line under the top bar showing the current section, which opens the same list (2026-11-20); an `IntersectionObserver` marks the section in view (`aria-current`), a click scrolls and `router.replace`s the `#hash`, so `/pilot#hangar` links and reloads land there (the mech page's back link is `#hangar`; the mech page uses the same index and sections under its own spec sheet, see [Mech page](#mech-page)); a hash link keeps landing while content above it loads, until the reader scrolls. **Every section after Identity folds** (2026-11-20): the title is a button (`aria-expanded`, chevron before the number, lilac only on hover/focus), the body stays mounted with `v-show` so unsaved fields and open pickers survive, head extras stay visible; Identity is `fixed`. Open by default; each section's state is kept per viewer in localStorage (`src/fileSections.ts`, works without storage), and an index click or a `#section` link opens the section before scrolling. Every section shows for every viewer, except the gallery, which read-only viewers don't get when it's empty. Sections sit on the page rather than in `.panel`s; boxes stay for item cards, the ID card and the danger zone. "GM review" (`GmReview`: the pending Decision form only) is its own section on the review route; "GM only" (reputation, commendations, reward history) shows in GM edit mode (2026-11-21).
  - **01 Identity** (`IdentityGrid.vue` at full width: form-like cells for age, gender, sexuality, height, weight, eyes and hair, the last one widening so no cell is left empty; fields while editable), then Appearance, Personality and Backstory, one under another. The writing headings (`SheetField.vue`) are 16px, bold and tracked with a thin rule under the row, so they don't read as a log entry's label. **02 Pilot ID**: `PilotIdCard` alone, centred as a showcase (at most 36rem), its `Download card` in the section head. **03 Service record**: the timeline, full width. Your own approved pilot gets a "Danger zone" panel at the very end of the file (`Mark pilot dead`).
  - **Always editable, no edit buttons** (while pending): appearance, personality and backstory are open editors that save themselves 0.8s after you stop typing (`src/components/SheetField.vue`; an empty editor shows a quiet "write here..."). Callsign and name are inline inputs, the table normal inputs, all saved when you leave them. Traits are off the sheet for now (the `traits` column and the `Entry` type in `src/entries.ts` are kept; nothing shows them, and the list parser `parseEntries` was removed in the 2026-11-20 cleanup).
- **The pilot page is modular.** Each category (mechs, equipment, talents, licences, core bonuses, mech gear and so on) is a section with a `[ + ]` box to add an item.
  - For game items, `[ + ]` opens a searchable picker of pre-made items from the imported LCPs. This is how most players add things, and the sheet stores only the item's ID.
  - Mechs are added with a small form (name, manufacturer ID, appearance, image).
  - Paragraph fields (appearance, personality, traits, backstory) use a rich-text editor (TipTap, which stores formatting as structured data rather than raw HTML, so players can't inject code into each other's pages; `RichTextEditor.vue`, extensions from `editorExtensions()` in `src/richText.ts`; the TipTap-free cleaning and reading side, `sanitiseDoc()` and `docText()`, is `src/richTextSafe.ts`, so read-only pages (lore, change review) don't download the editor). Its toolbar offers bold, italic and underline; extra-small, small, normal and large font sizes; a free text colour (native colour picker plus Clear); the HORUS glitch (the HORUS logo button); inline LANCER game icons (picked from a list, `GAME_ICONS` in `src/richTextSafe.ts`); and bullet lists and small headings. The toolbar is the field's header strip (`--raised`, one bordered box with the writing area under it, outlined lilac while anything inside has focus): segmented groups: B / I / U, XS / S / M / L, colour, glitch and game icon, and the Lucide list and heading symbols, parted by thin `--rule` lines, `--tap` sized, each with an `aria-label`, `title` and `aria-pressed` (pressed: lilac text on a faint tint). On phones it stays one row and scrolls sideways. Headings and lists are whole blocks, so with text selected part-way through a paragraph the heading and list buttons first split the paragraph at the selection's edges (`splitAroundSelection()` in `src/richText.ts`, one undo step, the space at each cut dropped, never inside a list item) and only the selected words change; with just a cursor they act on the whole block. **Free hex text colour** (the developer, 2026-11-21, reversing the 2026-11-16 no-colours rule): `sanitiseDoc()` keeps only `#rrggbb`; anything else is dropped. Every editor has the full toolbar (the `html` prop only chooses the saved format). Short fields are plain inputs.
  - **No separate registration form.** `my pilot` shows an empty modular pilot page when you have no pilot, and every section (identity included) is filled in place. The first save creates the pending pilot.
  - Sections that need LANCER data (equipment, talents, licences and so on) show with their `[ + ]` boxes marked "module offline" until the packs are imported. Mechs work straight away.
  - Pilot stats and mech skills get their own section on the page, added once their starting values are decided.
- **Approved pilots** get the same sheet read-only, with no note about it (the developer removed it, 2026-10-29).
- **Shared pieces:**
  - `src/myPilot.ts` loads and saves your own pilot (or, given an id, loads anyone's read-only for their record). Saves queue up and run in order, so autosaves can't overtake each other.
  - `src/gameData.ts` loads the pilot catalogues (pilot gear from `content_items`, bionics with their bonuses, pilot stats) and the shared item shape (`Item`, `toItem`). `src/mechData.ts` loads the mech catalogues (frames, weapons, systems from `content_items`).
  - `.sheet-label` (in `src/style.css`) is the section heading: 14px, bold, UPPERCASE and tracked, in `--text`, left-aligned. A GM-only or owner-only tag goes after the title as `<span class="private">GM only</span>`, which draws the lock (there is no "Private" tag; `StatRow`, `SheetField` and `LoadoutBox` have no `tag` prop). In a flex header it takes the free space, so extra info sits at the right; a header row with a label plus extra info gets `.sheet-head`, which moves the gap below onto the row.
  - `src/components/RichTextEditor.vue` and `RichText.vue`. Anything showing nothing uses the one `.empty` state (a dashed box, a centred sentence, an optional button); `AddBox.vue` and the `// empty //` / "none." variants are gone. (The older panel components, the placeholder page and the glitching titles were removed in the scope cut.)
  - `src/richTextSafe.ts` (the allowlist sanitiser), `loadoutSlots()` and the mech rules are tested in `src/*.test.ts` (`npm test`).

## Dossier sections

- **Below, full width:**
  - **04 Capabilities:** `StatFigures.vue` (general stats as a row of five filled tiles), then Personal stats and Piloting stats (HASE) as full-width `StatRow.vue` tile rows, one above the other, set apart by space and their headings (`.stat-block`, no hairlines), each block (general, personal, piloting) followed by its own "Where these numbers come from" (`StatSources.vue`, which `StatRow` renders itself; hidden when nothing modifies that block). Every tile (general, personal, HASE, mech stats and mech resources) is filled one step lighter than what it sits on (`--panel` on the page, `--raised` on a panel, set through `--tile`), with no outline and a 3px strip of the pilot's colour along its top (`--pilot`, `--edge` without one; decoration only); numbers 30px.
  - **Personal stats** (from the `pilot_stats` table) and **piloting stats** (HASE): `src/components/StatRow.vue` on the pilot file and the mech page: the section heading with, for budgets, pips (one per point, filled while still to spend, hidden over 12 points, decoration only) and "1 of 4 points left" at the right (numbers in mono; red "1 over the 4 points" only when overspent), then a tile per stat: its symbol (personal stats and HASE have their own, `STAT_ICONS` in `src/gameData.ts`; size's shows the size), the number in mono in `--text` (the effective total), the uppercase name and - / + pinned to the tile's foot, so they line up across a row (a disabled one says why on hover). Phones (under 40rem): budgeted blocks (personal stats, HASE) become one filled row per stat with a small gap between rows and the colour strip down the left (symbol, name, number, - / +); general and mech stats stay small tiles, at least 76px wide (four to a row at 390px, three on the narrowest phones), with a two-word name wrapping onto a second centred line; words never break. Each block's sources are listed under it in "Where these numbers come from". Both are visible to everyone logged in. Personal bases start at 2, stay within 2–4, and share 4 extra allocation points. HASE remains 0–6, starts at 0 and shares 2 + level points. Each + stops at its base maximum or when its own budget is spent; lowering refunds points. Biomod bonuses do not use allocation points or alter the base limits; the tile shows the effective total and the sources list the base and each modifier, including negative ones. Personal rule checks also run while game content is unavailable. Stored in `sheet.pilot_stats` and `sheet.mech_skills`.
  - **Kept in mind for later (the developer's option A):** summary tiles, each group a bordered tile with its title and a one-line summary (e.g. "hp 6 · hase 4/5", "level 3 · 1 core bonus") that opens the group.
  - **Licences**, **core bonuses** and **talents** (05 Qualifications, stacked full width: Licences, Talents, then Core bonuses as a grid of cards; the page uses `RankPanel`'s compact `rows` mode: a frame-art thumbnail with the maker's logo and code, the name opening its information, an "Unlocks…" line, rank pips I II III with held ones filled and the numeral always shown, `Lower rank` / `Raise rank · 600` on the row while editable and the alternate-frame radios under it; talents the same with a brown tile and their summary; the item-card look ([Item cards](#item-cards)) stays in the component), shared by my pilot, pilot records and GM pilot reviews (visible to everyone logged in). ## Item cards

- **Item cards** (the prototype's ItemCard; pilot and mech loadouts, bionics, licences, talents, core bonuses): `ItemCard.vue` is the one card: a header bar in its type's colour (`--type-*`: weapon grey, system green, frame/licence purple, pilot gear/bionic teal, talent brown, core bonus lime with dark text) with the type's symbol, the name (an `InfoButton`) and, at the right, system points, mod points or a rank (hidden when 0); then the body and a foot for its buttons. Integrated items get a light line under the header. `ItemDetails.vue` fills it for a game item (`itemCard()`, `itemFacts()` and `itemRules()` in `src/itemDetails.ts`, tested in `src/itemDetails.test.ts`): the facts line (`.sep`: licence rank or maker, mount and type: "IPS-N Blackbeard II · Main Melee"; none for pilot gear), its numbers as symbol + mono number + small word (`ItemStats.vue`; damage symbols in their `--dmg-*` colour), its actions and deployables always in full, each on the card's surface under a thin rule (COMP/CON's active effects only when they're the item's only rules: `cardRules()`; `ActionChip.vue` first, then the name and frequency, the action's own range and damage, its rules), its rules text, "Where these numbers come from" (modifiers applied by `equipment.ts`) and its tag chips. `BuildItem.vue` wraps it on mechs, with the profile/prototype choices at the top of the body; a weapon with Variable damage gets a Damage type select (`Choose…` until picked, a rule problem until then, stored in `weapon_options[key].damageType`; pilot weapons: [Pilot inventory](pilots.md#pilot-inventory)). **Description** (2026-11-20): each equipped item (pilot gear, mounted mech weapons, installed systems; not built-in items) can carry its player's description, max 140 characters (`ItemNote.vue`): an italic line at the top of the body, or a `Description` text field while editable, saved on change. It goes through approval like the rest of the sheet, and goes when its item is swapped or removed (`src/itemNotes.ts`); pilot gear's lives on the owned copy (`owned_gear[].notes`), so it follows the item when it's swapped. `ActionChip.vue` is the clipped chip for Quick, Full, Reaction, Protocol, Free, Overcharge, Quick Tech, Full Tech and Invade (`activationOf()`: `--act-*` colour and cci symbol; passive draws nothing). `SlotCard.vue` is one place in a loadout: its name as a small uppercase label above (none for systems), then the card, or the empty state with a sentence and a button. Cards sit in a `.slot-grid` (`src/style.css`: CSS columns at least 20rem wide, each filling from the top like masonry, so short cards leave no gaps; cards read down each column, 2026-11-19). `ItemPicker.vue` is the searchable picker dialog. Cards for pack content (not bionics) end with a small dim "Source: <pack name>" line (`source` prop, `.pack-source` in `style.css`); `sourceOf(id)` in `gameData.ts` looks the pack up from one shared read of `content_items`, refreshed after `invalidateCatalogues()`.
- **Symbols:** `src/components/Icon.vue` draws any SVG in `src/assets/icons/` in the text colour, by `name` (e.g. `<Icon name="lock" />`) or an imported url as `src` (logos, gameData's stat symbols). The folder holds LANCER's stat/range/damage symbols, COMP/CON's cci icons (actions, sizes, ranks, item types) and Lucide's (status, privacy, interface, HASE and personal stats), split from the prototype's sprite; credited in the README.
- **Tag names** come from lancer-data's tag list (`tagNames` in `src/gameData.ts`, loaded once), e.g. "Limited {VAL}" shows as "limited 3".

The manufacturer's colour is only the dialog's border (`--mf`, through `makerColour()`; manufacturers are fetched the first time one is needed). `src/info.ts` builds the contents (`itemInfo`, `frameInfo(frame, allFrames)`, `talentInfo`, `coreBonusInfo`, `bionicInfo`); its `TONES` remain in the data but aren't drawn any more. `InfoButton.vue` is the clickable name: a real button in its surroundings' colour that underlines on hover and focus. Tag descriptions (`tagDescriptions`) and licence names (`licenceNames`) are shared lookups filled when the catalogues load. It ends with the same "Source:" line (`Info.id`, set by the pack-content builders). Tested in `src/info.test.ts`.

## Mech page

- **Mechs:** a pilot can have **several**. Each mech has:
  - a frame
  - a name, appearance description and image (all public)
  - a **manufacturer ID** the player makes up, in the format `XXXX-XXXX-XXXX` (assumed: letters and digits). It's **public**, and should be unique. Uniqueness isn't critical, so the site checks for duplicates and warns, rather than the database enforcing it.
  - weapons on the **mounts its frame provides** (for example, Blackbeard has Flex, Main and Heavy)
  - systems, shown as system points used against the total. System points are calculated, not stored.
- **Mech hangar** (`MechHangar.vue`, 07 Hangar, its count and `New mech` in the section head): `New mech` (a small button with a plus, `New mech · 500` from the second mech, blocked with "Not enough manna" when the balance can't cover it) in the heading while editable, the cards (15rem each) centred as a group, and the empty state ("No mechs yet." / "No mechs.") when there are none. A card is a showcase, so centred: a `MechImage` (size `card`, 8rem tall: the mech's own image, else its frame's art, else the maker's logo, else a frame symbol; see [Images](#images)), the mech's name in `--text`, the frame, the class (dim), the manufacturer id in mono. The maker shows as a 3px top border (`--mf`), and as the logo only in the no-art placeholder. Every viewer sees the frame now.
- **Mechs are separate objects** with their own page at `/pilot/mechs/:mechId` (`src/views/MechView.vue`), one scrolling file like my pilot (2026-11-20; no tabs, no `?tab=`): a breadcrumb (`My pilot / <mech>` back to the mechs tab, or `<list> / <CALLSIGN> / <mech>` on a record), then the **spec sheet**, one block: the **registration plate** (the prototype's, a `--raised` head band) joined to the Overview body under it. Phones: a 40px logo and the figures on a row under a rule. The GM edit bar, or on your own mech while a change is open a `--void` bar with the Draft / Submitted badge and where to submit or edit it, joins the spec sheet's foot. Then its rule check, then the file index and numbered sections (`FileSection` / `FileIndex` as on my pilot; ids prefixed `mech-` so the fold state doesn't mix with the pilot's; `#mech-loadout` links and reloads land): **01 Stats** (the mech `StatRow`, the resources tiles), **02 Loadout** (the system points meter, core bonus assignments, weapon mounts and systems), **03 Traits** (only with a frame and something to show), **04 Profile** (appearance and history, full width), **05 Registration card** (2026-11-21; the mech card, `MechIdCard.vue`, centred at most 36rem wide like 02 Pilot ID, `Download card` in the section head so it works folded; the one section that starts folded until the viewer first opens it, `FileSection`'s `folded`; see [ID cards and link previews](pilots.md#id-cards-and-link-previews)), then for an editable mech a "Danger zone" with `Scrap mech` at the very end. **Overview** (the spec sheet's body, `MechOverview.vue`, `src/mechOverview.ts`, tested in `src/mechOverview.test.ts`; 2026-11-19, symbols and numbers rather than text; the plate above already names the frame and maker, so the panel doesn't): a top row of two even columns, centred as a showcase: the frame's art (a `MechImage` of size `overview`, 16rem tall, 12rem on phones) with the role chips under it (size is on the radar; no small maker logo, the plate has it, and no licence rank, every licensed frame comes at rank II; 2026-11-21), then, only while editable, the one-line caption ("Showing your image." / "Showing the frame image. Upload your own to replace it." / "No image yet.") and the small `ImageUpload` buttons (2026-11-20; also under a frameless mech's picture) and the maker's logo small (28px, in the maker's colour) as the first chip, or, for a frame with no art, the maker's logo as the dim placeholder, and beside it the same radar as the frame information (2026-11-20, one rule for both: `radarAxes()` in `src/mechOverview.ts`, with `frameRanges()` in `src/mechData.ts`; every stat that differs between frames, size included (½ as ½), in the stat tiles' order with their full names and symbols), here with this build's own numbers, placed between the lowest and highest any frame has and clamped to the rim (`RadarChart`, up to 28rem; on phones `wrap` and 26-unit labels, as the frame information's); one column on phones. The frame information's radar wraps its labels on phones (`wrap`, see [Pickers and information](#pickers-and-information)). Then the system points meter; the loadout as a diagram, a box per mount (Flex, Main, Heavy...) whose weapon places sit on the mount's own surface parted by thin `--rule` lines (no inset boxes): a weapon-type symbol on the weapon grey, its name, damage then range as the card shows them, modifiers applied, any mod as a chip; an empty place is one slim dashed line saying "Empty"; an "Integrated" box for weapons built into the frame, and the installed systems as green-tiled chips with their SP; then bars for "Damage" (all equipped weapons added up, flat numbers per damage type, in the damage colours) and the reach (shortest to longest of each range type, with its symbol). Public mech fields live in `characters.mechs`; history, frame, mounts, systems (and quirks, off the page for now like traits) in `sheet.mechs[mechId]` (`MechPrivate` in `src/myPilot.ts`).
  - **Manufacturer colour** (2026-11-16, widened 2026-11-20 by the developer): `--mf` from the frame's `source`, matched against the manufacturers in the packs (`useManufacturers()`, `makerColour()`, `makerLogo()` in `src/archive.ts`), so a future LCP's manufacturer works with no code. Decoration only, never meaning and never on text that must be read: on the mech page it is the plate's logo and 3px top border, a faint gradient on the plate band (`color-mix` at 18% into `--raised`, fading out by 70%; every text on it measured at 4.5:1 or more for GMS, HA, HORUS, IPS-N and SSC), the section-title dashes and the stat and resource tiles' top strip (the page sets `--page-accent`, which `FileSection` and `StatRow` read before `--pilot`). Nothing else: the radar, the file index, cards and text stay neutral (see the identity colour rule in [UI principles](look-and-feel.md#ui-principles)). `--mf` is set on the mech page only for a maker with a colour of its own, so a colourless one gets the neutral fallbacks, never lilac. The hangar cards still use it only as the 3px top border (and the logo in the no-art placeholder). Frames are public, so every viewer sees the maker. LCP `logo_url` images aren't loaded (they'd make every viewer contact an outside site).
  - **Resources** (Stats): AI capacity, Limited uses, structure repair cost and overcharge heat as tiles like the stat tiles (mono value, uppercase label), then any permanent check accuracy lines.
  - **Traits**: the frame's traits as cards like the information dialog's (frame colour, trait symbol and name; the trait's rules, its other actions and uncounted bonuses inside, grouped by the reminder's `from`), in a grid of equal-height cards; then the core system as one core-coloured card (its lore, "Passive" and "Core power" each with chip, name and text); then everything else (core bonuses, equipment, missing content; talents aren't shown, the pilot page has them, though their bonuses still count, 2026-11-21) as the prototype's `.effects` rows, parted by thin rules: its symbol, an uppercase kind label ("Core bonus", "Talent: Brawler I"), the action chip if any and the bold name, the rules text, and a dim "Not counted in the stats above." for uncounted bonuses.
  - **The frame** is picked on the plate (an `IPS-N Blackbeard` button while editable, a plain info button for everyone else). Licensed frames need rank II in their licence; GMS frames (e.g. the Everest) need none. **GM-only content** (the developer, 2026-11-18, reworked 2026-11-19): two rules, in `src/rules.ts`, tested in `src/rules.test.ts`. **HORUS and NHC** (`gmOnly()`, `GM_ONLY_NAMES`; a source, type, `license` or category of that name, or a licence whose frame is theirs, ignoring case) are blocked for players in every picker (frames, weapons, systems, mods, pilot gear, licences, core bonuses, talents, biomods) with the blocked pattern and "GM only"; GMs and owners pick them anywhere (a licence a pilot already holds, granted by a GM, can still be raised with manna). **Exotic** (`isExotic()`) is selectable **only in a GM's edit mode** (`gmEditing`), blocked everywhere else with "GM edit only", also for GMs and owners on their own pilots outside edit mode. An item is Exotic if its `source` is `EXOTIC` (the pseudo-manufacturer, any case: owner-made items with no mainline manufacturer) or it carries the Exotic Gear tag `tg_exotic` (one-of-a-kind prototypes that may have a real manufacturer), on the item or in its raw data, tags as objects or plain ids (the exact id, so `tg_exoskeleton` doesn't match). Biomods count by `source` only. Type, category, licence and pack names no longer count. Every picker asks `useRestriction()` (`src/restriction.ts`): the pilot and mech pages `provide(GM_EDIT, gmEditing)` and each picker reads it, so there is no per-picker prop; `restrictionOf(thing)` gives `{ gmOnly, exotic }` and `restrictionReason()` the sentence. Enforced in the pickers, and for players also by the database at submit ([Security](approval-and-security.md#security), Security rules); GM review is the backstop. Items a GM added aren't flagged. The picker lists the unlocked ones first and blocks the rest ("needs licence II"). Changing it takes the weapons off the mounts (after an "are you sure?"), since the new frame's mounts differ. It isn't in the loadout (the developer's choice, 2026-10-29).
  - **Mech stats** are a `StatRow` with LANCER's symbols, worked out by `mechStats()` in `src/mechData.ts` from the frame, HASE and supported equipment/talent/core bonuses (see Stat modifiers, [Stats and rules text](pilots.md#stats-and-rules-text)). Unset HASE counts as 0; hp = frame + 2×hull, repair cap = frame + floor(hull÷2), heat cap = frame + engineering, evasion = frame + agility, speed = frame + floor(agility/2), e-defence and tech attack = frame + systems, system points = frame + floor(systems÷2), no grit. "–" until a frame is chosen. Stat sources and other-effect reminders are visible to everyone, like the loadout.

## Mech loadout

- **The mech loadout** (`src/components/MechLoadout.vue`) uses the same cards: a system points `.meter` at the top ("All used.", "2 left", red "1 over"), then one slot per mount the frame gives (in its order, labelled "Main mount" and so on), then the systems, with `Add system` in their heading. Mount rules (`allowedSizes()` in `src/mechData.ts`, tested in `src/mechData.test.ts`): Main takes Main or Auxiliary; Heavy takes any size; Main/Aux takes a Main and an Auxiliary; Aux/Aux two Auxiliary; Flex one Main or two Auxiliary. An empty mount is one empty state saying what it takes ("Takes one Main or two Auxiliary weapons.", `MOUNT_HINTS`) with `Add weapon`; a mount with one of two places filled shows the weapon's card and a smaller empty state for the other. A **Superheavy** weapon also takes the first other empty mount, whose empty state reads "Bracing the Superheavy weapon." (`bracingMount()` in `src/rules.ts`); the picker blocks it when no mount is free. Weapons and systems both cost system points. The pickers block (disabled button, reason beside it): items the pilot's licences don't cover ("Needs IPS-N Drake II"; listed after the unlocked ones), anything over the system points, a second copy of a Unique item, and AIs over the build's capacity. **Integrated** weapons and systems (built into a frame, e.g. the Sherman's) show as "Integrated mount" / "Integrated system" cards that can't be removed and cost nothing; talent-granted integrated items appear automatically and optional special equipment is offered only while unlocked. Effective mounts include permanent core bonus choices.
- **Weapon mods** (2026-11-17; rules in `docs/lancer-rules.md`): lancer-data's `mods.json`, content kind `mods` (a mod is a `toMod()` `Item` of type "Mod"; `LCP_KINDS`, core content, the local seed and `import_lcp`, migration `20261117190000_weapon_mods.sql`, on the hosted project; `Load core content` comes back for an install without them). **Stored** per weapon place in `sheet.mechs[id].weapon_mods` (`"mount:place"` to mod id, only a mod id; old sheets without it work); `fittedMods()` / `weaponAt()` in `mechData.ts` say which mods sit on a weapon that's there (the rest are stray: they count for nothing, the rule check names them, and `Mods without a weapon` offers `Clear unfitted`). **One per weapon, on a mounted weapon only** (not frame- or talent-integrated ones, not the Integrated Weapon mount, not a `no_mods` weapon: `modsRefused()` / `modBlockedBy()` in `equipment.ts`). The mod sits **inside its weapon's card** (`BuildItem.vue` passes `ModSection.vue` into `ItemDetails`' `mod` slot): under a thin `--rule` line, a small system-green square with the mod symbol (`mod.svg`, COMP/CON's weaponmod), its name (an `InfoButton`), its SP at the right, then `ItemBody.vue` (the card's body, shared with `ItemDetails`: facts "IPS-N Nelson II · Mod for Melee", rules text, actions, tags); while editable `Swap mod` and `Remove mod`, or the empty state "No mod." with `Add mod` (read-only sheets show a mod, never the empty state). The picker (`MechLoadout.vue`) lists every mod, blocked ones (the licence, wrong weapon type or size, a second Unique, AI capacity, SP) with the reason beside a disabled `Choose`. `equipmentDetails()` takes the weapon's mod: added range and tags change the weapon's numbers and tags (named under "Where these numbers come from"); added damage is conditional (Thermal Charge needs a hit and a charge), so it is never counted and stays in the mod's rules text (developer, 2026-11-17); a mod's `bonuses` count through `mechEffects()` like other equipment; its SP counts in the meter, the plate and `mechProblems()`. The licence ladder (`licenceUnlocks()`) and the archives (category `weapon mods`, listed by licence like systems) include mods. Change review: "Mod on Assault Rifle: Nanocomposite Adaptation" in the mech's weapon-mounts group (`changeDiff.ts`).
- **Superheavy mount (2026-11-21):** a mount type that takes only Superheavy weapons. The weapon still needs a second empty mount (`bracingMount()` in `src/rules.ts`): the frame's Heavy mount if it has one, else any other empty mount. Blocked reason: `Needs an empty mount`.
- **Mount choices (2026-11-21):** "Core bonus assignments" also lists every `replace_mount` bonus on the mech (`mountReplacements()`), labelled by its source's name, stored in `core_mounts` under the source's key. `mechEffects()` returns the built `frame`; the page reads it from there.

## Images

- **Images (built 2026-11-17):** pilot portraits and mech images, uploaded by whoever can edit the page (the player on their own pending pilot or draft change, GMs in edit mode). Pasted links aren't supported (Discord attachment links expire). The browser shrinks each picture first (`src/images.ts`: long side at most 1024px, WebP at 0.85 quality, JPEG on Safari; inputs over 20 MB refused; animated GIFs become still) and uploads it to the `character-images` Storage bucket as `<uploader's user id>/<random id>.webp` (`.jpg`). The bucket is **public to read** (pending pilots' public cards are visible to every logged-in user anyway), 1 MB, WebP and JPEG only; uploads are immutable (no update policy): users insert into their own folder only and delete from it, GMs and owners delete anywhere (migration `20261117180750_image_uploads.sql`, tested in `supabase/tests/images.test.sql`). **The card stores the path, never a URL** (`characters.pilot_image`, and `image` in each `characters.mechs` entry); `imageUrl(path)` builds the public link with no network and returns null for anything not matching `IMAGE_PATH` (a database check constraint enforces the same shape on `pilot_image`), so a tampered value can't point the page at an outside site.
- **Frame art (2026-11-19):** official frames have artwork bundled from Massif's frame images (the files COMP/CON shows, which lancer-data's `image_url` points to on Massif's CDN, not in the COMP/CON repo; GPL-3.0, credited in the README): `src/assets/frames/<frame id>.webp`, 53 files for the frames in core and the eight expansion packs the site supports (long side at most 640px, quality 82, about 4.2 MB in all; frames whose pack art is a `nodata` placeholder, Sagarmatha and Chomolungma, have none; Everest's is Massif's "NO IMAGE DATA" placeholder, so it isn't bundled either and the GMS frames all show the placeholder symbol). `frameArt(frame, frames)` in `src/images.ts` says which picture a frame shows: an owner's upload (the frame's own `image` field, an `IMAGE_PATH` path in the `character-images` bucket, never a URL, separate from the pack's ignored `image_url`), else the bundled art by frame id, else, for an alternate, its original's (tested in `src/images.test.ts`). Bundled art is `import.meta.glob(..., { query: '?url' })` without `eager`, so each image is its own lazy chunk and downloads only when shown; `MechImage.vue` resolves it (`frameArtUrl()`) and draws the `<img>`. `images.ts` imports `auth` only inside `uploadImage()`, so its pure parts load in tests without a browser. Owners upload in the frame form (see [Content editor forms](game-content.md#content-editor-forms)). **A mech with no image of its own shows its frame's**, for every viewer now that frames are public, in the hangar card, the mech page's overview (the one place the picture shows on the profile tab). The mech plate has no thumbnail, so nothing to do there. An upload always wins. **`MechImage.vue` is the one component that draws a mech's picture** (2026-11-19): see "Images" at the end of this file.
- **Images:** `src/components/Portrait.vue` is the 3:4 pilot portrait frame (photos and drawings, so it stays boxed). With no image, or when the stored file is gone (the `<img>` errors), it's a calm empty frame (`--raised` fill, thin `--rule` border) with a centred pilot symbol in `--text-dim` and the accessible label "No image". **Mech pictures are `src/components/MechImage.vue`** (2026-11-19; one component for the hangar card (`size="card"`, 8rem), the mech page's overview (`overview`, 16rem, 12rem on phones: the one place the mech's picture shows on the profile tab, a minimal Overview panel holding just the picture for a mech with no frame), licence cards (`licence`, 11rem wide, 10rem tall), the frame picker rows (`pick`, 64px, 48px on phones), the information dialog and archives pane (`info`, 16rem) and the frame editor (`editor`)). It takes the stored upload path (`src`), the frame's picture (`art`, from `frameArt()`) and the maker's logo, and always shows something, in this order: the upload (a plain picture with rounded corners, no box), else the frame art (a transparent cut-out drawn straight on the page surface, standing on the bottom edge, no shadow), else a dim `--text-dim` placeholder in the same space (the maker's logo if known, else the frame symbol, half the height). A picture that fails to load (a deleted upload, a missing file) falls through to the next one, so there is never a broken-image icon. Each size reserves its height, so the page doesn't jump while art loads and cards line up with or without art. `InfoBody` shows it for frames and licences (`Info.art` null = a frame with no art; undefined = not a frame); the frame picker keeps its mini radar when a frame has no art. It takes the stored image path (`src`) and resolves it with `imageUrl()`; the header thumbnail and hangar cards use the same helper. `ImageUpload.vue` goes under the portrait only while the page is `editable` (the Identity panel on the profile tab, the mech page's Image panel): a `.small` `Upload image` / `Replace image` (a hidden file input) and a `.quiet.small` `Remove image` (no confirmation: uploading again undoes it), "Uploading…" / "Saving…" in dim text, and a red "Not saved: …" under them. The path is saved by the page's own `updateCharacter()`, so drafts, GM edit mode, conflicts and Retry all work as for any other field. **Clean-up is best effort and client side** (`useMyPilot`: `savedImages` / `approvedImages`): a file is deleted once a successful save stops using it and the approved card (while a draft is open) doesn't; withdrawing a draft deletes the images only it used; approving a change (`GmChangeView`) deletes the approved images it replaced; an owner deleting a pilot (`GmReview`) deletes the card's and its mechs' images. Failures are ignored (a player can't delete a GM's file). Images from rejected changes stay (a `shortcut:` comment in `myPilot.ts`).
- **Pithub pictures (2026-11-23):** `pithub_entries.image` (nullable path, same `character-images` bucket, never a URL; `lore_entries` has no such column, so `src/lore.ts` types it for Pithub only and `LoreEditView` sends it only when `section.plain`). The editor's Image panel is `ImageUpload.vue` saved through the entry's normal autosave; a replaced or removed file is deleted best effort after the save works. `PithubView` draws it with `imageUrl()` in its own `.omnimgf` box and hides the box if the file fails to load.
