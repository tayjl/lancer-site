# Game content

## Game data

- Don't hand-type frames, weapons and talents. Use **Massif Press's own data** (https://github.com/massif-press).
- **Official content to enable** (each is a GitHub repo and an npm package):

  | Content | npm package |
  |---|---|
  | Core | `@massif/lancer-data` (its wiki documents the JSON format) |
  | Karrakin Trade Baronies | `@massif/ktb-data` |
  | Long Rim | `@massif/long-rim-data` |
  | Wallflower | `@massif/wallflower-data` |
  | Dustgrave | `@massif/dustgrave-data` |
  | Operation Solstice Rain | `@massif/osr-data` |
  | Operation Winter Scar | `@massif/ows-data` |
  | Shadow of the Wolf | `@massif/sotw-data` |
  | Siren's Song, A Mountain's Remorse | `@massif/ssmr-data` |

- **Licence:** every package above is **GPL-3.0-or-later** (checked in each repo's `package.json` on 2026-10-28). Software built on the data that you share must be shared as source under the same licence. This repo is public and licensed **GPL-3.0-or-later** to match (see `LICENSE`).
- **LCP tools:** `cc-lcp-editor` (makes LCPs) and `vscode-comp-con-content-authoring` (a VS Code extension that checks LCP formatting).
- **Decided: characters store item IDs, not copies.** A character saves the ID of each frame, weapon, talent and so on (the IDs used in `lancer-data` and LCPs) and the site looks up names and stats from game data. Never copy names or stats into the character. This makes homebrew and LCP import work and rules fixes in the data show up automatically.
- **Decided: the private character sheet is one JSON column (`jsonb`)**, not split across tables.
  - Why: sheets are deeply nested (pilot, mechs, loadouts, mounts). One column means fewer tables, one read and one write per sheet, and a pending change can hold a full proposed sheet in the same shape. COMP/CON exports are JSON too, which helps import.
  - Cost: the database can't check that the item IDs exist or the shape is right, so the app validates it.
  - Public info (name, callsign, images and so on) stays in normal columns apart from the sheet, because it has different visibility.
- COMP/CON (the official LANCER companion app, built with Vue) is a useful reference for structuring characters. It's GPL, so read it for ideas and don't copy code wholesale or its styling code.
- Massif's **manufacturer logos are allowed** (the developer, 2026-10-31): `src/assets/logos/` holds GMS, HA, HORUS, IPS-N and SSC from COMP/CON's `public/img/logo/` (GPL-3.0, credited in the README), cleaned to their paths only (Illustrator's wrapper and undefined entities removed).
- **Massif's Lancer Third Party License** (https://massifpress.com/legal) requires an acknowledgement that the site isn't an official Lancer product and the text "Lancer is copyright Massif Press".
  - Both are in `src/components/ThirdPartyNotice.vue`, which names the site HOR_OS. Keep the wording, only the name may change.
  - Shown under `[ uplink with discord ]` on the login screen only (the developer's choice), not on logged-in pages.

## LCP import

- **Decided:** owners add custom content by writing it in `cc-lcp-editor` and importing the `.lcp`, **or in the site's own content editor** (`/gm/content/editor`, see [Content editor](#content-editor), built in phases: 1 pilot gear, tags, core bonuses, bionics, 2 weapons, systems, mods, talents, manufacturers, 3 frames).
  - Homebrew is mostly **new content** (frames, weapons, talents and so on). The rule changes are custom pilot stats, bionics, and no grit or save target (see [Stats and rules text](pilots.md#stats-and-rules-text) and [Biomods](pilots.md#biomods)). Otherwise mech maths is standard LANCER. Bionics are not LCP content.
  - Content is added while the site runs, so it is **stored in Supabase**, not only in code.
- An `.lcp` file (Lancer Content Package) is a renamed `.zip` of JSON files in the same format as `lancer-data`, with an `lcp_manifest.json` at the top level. Subfolders are ignored. Unzipping happens in the browser, so no backend is needed.
- `active_effects` (COMP/CON's short rewordings of the rules text) are dropped on import, at any depth, by `withoutActiveEffects()` in `src/lcp.ts` (developer decision 2026-11-21).
- **Actions and rules** (2026-11-24): a pack's `actions.json` and `rules.json` import like other kinds, so the homebrew export round-trips.
  - Each row is checked with the editor's `validateItem` (errors only). A row with an error is **skipped** and named in the preview's warnings (`Skipped a row in actions.json: …`), the rest import.
  - An ID must start with `hb_`. Official actions and rules keep their seed ids (`act_*`, `rule_*`), so a pack can never replace or shadow one. A homebrew ID already in another pack is the normal conflict. Duplicate IDs in a pack are still a hard error.
  - No database change: `content_items` already stores both kinds.
- Characters refer to items by **ID**, so a missing item breaks every character using it. Imported data is **kept**, and `remove_pack` refuses while any pilot or open change uses an item of the pack.
- Suggested, not decided: import the official packs through the same LCP import, so one feature covers official content, homebrew and future expansions.
- **gm: content** (`src/views/ContentView.vue`, owners only):
  - Layout: left-aligned `.panel`s with `.panel-head` headings. The header's `Load core content` is the primary button until core is installed, then `Import a pack` is (the preview's `Import pack` while a preview is open). Native file selection opens from the small header button. Mobile tables scroll within their container.
  - Flow: choose an LCP and preview its name, author, version (mono) and description, what changes (`--ok` "+2 new", `--info` "~1 to update", dim "older items kept") and counts per kind (uppercase label and mono number rows, also in the content library). Resolve ID conflicts (`.notice.warn`), then import or update.
  - When the import can't run, `Import pack` uses the blocked pattern with the reason beside it ("Fix the item IDs first") and the explanatory sentence is hidden. Pack warnings (dependencies, advanced effects) are info `.notice`s, not errors. Messages are explicit and failed imports keep the preview for retry.
  - Installed packs are searchable by name or author in a `.table` (version in mono, item count mono and right-aligned, import date, `Update`). A compact content-library count shows the kinds. Biomods are separate campaign content.
  - **Load core content:** a small owner-only header button imports the official `@massif/lancer-data@3.1.7` through the existing atomic importer. The data is an on-demand chunk (`src/coreContent.ts`) downloaded only on click. The pinned release matches the character-sheet data format. COMP/CON's `missing_*` placeholder records are omitted.
    - `hasCoreContent()` detects core by canonical item IDs and types across frames, weapons, systems, pilot gear, talents, core bonuses and tags (including the split local seed packs), so the button disappears once core is detected and stays hidden after refresh. Partial or conflicting installs use the normal conflict preview rather than overwriting another pack.
    - Tests cover the official dataset, detection, validation and browser retry/hide. No real core import was done in tests.
  - `src/lcp.ts` uses pinned `fflate` to read ZIP data in the browser. It requires a root `lcp_manifest.json` with name, author, version and description, imports root frames, weapons, systems, mods, pilot_gear, talents, core_bonuses, tags, manufacturers, actions and rules, and lists unused files and subfolders.
    - Validates JSON, item names, unique IDs and limits (15 MB archive, 8 MB per JSON file, 20 MB expanded JSON, 10,000 items). It checks structure and IDs, not every game-rule field.
    - Declared dependencies and advanced COMP/CON v3 effects give explicit warnings and are not resolved automatically.
  - `public.import_lcp` (migration `20261029055426_import_lcp.sql`, deployed to the hosted DB, security invoker) saves the pack and all items atomically under existing owner RLS. It rechecks ownership, payload validation, cross-pack ID collisions, type changes and the expected pack ID and import timestamp. Omitted items are kept so existing pilots keep their references.
  - **Removing a pack** (owners only, a small `Remove` beside `Update`, migration `20261117173030_remove_pack.sql`, tested in `supabase/tests/remove_pack.test.sql`):
    - `remove_pack(pack_id)` deletes the pack and its items, but is refused while any pilot (dead ones too) uses one of its items, in their sheet or in an open change (draft or waiting for review). `pack_usage()` lists who uses what, matching the item id as text inside the sheet (a false match only blocks).
    - The tables have no delete grant, so these functions are the only way.
    - A pack in use shows a disabled `Remove` with "Used by WARDEN, LANTERN" (three names at most, then "and 2 more"). An unused one asks "are you sure?", then shows "Removed …" and clears the game-content cache. Removing LANCER Core is allowed the same way and `Load core content` comes back.
  - Imports clear the game-content cache (`invalidateCatalogues()`, see Gotchas). The page's item list reads every page with `fetchAll()`.
  - `src/lcp.test.ts` and `supabase/tests/lcp.test.sql` cover parsing, conflicts, role checks, updates, retained items and rollback. Database tests run in a rolled-back transaction.
- **gm: content editor** (`/gm/content/editor`, owners only): see [Content editor](#content-editor). It sits under the Content tab (which stays current). The content page's header has `Open editor` and its update preview notes the campaign edits an update keeps.

## Content editor

- **The content editor** (2026-11-17, owners only through the existing "Owners manage content items" RLS, nothing widened, mockup `docs/redesign/editor/`, Option A):
  - **Imported content is editable and edits survive pack updates.** `content_items.edited` (jsonb, null = the pack's original) holds the campaign's version. `import_lcp` only writes `data` (`on conflict ... set data`), so an update never touches `edited` (pgTAP-tested in `supabase/tests/content_editor.test.sql`).
    - `loadKind()` in `src/catalogue.ts` selects `edited` and hands every consumer `edited ?? data` as `data`, so every page sees edits with no other change. A check constraint keeps `edited->>id = id` and a name.
    - The editor shows an **Edited** badge, a `Revert to original` action (sets `edited` to null after an "are you sure?") and an **Original** tab in the preview. The update preview says how many items have campaign edits and that they're kept (an info notice, `planLcp()` counts `edited`, the page reads a cheap `edited->>id` alias, never the edit itself).
  - **New items go in one site-owned pack, `Campaign homebrew`** (`HOMEBREW_PACK`), made the first time an owner makes an item (`homebrewPack()` in `src/editorStore.ts`, a minimal valid manifest).
    - Homebrew items live in `data` (not `edited`) and **start as drafts** (`content_items.draft`, default false). `loadKind()` leaves drafts out, so no picker, archive or sheet offers them (not secret, no RLS).
    - `Publish item` (after an "are you sure?", only when nothing is unsaved) makes them live. A trigger (`private.keep_published()`) refuses a published item going back to a draft. Official items have no draft state.
  - **Saving is explicit** (`Save changes`, not autosave), because a save changes other pilots' sheets. It follows the site's save rules:
    - Every write ends in `.select()` through `checkWrite()`. `content_items`, `bionics` and `pilot_stats` have an `updated_at` (moddatetime) and updates are guarded with `.eq('updated_at', <raw string last loaded or saved>)`, so a newer save elsewhere shows `ConflictNotice` and stops saving.
    - Status via `SaveStatus` (`useSaveStatus`). `Discard changes` drops unsaved edits. `Save changes` uses the blocked pattern ("Fix 1 problem first."). Leaving with unsaved changes asks first (route guard, in-page switches and `beforeunload`). A conflict's Reload (`ConflictNotice`'s `reload` event) skips that guard, so it doesn't prompt; closing the tab still asks. `invalidateCatalogues()` runs after every write, so the site sees changes without a reload.
  - **"Used by":** `item_usage(item_id, is_bionic)` (owner-only `security definer`, same matching as `pack_usage`: the id as a quoted JSON string in a sheet or open change, bionics matched exactly because they are numbers in a list) names the pilots. The pane shows "Used by WARDEN, LANTERN and 3 more. Saving changes their sheets." (a one-line info notice).
    - `delete_content_item(id)` (owners only, refused while used, **homebrew items only**: official items are removed with their pack or reverted) is a danger-zone `Delete item` with the blocked pattern while used.
    - Bionics and personal stats have no delete (no grant): a bionic is **retired**.
  - **Bionics** (a site table) save through `save_bionic(...)`, an invoker-security function, so the bionic and its stat bonuses save all-or-nothing and a stale save is refused. A bonus must point at a stat that exists (the foreign key, the form only offers existing stats, one bonus per stat).
  - **Page** (`src/views/ContentEditorView.vue`, `src/components/editor/`, route `/gm/content/editor`, `meta.owner`, `section: 'gm-content'`, linked as `Open editor` on the content page): the archives' list + pane machinery (`useListPane`, the `.list-pane` styles, `SheetTabs` for the kinds with counts, a search).
    - Two tab rows (`TAB_GROUPS` in `src/contentEditor.ts`): a group row (not sticky, larger sentence-case tabs, no counts), then the kinds of that group (sticky, with counts). Groups: Mech content (Frames, Weapons, Systems, Weapon mods, Core bonuses, Manufacturers), Pilot content (Pilot gear, Talents), Combat rules (Rules, Actions, Tags, Definitions), Campaign (Biomods, Factions, Commendations).
    - The group comes from `?cat=` and choosing a group opens its first kind. Rules, Actions and Tags are separate kinds (the Rules tab lists rules only). An old `?cat=rules&sec=tags|actions` link is redirected once (`oldLink`).
    - Biomods, Factions and Commendations are site tables (built on the faction pane's pattern, see [Pilot profile](pilots.md#pilot-profile)). A faction is just a name (see [Reputation](pilots.md#reputation)). List grouping by manufacturer is biomods only. The personal stats tab was removed 2026-11-19: they're edited in the Supabase dashboard, and the `pilot_stats` table and everything reading it stay.
    - URL state: `?cat=` and `?item=` (`new` for a new one). The list is a box per pack, Campaign homebrew first (always, with `New <kind>`), official packs showing 40 until `Show N more` (a search shows every match). Rows show name, facts and a `Draft` or `Edited` badge.
    - The pane (`EditorPane.vue`, keyed per item): a sticky bar (name, Draft/Published/Edited, status, `Discard changes`, `Publish item`, `Save changes`), a quiet line for an imported item ("From {pack}." with `Revert to original` once edited, the bar's badge says `Official` or `Edited`, `Published` is a plain badge), the one-line used-by notice, the problems (each with the word "Error" or "Warning"), the form (every section a `FoldPanel`), the danger zone, and `Advanced: raw data` (always starts folded, for every kind including site kinds).
    - On wide panes (a container query at 54rem) the **live preview** sits beside it, sticky only while it fits the screen, so a long one such as a frame's full information scrolls with the page (`ResizeObserver` in `EditorPane.vue`).
    - **Desktop layout** (2026-11-20): the editor page has its own 120rem cap (not `--page-max`), the list is 18rem, the preview `clamp(24rem, 30%, 26rem)` and the form takes the rest (544px at 1280, 1152px at 1920). Under 56rem nothing changed.
    - `EditorPreview.vue` has the tabs Item card | Full information | Original, built with the site's own builders (`itemInfo`, `frameInfo`, `talentInfo`, `coreBonusInfo`, `bionicInfo`, `manufacturerInfo`, `ItemDetails`) from the unsaved form state. Phones: the list is a page, an item a page with a back link and Edit | Preview tabs.
  - **Every kind can also be edited through "Advanced: raw data"** (`RawDataField.vue`, a collapsed mono JSON box sharing one object with the form, broken JSON is `--danger` with the word "Error" and blocks Save). **Every kind has a form**: pilot gear, tags, core bonuses and bionics (phase 1), weapons, systems, weapon mods, talents and manufacturers (phase 2, 2026-11-17), frames (phase 3, 2026-11-18, see [Content editor forms](#content-editor-forms)).
    - Validation is one pure module, `src/contentEditor.ts` (tested in `contentEditor.test.ts` and `contentEditorForms.test.ts`): the id must stay the same, a name is required, a gear type, tags that take a value (`{VAL}` in the name) need a number, bonus formulas must parse (`bonusValue`), damage must be a number or dice (`flatDamage`, the flat number shows as "Players see 6 flat", never "average"), ranges and actions.
    - Unknown tags, bonus ids and activations, and an action with no rules text (cards only draw actions that say what they do), are **warnings**, not errors.
    - A new item's id is `hb_` + a kind code + the name's slug, unique-checked against every id and read-only (`newId()`). A **manufacturer's id is the short code you type** (`CHI`, letters, digits, `-`, `_`, `.`), fixed once created.
    - **The first listed item opens by itself on desktop** (written once into `?item=` so a later search can't swap it under unsaved edits). Phones keep the list page.
    - **Problems carry the field they belong to** (`Problem.field`, a path into the data such as `profiles.1.range.0.val`). The list at the top stays and the input also gets the danger outline, `aria-invalid` and an "Error: …" line under it (`Field.vue` and `FieldError.vue`, fed by `provideProblems()` / `useProblems()` in `useFields.ts`, so a form only names the path). A folded entry with a problem says "Needs fixing".
  - **Factions and commendations use `EditorPane` like every kind** (2026-11-24, `FactionForm.vue`, `CommendationForm.vue`, `FactionPane`, `CommendationPane` and `useSimpleEditor` are gone). Their rows save through `createItem` / `saveItem` / `deleteItem(key, kind)` in `editorStore.ts` (own tables, ids from the database, `updated_at` guard, `checkWrite`). Validation is `problemsFor` (`ctx.others` = the other rows' names). The danger zone, conflict notice, save bar and raw-data box are the pane's. No item-usage check: the database refuses the delete as before.
- **The id rule:** an id is generated from the name and fixed once created (read-only in every form, `newId()`). Exceptions are manufacturers (the short code you type) and the site tables whose ids the database makes (biomods, factions, commendations).
- **Reusable fields** (`src/components/editor/`, the frame form uses these too):
  - `Field` (label, input in its slot, hint, problem marking, `block` for rules text editors and radio groups).
  - `FoldPanel` (a folding section panel, its title a step above field labels (16px), with a one-line summary and "Needs fixing" while folded, used by every form's sections). Only Basics (Identity on frames) starts open, plus Range and damage (weapons, pilot weapons) and Stats (frames). Open or closed is remembered per kind and section title in this browser through `src/fileSections.ts`, ids `editor:{kind}:{title}`, the kind provided by `EditorPane`. `forget` opts out, as the raw data box does.
  - `RepeatList` (grouped entries as folding boxes, the first open, with up, down, remove and "Add", `fixed` for a talent's three ranks, used for a weapon's profiles, actions, deployables and ranks).
  - `ActionListField` (`ActionChip` beside the activation), `DeployableListField` (name, kind, size, HP, evasion, e-defence, armour, rules, activation, range, its own actions, a `path` prop), `DamageField` (range or damage, `path` and `noun` props).
  - `TagListField` and `BonusListField` (`path` props, only the ids the build maths counts (`BONUS_TYPES`) plus personal stats, a `replace` toggle, extra keys kept).
  - `ChoiceField` (one of a few as real radio inputs: licence rank, mount size), `ToggleChips` (several of a list as neutral `aria-pressed` chips with a tick), `ItemIdListField` (existing items by id through `ItemPicker`), `ColourField` (hex text and a picker).
  - `ItemBasics` (name, id, manufacturer, licence and rank, system points, a slot for more, shared by weapons, systems and mods).
  - `ManufacturerField` and `LicenceField` (the manufacturer select in the item, frame, core bonus and biomod forms, and licence plus rank in items and frames). The select always ends with the built-in **Exotic** option, id `EXOTIC` (`EXOTIC_MAKER` in `src/archive.ts`, a constant and not a content row).
  - `RawDataField`, `EditorPreview` (the border is a manufacturer's own colour, never lilac) and `useFields` (typed accessors over one data object replaced whole on every change).
  - Rules text is `RichTextEditor` with the `html` prop (the HTML string game data uses) and the same full toolbar as every editor. On display `src/rulesText.ts` keeps only the allowed sizes, `#rrggbb` colour, glitch, game icons and h3 and drops everything else. Inputs and selects in `.ed-form` fill their field's width (`style.css`).
- **List by manufacturer** (2026-11-21): frames, weapons, systems, weapon mods, core bonuses and biomods list in a box per manufacturer (`BY_MAKER` in `ContentEditorView.vue`: logo, count, `--mf` top border, `Other`, Exotic last, an edited item's `edited.source` moves it), with `New <kind>` above the boxes and `Show N more` per box (`expanded` is keyed by box). Pilot gear, talents, tags and manufacturers stay a box per pack, factions and commendations one box. The row doesn't repeat the manufacturer.
- **Effects, requirements, equipment** (2026-11-21): `BonusListField` is the **Effects** field.
  - Any stat or `EFFECT_BONUS_TYPES` effect (mounts, structure repair cost, drone and deployable numbers, weapon range, threat, damage and added tags, overcharge heat), a value that fits the type, and under `Options` the weapon filters, `max` (add_mount) and `Sets the base`.
  - Only what lasts out of combat and shows on the sheet is edited. In-combat and conditional effects belong in the rules text.
  - No `Only when`, weapon-size or damage-type input (nothing official or local uses them). Rows that carry `condition`, `weapon_sizes` or `damage_type` keep them untouched, and a conditional row is never counted.
  - Lists key rows by a stable id (`useRowKeys`), so rich-text editors and fold state follow the row on remove or move. `RichTextEditor` takes a changed model value (and label) from outside.
  - `RequirementListField` (a `Requirements` fold, last, on every kind but tags, manufacturers and the site tables except biomods) writes `requires`. `GrantFields` (built in, optional, `Replaces the frame's built-in weapons.`) is on core bonuses, systems, biomods, frame traits and core systems (talent ranks have the checkbox).
  - Pickers show the unmet requirement as the blocked reason `Needs Brawler II` (`unmetRequirements()` / `requirementReason()` in `rules.ts`): pilot gear, talents, licences, core bonuses and the mech page's frame picker, next to the mech loadout's.
- **Definitions tab** (2026-11-24): `?cat=definitions&item=<list key>` edits the 12 small game lists in `game_definitions` (`DEF_KINDS` in `src/definitions.ts`: label, noun, box, and which fields a list has).
  - The list column shows four boxes of lists with entry and hidden counts (`loadDefinitionFacts`). `DefinitionPane.vue` (keyed per list) edits one list as a whole: `RepeatList` rows with move up/down (the order is `sort`), label, id (made from the label until typed in, fixed once saved), icon, colour (only the game's own `--dmg-*` / `--act-*` names), mount slots and hint, and Hidden.
  - A saved row has no Remove (`removable` prop on `RepeatList`): hide it or `Delete`, which goes through `delete_definition` and is refused while used.
  - One `Save changes` sends new or changed rows through `save_definitions` (`saveDefinitions` in `editorStore.ts`, all or nothing, each saved row guarded by its raw `updated_at`). Pure rules (ids, problems, payload) are in `src/definitionEditor.ts`.
  - The pane bar styles are in `style.css` (`.editor-pane .bar`), shared with `EditorPane`. After a write, `invalidateCatalogues()` and `loadDefinitions()` refresh the pickers.
- **Effect registry** (2026-11-24): every effect type is one entry in `BONUS_REGISTRY` (`src/bonuses.ts`): id, label, picker group, value kind, scope (pilot or mech), how it is counted (`stat` with its mech stat key, `pilot`, or `effect` read by its own code), filters.
  - The editor picker (`bonusTypesFor`), validation (`problemsFor`), the one-line summary (`bonusSummary`), `isPilotBonus` and the mech sheet maths (`mechEffects`) all read it.
  - **To add a mechanic: add one entry.** A stat the mech counts needs only its `stat` key. A new effect also needs its code in `mechData.ts`.
  - Personal stats come from `pilot_stats` through `personalDef`, so an owner can add a stat and use it as an effect with no code.
  - An id not in the registry is kept, shown on the sheet as a reminder (`bonusReminder`) and warned about in the editor ("shown on the sheet but not counted"). Undeclared `pilot_*` ids are the same: a reminder, and the editor warns they aren't counted. Pilot gear effects are not read yet.
  - `bonusReminder` wording: a minimum reads "Threat range is at least 3.", a replace bonus reads "Sets speed to 4.".
- **Core power checks** (2026-11-24): a frame's core power can ask for check modifiers through `core_system.check_bonuses`, a list of `{ id, accuracy: 1 | -1, val: 0 }` (id one of hull, agility, systems, engineering, tech_attack).
  - `coreCheckBonuses()` in `src/coreRules.ts` reads the field first (an empty list means none, a non-list is ignored) and falls back to `CORE_CHECK_BONUSES` for official frame ids, so `mechEffects` is unchanged for official frames.
  - The table stays: it is the default for official frames and still keys the four core bonuses (`cb_*`) read in `mechEffects`.
  - The `Core power checks` fold in `FrameForm.vue` shows the built-in list until edited, then writes the frame's own field. It is its own small row editor, not `BonusListField`, because the effect picker has no accuracy input or check types. Validation is in `checkFrame` (`contentEditor.ts`).
- **Phase 4b** (2026-11-24):
  - Weapons get the `Equipment` fold (`GrantFields`, `checkWeapon` already checked it, `talentGrants` reads equipped weapons). Mods and pilot gear get **no** grants because the sheet never reads them there (`mechData.ts` `granting` is weapons and systems only). Biomods can't store actions (the `bionics` table has no actions column) and core systems wait for the frame form's owner.
  - The effect field has a search box (`Search effect types`, narrows every row's picker, a row keeps its own type, Add starts from the first match) and a plain `bonusSummary` line under each row.
  - **Duplicate** (pane bar, `DUPLICABLE` kinds, `duplicateItem` in `contentEditor.ts`): a new unsaved item with a new id and `Copy of X`, opened through the view's `copy` ref.
  - **Used by** for items: `referencesTo(id, rows)` scans the loaded `REFERRING_KINDS` rows (cached `loadKind`) for any value equal to the id, shown under the pilots line. Biomod references are not scanned.
  - **Core system requirements:** not added. Nothing reads a core system's requirements: `unmetRequirements` runs on the frame itself (`MechView` frame picker, `f.raw`) and on items, and `rules.ts` never reads `core_system`. The frame's own `Requirements` fold already gates the frame and its core system.
- **Export and import of actions and rules** (2026-11-24): the homebrew `.lcp` carries published `actions` and `rules` rows (`writeLcp` writes every `LCP_KINDS` file) and the importer reads them back, checking each with `validateItem` and requiring an `hb_` id (see [LCP import](#lcp-import)).
- **Hidden takes effect** (2026-11-24, phase 7c): `hidden` (`data.hidden`, `edited.hidden` for official items, `organisations.hidden`, `commendations.hidden`, biomods keep `retired`) means "not offered", never "gone".

## Content editor forms

- **The phase 2 forms** (same shapes as `@massif/lancer-data` `lib/*.json`). Fields with no input are kept untouched and reachable through the raw box. The weapon's **Can't take mods** (`no_mods`) and a deployable's activation and range have inputs now.
  - **Data-only fields** (audit, 2026-11-24): no input, never read by the site, kept as data. Why, per group:
    - `skirmish`, `synergies`, `active_synergies`, `counters`, `filter_ignore`, action `confirm`, `hide_active`, `ignore_used` and `synergy_locations`: nothing reads them; the rules text carries the wording.
    - `y_pos`, `image_url`, `other_art`: layout and art hints the site doesn't use (the frame's `image` replaces `image_url`).
    - `ammo`: there is no ammo mechanic.
    - Faction `description`: no field and no reader, left alone.
  - **Weapons** (`WeaponForm.vue`): Basics (`ItemBasics` plus mount size, `Auxiliary/Main/Heavy/Superheavy`, and weapon type), then **Range and damage** or **Profiles**, Actions, Deployables, Tags, Bonuses when equipped, and Text (rules, on attack, on hit, on critical hit, lore).
    - A weapon has one set of range and damage at the top, or `profiles[]` (`Split into profiles` moves range, damage and the on-* text into profile 1, going back to one profile folds it up again: `splitProfiles()` / `setProfiles()` in `contentEditor.ts`).
    - With profiles each has its own unique name, range and damage, and optionally its own tags, rules, on-* and actions. The weapon's own tags, rules and actions are shared and a profile's replace them while in use (how `selectWeaponProfile` merges), so empty ones are left out of the data.
    - A licence is a frame's (`license_id` is the frame id, `license` its name, `license_level` I to III). No licence is how the data writes GMS gear (`license: "GMS"`, `license_id: ""`, rank 0). Picking a licence also sets the manufacturer to the frame's.
    - Values the data has but the form doesn't offer (a `Ship-class` mount, a `Special` type) are accepted and kept.
  - **Systems** (`SystemForm.vue`): Basics (type: `System, AI, Shield, Deployable, Drone, Tech, Armor, Flight System, Integrated`, a system with no `type` shows as System and gets one only if changed), Text, Actions, Deployables, Tags, Bonuses.
  - **Weapon mods** (`ModForm.vue`): Basics, **Which weapons it fits** (`allowed_types`, `allowed_sizes`, `restricted_types`, `restricted_sizes` as `ToggleChips`, a list left empty allows everything, as `modBlockedBy` reads it), **What it adds** (`added_range`, `added_damage`, `added_tags`, added damage isn't counted in the weapon's numbers because it's conditional, so its hint asks to say when it applies in the rules text), Text, Actions, Tags, Bonuses.
  - **Talents** (`TalentForm.vue`): name, id, summary (`terse`), description, and **exactly three ranks** (I, II, III: a `fixed` `RepeatList`, a notice with `Make it three ranks` if the data has another count).
    - A rank has a name, rules text, actions, bonuses, `Built in` (`integrated`, picked from every weapon and system, even talent-only ones) and `Optional equipment` (`special_equipment`), and a checkbox for `exclusive` (the highest owned rank's built-in equipment is the only one).
    - Granted items become talent-only (`useMechData()`), so they leave the ordinary pickers. Checks: three named ranks, every granted id exists (`Context.known`).
  - **Frames** (`FrameForm.vue`, `CoreSystemFields.vue`, lancer-data's own `frames.json` shape, `y_pos`, `image_url`, `counters`, `other_art` and a core system's `active_synergies` have no input and are kept): folding `FoldPanel` sections, each with a one-line summary while folded.
    - **Identity** (open): name, read-only id, manufacturer, read-only licence id, `mechtype` roles as `ToggleChips`, the licence rank that unlocks it (None, I, II or III), the **image** and the lore as an `html` rich-text editor. The image is the frame's current picture (bundled or uploaded, with `ImageUpload.vue`). An upload goes to the owner's own folder of the `character-images` bucket (existing policies allow it) and sets the frame's `image` field. `Remove image` brings the bundled art back. A replaced or removed upload stays in the bucket, a `shortcut:` in the form.
    - **Stats** (open): every `stats` key as a number box, size one of ½, 1, 2, 3 as a select. Sensors and Save target are labelled "(not used)" and dimmed.
    - **Weapon mounts**: plain rows of a select with what the mount takes (`MOUNT_HINTS`, in `mechData.ts`) and up, down, remove (not `RepeatList`, as in the mockup).
    - **Traits** (`RepeatList`): name, use limit, rules, actions, bonuses (mech ones only), deployables.
    - **Core system**: name, lore. Passive: name, rules, actions, bonuses (counted in the stats). Core power: name, activation with its chip, lasts for, switch off with, rules, actions, bonuses (not counted in the stats: they show in the power's entry as "While active, not counted in the stats: …"). Built-in equipment through `ItemIdListField` (`useEquipmentOptions()`, shared with the talent form). Deployables.
    - **Licence unlocks** (read-only): ranks I to III, the frame itself at its rank and the weapons, systems and mods naming it, each opening its information.
    - **A frame is its own licence** (`license_id` = its id, which follows the name until the first save, `license_level` 0 for GMS, 2 otherwise), unless it is an alternate: the "Alternate of" select sets `license_id` to the original's id and `variant` to its name (`checkFrame()` refuses an alternate of itself or of another alternate). A new frame starts as GMS with plain numbers and one Main mount (`blankFrame()`).
    - `checkFrame()`: a name and a manufacturer, an `image` that is not an `IMAGE_PATH` path is an error, a licence rank 0 to 3, every non-"unused" stat a number (whole, 0 or more, tech attack may be negative, size ½/1/2/3), at least one known mount, unique non-empty trait names, a core system name, built-in ids that exist, and the shared action, bonus and deployable checks (paths such as `traits.0.actions.1.name` and `core_system.passive_bonuses.0.val`).
    - **A bonus the build maths doesn't count is never value-checked** (only warned): the data has accuracy bonuses with no `val` (`{"id":"check","accuracy":1}`) and checking them would block saving any such official frame.
    - The preview needs no "Frame card" tab: frames show Full information only.
  - **The Exotic Gear tag** (2026-11-19): every weapon, system, mod, pilot gear, frame and core bonus whose manufacturer is `EXOTIC` carries `tg_exotic`.
    - `withExoticTag()` in `src/contentEditor.ts` adds it. The editor does so as soon as the manufacturer changes (the tag list shows it, can't remove it and says "Exotic items always carry Exotic Gear.", `lockedTags()` and `TagListField`'s `locked`). `createItem()` / `saveItem()` in `src/editorStore.ts` add it again at save, so the raw data box can't skip it. Biomods have no tags.
    - Migration `20261119140000_exotic_tag.sql` (pgTAP `supabase/tests/exotic_tag.test.sql`) adds it to existing items in `data` and `edited`. A tagged prototype with a real manufacturer keeps its manufacturer.
  - **Manufacturers** (`ManufacturerForm.vue`): name, id (typed at creation), logo (one of the bundled ones, `LOGO_NAMES` in `archive.ts`, or none), main colour (`dark`, which the site draws, required, plain 6-digit hex) and darker colour (`light`, optional, not drawn yet) as `ColourField`s, motto (`quote`) and description. The preview is the full information, with the manufacturer's colour as its border and its logo.
- **Export as .lcp** (`exportHomebrew()` in `src/editorStore.ts` and `writeLcp()` in `src/lcp.ts`, `fflate`): the Campaign homebrew's **published** items, files named by kind plus a valid `lcp_manifest.json`. `src/lcp.test.ts` round-trips it through `readLcp()`.
- **Effects, Requirements and Equipment folds** (2026-11-21): every form's bonus section is **Effects** (`Effects when equipped` on weapons, systems and mods, `Passive effects` / `Power effects` on a core system). A `Requirements` fold is last on weapons, systems, mods, pilot gear, core bonuses, talents, frames and biomods. Core bonuses, systems and biomods have an `Equipment` fold (frame traits and core systems the same fields inline). A biomod keeps its `Stat bonuses` (personal stats, `bonuses`) and gains `Effects` (`effect_bonuses`, no personal stats). Checks are in `contentEditor.ts` (`checkRequires`, `checkGrants`, `effectValueProblem`), and the editor passes the talent and core bonus ids in `Context`.
- **Not built yet:** "used by N" on each list row, reordering tags, bonuses or damage.
