An editor for game content, inside the site

Owners write homebrew frames, weapons, systems and the rest in a form, with a live preview of what players will see. Everything made here lives in one pack, Campaign homebrew. Official packs can be read and copied, never changed. The frames below are the real mockup pages: scroll inside them, click a list row, switch the preview tabs.

1 · Editing a homebrew weapon

Option A, the proposed layout: the archives' list and pane, with the form in the pane and the preview beside it. Shown with two profiles, an on-hit action, three tags (one with a mistake), two bonuses, and a weapon that five pilots already use. Scroll the frame to see every section.

Save status and mistakes

Same wording and colours as the rest of the site. A mistake is red with a warning sign and the word "Error", beside the field; a blocked Save keeps its label with the reason next to it. Saving is explicit here (not autosave), because saving a used item changes other people's sheets.

Unsaved changes Saving… Saved Not saved: you don't have permission to change this, or it no longer exists. Error: Limited needs a number of uses.

2 · An official item

Official packs are read-only: no form, a lock in the list, and a Copy to homebrew button. The copy gets a new id, starts as a draft and leaves every existing sheet alone.

3 · A frame, the big one

A frame has too many parts for one long form. Each part is a folded section with a one-line summary; only Stats and Weapon mounts are open. This is an outline: the folded sections reuse the same repeaters, action pickers and tag pickers as the weapon. A frame can also be a draft, shown here with Save draft and Publish.

4 · On a phone

One screen at a time. The list is its own screen; opening an item shows the form with a back link, and the preview sits behind an Edit | Preview tab row instead of beside the form. Save stays in the sticky bar. Controls are 44px.

5 · Two layouts for the weapon screen

Option A is screen 1 above. Option B removes the separate preview: the item card itself is the form. Hovering a part outlines it; clicking opens the editor for that part in place. Here the tags are open.

Option A · form and preview side by side

  • Every field is in a fixed place and nothing is hidden, so it is easy to find, test and make accessible.
  • One pattern for all ten kinds: frames, talents and tags only change the form, not the screen.
  • Phones work naturally: Edit and Preview become two tabs.
  • You edit in one place and look in another, and the preview column is narrow on a small laptop.

Option B · edit on the card

  • What you change is what you see; it feels like building a card in COMP/CON.
  • Fewer boxes on screen for a small item like a weapon.
  • Ids, bonuses, dice, lore and raw data are not on the card, so a side panel is needed anyway.
  • Every kind needs its own clickable card, and big items like frames get crowded; small tap targets and many hidden controls are hard on phones and for keyboard use.

Notes for the developer

Where it lives

A sub-page of Content (/gm/content/editor), reached from a button on the Content page and shown in the mockups with the Content tab current and a "Packs and imports" link back. I would not add a new top-bar tab: the bar already needs about 75rem for an owner, and another tab moves the Menu drawer breakpoint further up. Content stays the pack manager (import, update, remove); the editor is where the items inside are made.

Open decisions

  1. Who edits. Owners only matches today's rule (only owners change LCP content), and the lock note reads "Owners only". "GMs and owners" would be a one-word change in the note, but it also means a policy change on the homebrew pack: GMs could then change every pilot's sheet by editing a used item.
  2. Drafts. I mocked them (a dashed "Draft" badge in the list, Save draft and Publish) so half-finished items never reach pilots' pickers and a copied official item doesn't appear twice. The cost: every picker and archive list must skip drafts, and an item in use can't go back to draft. Without drafts, Save changes is the only button and a new item is live at once.
  3. Overriding official items. Not allowed in the mockup: edits would change every pilot's sheet and be lost on the next pack update. Changing an official item means copying it, then swapping it on sheets by hand. A "swap everywhere" action could come later.
  4. The used-by notice colour. It is the info colour because the site has no caution colour; red means a rule is broken. Say if you want it stronger.

Other things the mockup assumes

  • Bionics and personal stats are site tables, not LCP content, so they sit after a divider in the tabs, have no "Campaign homebrew" box, and are left out of Export as .lcp.
  • Rules text uses the site's toolbar with bold, italic, underline and bullets only, and the same sanitiser as everywhere else. Dice become one flat number; the number shown beside the field is called "Players see", never an average.
  • The bonus picker lists only the bonus types the build maths counts. Anything else needs Advanced: raw data and is not counted. The raw box is checked with the importer's own validation before Save is allowed.
  • Reordering uses up and down buttons, not dragging, so it works with a keyboard and on phones. The grip is only a visual cue.
  • Saving an in-use item asks no confirmation of its own: the notice above the form already says who it affects. Delete is blocked, with the reason, while any pilot or open change uses the item (same rule as removing a pack).

What each phase would ship

  1. Phase 1, the small kinds: bionics, personal stats, pilot gear, tags and core bonuses. This builds the shared parts once: list and pane, save and conflict handling, the used-by check, the bonus picker, the rules-text field, Advanced: raw data, Copy to homebrew and Export as .lcp.
  2. Phase 2, the repeating kinds: talents (three ranks), weapons (profiles, ranges, damage, actions), systems and weapon mods. Adds the repeaters, activation picker and damage entries.
  3. Phase 3, frames: stats, mounts, traits, core system and deployables, in the folded layout, plus the licence ladder derived from items.
