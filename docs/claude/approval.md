# Pending approval workflow

Purpose: how new pilots and changes to approved pilots are submitted, reviewed, approved or sent back, including saving, optimistic locking and the GM review pages. Read when a task touches drafts, submission, GM review or `approve_*` / `reject_change`.

## Pending approval workflow (decided: option 2)

- The approved character stays **untouched** while a change is pending.
- Proposed changes are stored **separately** (a pending-changes table) until a GM approves or rejects them.
- Players keep a usable sheet while they wait, and the GM can see exactly what changed.
- **One pending change per character at a time.** The player can **edit or withdraw** it until a GM reviews it. Once it's **submitted**, a database trigger locks it: players can only take it back to a draft (`submitted_at` back to null, "Edit change") or withdraw it, and can never change its status, review fields or `based_on`.
- **Watch out:** if a GM edits a character directly while the player has a pending change, approving that change could overwrite the GM's edit, because the change was based on the older sheet. The approval function should catch this, for example by checking that the character hasn't changed since the pending change was made.
- GMs approve or **send back** a **whole** change, with no partial approval. Sending back needs a **note**. `review_reason` holds the GM's note for either outcome (required when sending back, optional when approving), and the player sees it. **Sending back never loses the player's work** (2026-11-19, after a player lost hours of writing): `reject_change(change_id, reason)` marks the change `rejected` (the history row; the enum value stays `rejected`) and, in the same transaction, inserts a **new draft** for the same character with the same card and sheet, `submitted_by`, `based_on` stamped with the pilot's last change at send-back (`private.pilot_last_changed()`: the GM has just reviewed the change against the pilot as it is, so a GM edit made before sending back can't leave the draft stale for ever, while any edit after it still blocks approval) and the note in `review_reason`. A draft with a `review_reason` is a **sent-back** draft. Submitting it clears the note from the draft (a trigger; the history row keeps it), like submitting a sent-back pilot. Players still can't set `review_reason` or `based_on`. Migration `20261119130000_send_back_changes.sql` also backfills a draft for every approved pilot whose latest change was rejected and has no open change.
- Approving means (1) applying the change to the character and (2) marking the pending change as approved. Both must happen in **one database function** (all-or-nothing), so a failed request can't leave half-applied data: `approve_change(change_id, expected_submitted_at, note)` (refuses if the player resubmitted since the GM opened it) and `reject_change(change_id, reason)` for changes, and `approve_pilot(target_character_id, expected_updated_at, note)` for new pilots (migration `20261116225551_approval_hardening.sql`, which also holds the triggers above). **New pilots use the same draft → submit flow as changes** (migration `20261119120000_pilot_submission.sql`, tested in `supabase/tests/approval.test.sql`; `submitPilot()` / `reopenPilot()` in `src/myPilot.ts`): the player may only set `characters.submitted_at` null → now() (the database stamps the time, and clears the GM's sent-back note) or back to null, only while pending; while it's set the player can't change the pilot's card or sheet (GMs and owners can, so GM edit mode still works). `approve_pilot` refuses an unsubmitted pilot, and a GM sending back (`send_back_pilot`) clears it. A sent-back pilot is a draft with the GM's note.
- **History** is wanted, kept simple. Suggested: don't delete reviewed changes. Keep each one with its status (approved or rejected), who reviewed it, when, and the reason. Those rows are the history.
- **Built** (2026-10-29):
  - **Saving is trustworthy** (2026-11-17; `useMyPilot` in `src/myPilot.ts`, `checkWrite()` in `src/lib/supabaseClient.ts`, tested in `src/myPilot.test.ts` and `src/lib/supabaseClient.test.ts`): saves run one at a time and each sends the **whole** card, sheet or draft as it is on screen when it runs (never a copy taken when it was queued), so two quick edits can't undo each other and a later save carries an earlier failed one. A failed save never reloads: the edit stays on screen, the status reads red "Not saved: …" with a small `Retry` that re-sends what's still unsaved (the error stays until a save succeeds), and `Submit change` / `Resubmit pilot` refuse while an edit is unsaved. Every `.update()`, `.upsert()` and `.delete()` ends in `.select()` and goes through `checkWrite()`, because RLS turns a refused write into "0 rows, no error": it reports "Not saved: You don't have permission to change this." **Never trust a write that doesn't check its rows.** The same shape applies to the pilot sheet, mech pages, GM edit mode (`GmEditBar` has the Retry too), the lore editor (every save sends the whole entry) and the GM pilots roster (typed numbers stay in the field).
  - **Newer saves are never overwritten (optimistic locking):** the card (`characters`), the sheet (`character_sheets`), the player's draft (`pending_changes`) and lore entries are updated with `.eq('updated_at', <the raw string this page last loaded or saved>)` and the page stores the new `updated_at` each save returns (never re-serialised through `Date`). When the write touches no row because the row moved on (checked with a second read, so a permission failure isn't mistaken for it), saves stop for that page and `ConflictNotice.vue` shows "Not saved" (body: "Someone else changed this. Reload to see their version.") with a `Reload` button (a full page reload). The sheet's `updated_at` only moves when `sheet` itself changes (the trigger), so a GM setting level, manna or a note doesn't cause conflicts. The first sheet save (no row yet) is an upsert, unguarded. `pending_changes.updated_at` (migration `20261116235409_pending_changes_updated_at.sql`, moddatetime like the other tables, pgTAP-tested in `approval.test.sql`) is new: **the hosted database needs this migration before the site is pushed**, or draft saves fail.
  - **Profile and session** (`src/auth.ts`, `App.vue`): if the profile can't be loaded (network, a paused free Supabase project) the page area shows "Couldn't load your profile" with the paused-project hint and `Retry` (`profileError`, `loadProfile()`), instead of sitting on "Loading…". When the session ends while the site is open (signed out in another tab, expired), `App.vue` sends you to `/login`.
  - **Drafts:** a change starts as a draft (`pending_changes.submitted_at` is null, migration `20261029024308_pending_change_drafts.sql`). It lives in the database, so it works across devices. Only submitted changes reach the GM queue, and `approve_change` refuses a draft.
  - **Player** (`src/myPilot.ts`, top strip of `PilotManageView.vue`): an approved pilot shows `[ propose changes ]`, which copies the pilot into a new draft. While a draft is open, the page and the mech pages show it and every save goes into it instead of the pilot, so they needed no changes of their own. `[ submit for review ]` puts it in the queue. A sent-back change is a draft with the GM's note (below); an approved one shows the GM's note, if any, as a "Note from the GM" notice with a `Clear note` that hides it on this device only (localStorage per change id). Once submitted, the sheet is read-only, with `[ edit change ]` (back to a draft, out of the queue) and `[ withdraw ]` (deletes it). Withdrawing a sent-back draft deletes only the draft; the rejected history row stays, and the pilot page then shows nothing about it. Buying with manna in a draft spends from the same balance.
  - **"Changed since" check:** `based_on` is set by the database when the draft is created (a trigger, so players can't fake it) to when the pilot last changed (`private.pilot_last_changed()`: the later of the card's and the sheet's `updated_at`); it never changes afterwards. The sheet's `updated_at` now only moves when the sheet itself changes, so a GM setting level, manna or a note doesn't block approval. A real edit to the pilot after the draft was made does: the review page warns and disables approve, and `approve_change` refuses it too.
  - **GM** (`gm: changes` `/gm/changes`, `src/views/GmChangesView.vue`): submitted changes, oldest submission first, in the same "Waiting for review" queue as gm: pilots (`ReviewQueue.vue`: pilot cards with "Player: x" and the waiting time), then the 20 latest reviewed changes as a "Reviewed" `.table` (pilot, status badge (`Approved` or `Sent back`), reviewer, when, note: the GM's note when sending back or optional note on an approval). Each opens `/gm/changes/:id` (`GmChangeView.vue`, titled "Change to CALLSIGN", breadcrumb `GM changes / CALLSIGN`): a summary strip `.panel` (pilot name, a `.sep` line with the player and when, a link to the record; then Balance before / Cost of change / Balance after as uppercase labels over mono numbers, like the pilot sheet's header figures; sticky under the top bar on wide, tall screens; refunds labelled as refunds). Change-tracker colours are status tokens: `--ok` for additions, positive deltas and refunds; `--danger` for spending, removals and negative balances; `--info` for remaining manna and neutral updates. Never colour alone: the key line and each line's kind keep the symbol and word, and costs keep their sign. Every line has one of five kinds (`changeDiff()` in `src/changeDiff.ts`, tested): **Added** (new) and **Raised** (a number or rank went up), + in `--ok`; **Removed** and **Lowered**, − in `--danger`; **Updated** (anything else), ~ in `--info`. Line text is sentence case and never repeats the verb ("Acuity 2 → 3", "IPS-N Drake licence, rank I → II", "Ace, rank I", "Assault Rifle"). Times ("Submitted 13h 21m ago") are in the sans font; mono is for compared figures. Reworked 2026-11-19 for readability (`reviewSections()`, `writingSummary()` and `wordCount()` in `changeDiff.ts`, `ChangeTally.vue`, all tested): under the summary strip a **Contents** `.panel` (a `nav`) holds the key line once ("+ added or raised · − removed or lowered · ~ updated", each with its symbol and tone), a `Jump to decision` link (while waiting), and one link per section with its counts (`ChangeTally`: "+3 −1 ~2", symbols and tones, words for screen readers) and its manna; the links scroll to the section (`scrollIntoView`, with `scroll-margin-top` clearing the sticky strip). Below, **one `.panel` per section in sheet order**: identity, appearance, personality, backstory, personal stats, piloting stats (never merged), biomods, loadout, licences, core bonuses, talents, then one panel per mech. Each has a `.panel-head` (title at the left; counts and manna at the right). Lines sit in **aligned columns** (kind symbol and word, then the text, then the manna in mono, right-aligned, red with a minus for spending, green with a plus for refunds, nothing when free; on phones the kind and manna share a row with the text under them), ordered added or raised, then updated, then removed or lowered. A line's manna (`DiffLine.manna`) is the sum the strip uses: licence and talent ranks at their prices, biomods at their own price (`changeDiff()` takes `prices`), and every mech after the first (the first into an empty hangar and the last one out are free). A **mech's panel** is headed "Mech: name" with its frame (looked up by the mech's id, carried on each line as `mechId`, so same-named mechs keep their own panels) and a plain "New mech" badge when it is one (a scrapped mech has its "Mech scrapped" line, which carries the refund, and no badge); identity, frame, appearance, history, weapon mounts and systems are small uppercase sub-heads inside the panel, not separate panels. **Long writing** (appearance, personality, backstory, mech appearance and history) shows one line, "Backstory rewritten · 412 → 530 words" (or "written · 530 words"), with a `Show text` / `Hide text` toggle that opens the formatted new text, and the old text beside it ("Before" / "After", two columns on wide screens, stacked on phones); no inline word highlighting. Ranks and stats show before → after. Unchanged content is omitted. There is no separate "other changes" split: removals and reductions sit in each section, last. Rule checks and stale-change warnings remain visible, (the stale warning a `.notice.warn`), followed by a plain "Decision" `.panel` (a "Note to the player" `label.field`, hint "Optional when approving, required when rejecting."; `Approve change` `.primary` through `confirmAction()` runs `approve_change` with the note, using the blocked pattern with its reason beside it when stale; `Reject change` `.danger` runs `reject_change`). The developer reverted the full-character comparison on 2026-10-29: no full pilot/mech sheets, snapshots or inline word highlighting in change review. Reviewed history cannot reconstruct the original baseline/cost; its figures are clearly labelled as proposal spending using current manna received.
  - **Pilot gear in changes** (2026-11-21): buying an item adds an owned copy to the draft; the review shows "Bought {Item}" in the loadout section with its price (`changeDiff()`'s `prices.gear`), and description edits keyed by the owned copy. Equipping is never part of a change: it goes live through `equip_pilot_gear` (which doesn't move the sheet's `updated_at`, so it never makes a change stale), the draft's `equipped_gear` is replaced by the live one on load, and `approve_change` keeps the live list. A GM's whole-sheet save on an approved pilot re-reads the live `equipped_gear` first (`write()` in `src/myPilot.ts`), so it can't undo a player's equip.
  - **Not in pending:** a change (a draft or a submitted one) is private, and players can only read their own changes, so changes stay GM-side. The pending tab lists new pilots only.
