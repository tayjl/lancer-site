# Lcp import

Covers: LCP import and the owner gm: content page.
See also: [game-data.md](game-data.md), [content-editor.md](content-editor.md).

- **Decided:** owners add custom content by writing it in `cc-lcp-editor` and importing the `.lcp`, **or in the site's own content editor** (`/gm/content/editor`, see [content-editor.md](content-editor.md), added 2026-11-17: built in phases: 1 pilot gear, tags, core bonuses, bionics; 2 weapons, systems, mods, talents, manufacturers; 3 frames). Homebrew is mostly **new content** (frames, weapons, talents and so on). The rule changes are custom pilot stats, bionics, and no grit or save target (see [stats.md](stats.md) and [biomods.md](biomods.md)). Otherwise mech maths is standard LANCER. Bionics are not LCP content (see [stats.md](stats.md) and [biomods.md](biomods.md)). Because content is added while the site is running, it has to be **stored in Supabase**, not only in the app's code.
- An `.lcp` file (Lancer Content Package) is just a renamed `.zip` of JSON files, in the same format as `lancer-data`. It must contain an `lcp_manifest.json` at the top level, and subfolders are ignored.
- Things to plan for:
  - Characters refer to items by **ID**. If an item goes missing, every character using it breaks. So imported data must be **kept**, and deleting items that characters use must be blocked: `remove_pack` refuses while any pilot or open change uses an item of the pack.
  - Unzipping can happen in the browser, so this still doesn't need a backend.
- Suggested, not decided: import the official packs through the same LCP import as homebrew. One feature then covers official content, homebrew and future expansions.
    - **gm: content** (`src/views/ContentView.vue`, owners only): working LCP import and updates (built 2026-10-29). Redesigned 2026-11-16: left-aligned `.panel`s with `.panel-head` headings and sentence-case copy; the header's `Load core content` is the primary button until core is installed, then `Import a pack` is (the preview's `Import pack` while a preview is open). Choose an LCP using the import button in the page header (the large import/drop panel was removed at the developer's request), preview its name, author, version (mono) and description, what changes (`--ok` "+2 new", `--info` "~1 to update", dim "older items kept") and its counts per kind, resolve ID conflicts (`.notice.warn`), then import/update. When the import can't run, `Import pack` uses the blocked pattern with the reason beside it ("Fix the item IDs first") and the explanatory sentence is hidden. Pack warnings (dependencies, advanced effects) are info `.notice`s, not errors. Counts per kind (the preview and the content library) are rows of an uppercase label and a mono number. Success and failure messages are explicit; failed imports keep the preview for retry. Installed packs are searchable by name/author, in a `.table` (version in mono, item count mono and right-aligned, import date, `Update`). A compact content-library count replaces the old placeholder editor grid; biomods are separate campaign content. Native file selection opens from the small header button; mobile tables scroll within their container.
      - **Load core content:** a small owner-only button in the page header imports the official `@massif/lancer-data@3.1.7` data with one click through the existing atomic importer. The data is in an on-demand chunk (`src/coreContent.ts`), so it is downloaded only when clicked; this pinned release matches the existing character-sheet data format. COMP/CON's `missing_*` placeholder records are omitted. `hasCoreContent()` detects core by canonical item IDs/types across frames, weapons, systems, pilot gear, talents, core bonuses and tags (including the split local seed packs), so the button disappears once core is detected and stays hidden after refresh. Partial/conflicting installations use the normal conflict preview rather than overwriting another pack. Tests cover the actual official dataset, detection, validation and browser retry/hide behavior. No real core import was performed during development tests.
      - `src/lcp.ts` uses pinned `fflate` to read ZIP data in the browser. Requires a root `lcp_manifest.json` with name, author, version and description. Imports root frames, weapons, systems, pilot_gear, talents, core_bonuses, tags and manufacturers; unused files/subfolders are listed. Validates JSON, item names, unique IDs and limits (15 MB archive, 8 MB per JSON file, 20 MB expanded JSON, 10,000 items). This checks structure and IDs, not every game-rule field. Declared dependencies and advanced COMP/CON v3 effects produce explicit warnings; dependency/version requirements and advanced effects are not automatically resolved.
      - `public.import_lcp` (migration `20261029055426_import_lcp.sql`, deployed to hosted DB) saves the pack and all items atomically under existing owner RLS (security invoker). Rechecks ownership, payload validation, cross-pack ID collisions, type changes and the expected pack ID/import timestamp. Keeps omitted items so existing pilots retain their references. **Removing a pack** (owners only, a small `Remove` beside `Update`; migration `20261117173030_remove_pack.sql`, tested in `supabase/tests/remove_pack.test.sql`): `remove_pack(pack_id)` deletes the pack and its items, but is refused while any pilot, dead ones too, uses one of its items, in their sheet or in an open change (a draft or one waiting for review). `pack_usage()` lists who uses what, matching the item id as text inside the sheet (a false match only blocks a removal). The tables still have no delete grant: these functions are the only way. A pack in use shows a disabled `Remove` with "Used by WARDEN, LANTERN" (three names at most, then "and 2 more") beside it; an unused one asks "are you sure?", then shows "Removed …" and clears the game-content cache. Removing LANCER Core is allowed the same way, and `Load core content` comes back. Imports clear the game-content cache (`invalidateCatalogues()`, see Gotchas), and the page's own item list reads every page with `fetchAll()`. `src/lcp.test.ts` and `supabase/tests/lcp.test.sql` cover parsing, conflicts, role checks, updates, retained items and rollback. Browser flows were checked with generated LCPs and mocked API responses; database tests run in a rolled-back transaction.
    - **gm: content editor** (`/gm/content/editor`, owners only): see [content-editor.md](content-editor.md). It sits under the Content tab (which stays current); the content page's header has `Open editor`, and its update preview notes the campaign edits an update keeps.
