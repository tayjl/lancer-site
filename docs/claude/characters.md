# Characters, sheet, levelling, biomods, mechs, reputation

Purpose: the full rules for pilots, their public/private split, profile customisation, the sheet contents, homebrew levelling and manna, biomods, mechs and reputation. Read when a task touches characters or the sheet.

## Characters (decided unless marked)

- Three tabs: **Pending**, **Approved** and **Dead**.
- **New character:** the player fills in a template and submits it, and it shows as pending. When a GM approves it, it moves to Approved. **Submission is up to the player** (the developer, 2026-11-19): a new pilot is a **draft** (`characters.submitted_at` null) until they press `Submit pilot`, and only submitted pilots reach the GM queue and the Pending tab. Starting to write is never submitting.
  - Suggested in `docs/database-sketch.md`: a new character is a normal character with status pending, which the player edits directly until a GM approves it. Pending changes are only for approved characters.
- **Every logged-in user can see every character (pending, approved and dead), and almost everything on it** (the developer, 2026-11-19: "aside from a toggled backstory, I want all pilot information to now be public"):
  - Pilot card (the `characters` row): name, callsign, age, gender, sexuality, height, weight, eye colour, hair colour, appearance description and image, personality, and traits (narrative: what the character is good at).
  - Mech card: name, appearance, image, manufacturer ID.
  - **The whole sheet except the backstory:** stats, biomods, loadout, licences, talents, core bonuses, every mech's frame, loadout, mods and history, plus **level** (and so licence level). Other players read it through `pilot_sheet(target_character_id)` (migration `20261119200000_public_sheets.sql`, tested in `supabase/tests/public_sheets.test.sql`): `security definer`, returns `(sheet, level)` with `backstory` removed, for any status, to any logged-in user (revoked from `anon`; an unknown pilot gives no row). `character_sheets` keeps its RLS (own player, GMs and owners), because it holds the backstory and the review note; a direct select by anyone else still returns nothing.
  - **Still private:** the backstory (the player can make it public, below), **manna** (the developer's correction, 2026-11-19: only the pilot's player and GMs see how much a pilot has received, spent or has left; the function never returns it, and other viewers' pages show no manna figures or manna blocks), the GM's review note (`character_sheets.review_note`), draft and submitted changes (`pending_changes`: only their own player and GMs), experience and the reward log, reputation, and anything GM-only. The function never returns the note or those tables.
- **Death:** GMs, owners, or the character's own player can mark a character dead. Everyone can see the Dead tab. Dead characters can't come back (a database trigger refuses any change away from dead, even from GMs and owners).
  - A player marking their own character dead needs **no GM approval**, just a "are you sure?" confirmation on the page.
  - Players can't update the characters table directly, so this needs a small database function. It checks that the caller owns the character (or is a GM or owner), and refuses to change a dead character back. A flash clone counts as a new character, which the player submits for approval as usual.
- **Images (built 2026-11-17):** pilot portraits and mech images, uploaded by whoever can edit the page (the player on their own pending pilot or draft change, GMs in edit mode). Pasted links aren't supported (Discord attachment links expire). The browser shrinks each picture first (`src/images.ts`: long side at most 1024px, WebP at 0.85 quality, JPEG on Safari; inputs over 20 MB refused; animated GIFs become still) and uploads it to the `character-images` Storage bucket as `<uploader's user id>/<random id>.webp` (`.jpg`). The bucket is **public to read** (pending pilots' public cards are visible to every logged-in user anyway), 1 MB, WebP and JPEG only; uploads are immutable (no update policy): users insert into their own folder only and delete from it, GMs and owners delete anywhere (migration `20261117180750_image_uploads.sql`, tested in `supabase/tests/images.test.sql`). **The card stores the path, never a URL** (`characters.pilot_image`, and `image` in each `characters.mechs` entry); `imageUrl(path)` builds the public link with no network and returns null for anything not matching `IMAGE_PATH` (a database check constraint enforces the same shape on `pilot_image`), so a tampered value can't point the page at an outside site.
- **Frame art (2026-11-19):** official frames have artwork bundled from Massif's frame images (the files COMP/CON shows, which lancer-data's `image_url` points to on Massif's CDN, not in the COMP/CON repo; GPL-3.0, credited in the README): `src/assets/frames/<frame id>.webp`, 53 files for the frames in core and the eight expansion packs the site supports (long side at most 640px, quality 82, about 4.2 MB in all; frames whose pack art is a `nodata` placeholder, Sagarmatha and Chomolungma, have none; Everest's is Massif's "NO IMAGE DATA" placeholder, so it isn't bundled either and the GMS frames all show the placeholder symbol). `frameArt(frame, frames)` in `src/images.ts` says which picture a frame shows: an owner's upload (the frame's own `image` field, an `IMAGE_PATH` path in the `character-images` bucket, never a URL, separate from the pack's ignored `image_url`), else the bundled art by frame id, else, for an alternate, its original's (tested in `src/images.test.ts`). Bundled art is `import.meta.glob(..., { query: '?url' })` without `eager`, so each image is its own lazy chunk and downloads only when shown; `MechImage.vue` resolves it (`frameArtUrl()`) and draws the `<img>`. `images.ts` imports `auth` only inside `uploadImage()`, so its pure parts load in tests without a browser. Owners upload in the frame form (below). **A mech with no image of its own shows its frame's**, for every viewer now that frames are public, in the hangar card, the mech page's overview (the one place the picture shows on the profile tab). The mech plate has no thumbnail, so nothing to do there. An upload always wins. **`MechImage.vue` is the one component that draws a mech's picture** (2026-11-19): see "Images" below.
- **Pilot profile customisation (2026-11-20, wave 1 of 2; migration `20261120090000_pilot_profile.sql`, tested in `supabase/tests/pilot_profile.test.sql`; the hosted database needs it before the site is pushed, or the registry list fails to load):** cosmetic and **public to every logged-in user**, and it **saves live with no GM approval, even on approved pilots** (game parts still go through changes). A pilot's own player writes it unless the pilot is dead; GMs and owners write any (GM edit mode in the UI).
  - **Table `pilot_profiles`** (one row per pilot, `character_id` primary key, cascade): `colour` (`#rrggbb`, check constraint), `motto` (at most 120), `banner_image` (an upload path, the same shape check as `pilot_image`), `gallery` (jsonb array of at most 4 `{path, caption}`, paths in the upload shape, captions at most 140: a trigger, `private.check_pilot_gallery()`), `updated_at`. Players insert and update (never delete); GMs and owners insert, update and delete. The uploads use the existing `character-images` bucket policies unchanged (own folder in, own folder or GM anywhere out).
  - **Wave 2 tables** (`pilot_timeline`, `commendations`, `pilot_commendations`; built in wave 2, below): `pilot_timeline` (`kind` `player` | `gm` | `auto`; `title` at most 100; `body` rich-text jsonb or null; `occurred_on`; `created_by` forced to the logged-in user, and an entry's `character_id`, `kind`, `created_by` and `created_at` never change; everyone reads; a player adds, edits and deletes their own `player` entries on their own living pilot; GMs and owners add and edit `gm` entries anywhere and delete any entry; **nobody inserts `auto` entries directly**, only the `security definer` triggers below do), `commendations` (unique `name`, `description` at most 300, `icon` = an icon name from `src/assets/icons`; everyone reads, owners manage) and `pilot_commendations` (an award: `character_id`, `commendation_id` (both cascade), `reason` at most 300, `awarded_by` forced to the logged-in user, `awarded_at`; everyone reads, GMs and owners give and take back). A dead pilot's player can't write their timeline either. Types are in `src/lib/database.types.ts`.
  - **Wave 2 (2026-11-20; migration `20261120100000_timeline_milestones.sql`, tested in `supabase/tests/timeline_milestones.test.sql`; the hosted database needs it, but only for the automatic entries: nothing else breaks without it):**
    - **Automatic service-record entries** (`kind = 'auto'`, today's date, a short title, no body, written by `security definer` triggers with a fixed `search_path`): `characters` pending → approved "Approved for duty"; → dead "Killed in action"; an approved pilot's `mechs` gaining an id "New mech: {name}"; `character_sheets.level` rising on an approved pilot "Reached level {n}"; an approved pilot's `sheet.licences` gaining a rank "{frame name} licence, rank {I/II/III}" (name from `content_items`, `edited` before `data`, else the id); a `pilot_commendations` insert "Awarded {name}" with the reason as the body (one plain rich-text paragraph). Pending pilots get no mech, licence or level entries (their approval covers it). A revoke removes nothing from the record (a GM deletes the entry by hand).
    - **Service record** (`src/serviceRecord.ts`, `useServiceRecord(characterId)`; `src/components/ServiceRecord.vue`, in 03 Service record, full width): a vertical timeline, newest first (`sortTimeline()`: date, then when written), 10 shown then `Show all N` / `Show fewer`, "No entries yet." when empty. Each entry: date (sans, dim), a `Log` / `GM` / `Record` label with a marker symbol (`KIND_MARK`: pilot, shield, flag; `auto` markers are dashed), bold title, body through `RichText`. The line and markers are `--pilot` (neutral `--edge` without one), decoration only. The pilot's own player (own living pilot, any status) adds, edits and deletes their `Log` entries; a GM in GM edit mode or on GM review adds and edits `GM` entries and can delete any entry; `Record` entries can only be deleted (by a GM). The inline form is a date, a title (100) and an optional basic rich-text body, saved with `SaveStatus`; edits are guarded by the entry's `updated_at` (`checkWrite`); deletes go through `confirmAction`.
    - **Commendations:** owners make them in the content editor's **Commendations** tab (`CommendationPane.vue`, the `FactionPane.vue` pattern for site tables: explicit save, `updated_at` guard, `checkWrite`, unsaved guards, `Delete commendation` after "Delete {name}? Pilots who have it lose it. This can't be undone."; name unique, description at most 300, an icon radio grid from `ICON_CHOICES` in `src/commendations.ts` with a live `MedalBadge` preview; `validateCommendation()` in `contentEditor.ts`; `createCommendation` / `saveCommendation` / `deleteCommendation` in `editorStore.ts`). GMs and owners award them on GM review in a `GM only` "Commendations" panel (`CommendationAward.vue`: a select, an optional reason, `Award`, and what the pilot has, each with `Revoke` after a confirm; it sits between Reputation and Reward history; an award also reloads the service record). `usePilotAwards()` loads a pilot's awards with the commendation and the awarder's name. The cover shows the medals (`CommendationBadges.vue`, nothing when there are none): the icon in a round badge ringed in `--pilot` (`MedalBadge.vue`) and the name, each a button opening a small dialog (description, reason, awarded by, date). Registry cards show a small medal and a count when above zero (`PILOT_FIELDS` embeds `awards:pilot_commendations(count)`, so it is the same single query). Icons added from Lucide for this: medal, star, shield, flame, heart, crosshair, crown (`src/icons.ts` is the shared url lookup behind `Icon.vue`).
    - **Pilot ID card** (`PilotIdCard.vue`, `src/idCard.ts`, `src/idCardExport.ts`; its own section, 02 Pilot ID, centred at most 36rem wide, with `Download card` in the section head): an in-universe Union pilot licence, a chip-card terminal read-out about the size of a credit card (an SVG drawn at 856 x 540, scaled to fit, 309px wide at 375) with the top-right and bottom-left corners cut off (`CUT`, 48). The look (redesigned 2026-11-19 as "techy", not a flat slab): the dark panel with a faint 32px grid and a static diagonal sheen in the pilot colour; the pilot colour as edge light only (the two cut corners with a blurred glow, corner brackets at the square corners and around the portrait, a short rule under the header, the licence symbol, the medals' hexagon outlines and icons); thin `--rule` hairlines; a header with the licence symbol, "PILOT LICENCE", "UNION ADMINISTRATIVE DEPARTMENT" (pilots are licensed by Union, not HORUS: no HORUS branding on the card, the developer, 2026-11-20) and a drawn contact chip; the portrait in a sharp window (the pilot symbol when none) with scan lines and a tint toward the pilot colour; "CALLSIGN" as a small mono label over the callsign (52 units, weight 600, tidied 2026-11-20), the name under it; Level and Licence level as big mono figures, Status (with a lamp in its status colour: `--ok` approved, `--dead` dead, else `--wait`) and Issued (the approved date) smaller, every label in the same small uppercase mono (22 units); a footer with a deterministic barcode of the serial (`barcodeBars()` in `src/idCard.ts`: guard bars, bars from FNV hashes, tested), `pilotSerial(id)` (`UAD-0042-XXXX-XXXX`: the padded id then two Crockford base-32 codes from an FNV hash of it, deterministic), the commendation icons as hexagon medals (six at most, then "+N"). No microtext (it ran off the card). Everything stays in the one SVG, patterns, gradients, the blur filter and masks included, and they all survive the PNG. Colours are read from the site's tokens once, because a downloaded picture has no stylesheet. **`Download card`** makes a PNG with no library: the card's SVG is cloned, every `<image>` (portrait, licence symbol, medal icons) and the two latin-subset fonts are fetched and put in as data urls (an SVG drawn as an image can't load anything outside), then it is drawn to a 2x canvas (1712 x 1080) and saved as `<callsign>-id.png`. A picture that can't be fetched is left out and the note says so ("Downloaded, without the portrait (it couldn't be fetched)."). The card shows what the page shows, so while you have an open change on your own pilot it carries the change's draft figures and card.
    - **Motto** is now a growing, wrapping textarea (Enter leaves it) instead of a one-line input, so long mottos don't clip on phones.
  - **UI** (`src/pilotProfile.ts`, `usePilotProfile(characterId)`; used by `PilotManageView.vue`): loads the row (`ready` stays false if the read fails, so nothing is saved over an unseen profile); each save sends the whole profile as it is on screen, one at a time; the first save is an upsert, later ones update with `.eq('updated_at', <raw string>)` through `checkWrite()` and set `conflict` (the page's `ConflictNotice`) when someone else saved first; failures keep the edit and `Retry` re-sends. Images no longer used are deleted best-effort after a successful save. `profileEditable` in the page is separate from the sheet's `editable`: your own living pilot (any status, so approved pilots too) or a GM in edit mode.
    - **Header:** the banner (`ImageUpload` with `noun="banner"` and `BANNER_SIDE` 1600, the only image bigger than 1024px) is the cover's top strip (9rem, 6rem on phones, `object-fit: cover`, fading into the panel at its foot, the pilot colour as a 2px line under it; uploaded in the cover's tools while editing); the motto sits under the name in italic `--text-dim` with the colour as a 3px left bar (an inline field while editable, saved on leaving it); the cover's top border is 3px in the pilot colour.
    - **Colour field** (the cover's tools): `PilotColourField.vue` (hex box and colour picker, `Reset colour`; the sheet previews the picker live and saves when you let go or leave the box).
    - **Gallery** (`PilotGallery.vue`, 08 Gallery): up to 4 thumbnails (4:3, `object-fit: cover`, four across, two columns on phones), each a button opening the full picture and caption in a `dialog.dialog`; editable: `Add picture` (hidden at 4, "4 of 4 pictures" in dim text), per picture a caption field, `Replace` and `Remove`; read-only viewers get no section when there are none. Gallery list changes are the pure functions `addPicture`, `replacePicture`, `removePicture`, `setCaption` (tested).
    - **Registry cards:** `PILOT_FIELDS` embeds `profile:pilot_profiles(colour)` so the cards load in one query, and `PilotCard` takes `colour` (a 3px top border). The GM queues' cards don't use it yet. Wave 2 adds a commendation count (below).
    - **Colour, in the page:** the sheet root gets `--pilot` (and `.has-pilot`) when a colour is set. It also gives the profile panels a 3px top border and the gallery's hover/focus outline and dialog border.
- **COMP/CON import:** dropped (the developer, 2026-11-19). Not planned.

## Character sheet contents

- **The full field list** (from the developer, 2026-10-28):
  - Profile: name, callsign, age, gender, eye colour, height, weight, sexuality, hair colour, personality, appearance description, appearance image, and traits.
  - Pilot stats: physicality, dexterity, perception, acuity, tech-fluency.
  - Mech skills: hull, systems, agility, engineering.
  - Also: licences, weapons and equipment (pilot gear only), bionics/bodymods, backstory.
  - Mechs (added in a follow-up answer): several per pilot, each with a name, appearance description, image, weapons on the frame's mounts, a manufacturer ID, and systems with system points.
  - Confirmed as staying, though not on the list: talents, core bonuses, licence level, pilot HP, manna and mod points.
- **It's a general character manager, not a combat tracker.** It doesn't track current HP, structure, stress or heat.
- **Pilot combat stats (updated 2026-10-29):** HP 6, armour 0, speed 4 and **e-defence 10** before permanent equipment/talent/core bonuses. **Pilots have no evasion** (latest developer correction); ignore `pilot_evasion` bonuses and omit them from equipment cards. Keep pilot e-defence and normal mech evasion. **Grit is shown** (the developer, 2026-11-19): a Grit tile in General stats, half the level rounded up, display only (nothing uses it). No save target or sensors. Stats are public (2026-11-19), calculated and have source disclosures.
- **Mech stats:** structure, stress, HP, heat cap, armour, evasion, speed, e-defence, tech attack, repair cap, system points and size. Speed gains floor(Agility / 2); e-defence and tech attack each gain Systems; evasion uses the normal frame + Agility formula (no pending rework). Grit, save target and sensors remain excluded. Values are calculated, never stored.
  - **Permanent build effects (2026-10-29):** `mechEffects()` collects frame traits, passive core bonuses, equipped weapons/systems (including integrated items), pilot gear, owned core bonuses and purchased talent ranks. `bonuses.ts` handles safe arithmetic (known licence/HASE/size variables, no JavaScript evaluation), replacements and highest overrides. `mechStats()` and rule checks share these effects. Armour normally caps at 4, with `armor_max` modifiers; Fomorian Frame increments size up to 3. `equipment.ts` applies matching weapon range/damage bonuses, Hunter II Thrown, selected profiles, Limited bonuses (including floor(Engineering/2)) and drone/deployable modifiers. Damage dice are converted to the flat homebrew number (rounded up) once, after modifiers. `coreRules.ts` explicitly supplements permanent core check modifiers omitted from the pinned dataset's structured bonuses; `mechEffects()` adds a supplement entry only when the frame's (or core bonus's) own structured bonuses don't already carry it (newer data gives Exposed Reactor its bonus), so it never counts twice. Conditional abilities and active core powers are readable reminders, never treated as permanently active. The mech page's "other effects and conditions" list (2026-10-31) holds frame traits and their actions, the core passive and active power, core bonuses, talent ranks and bonuses not counted in the stats, in plain wording. An action named like its trait or core power (COMP/CON's data often has both) is listed once, under the parent, with the action's chip and text (trigger and effect); the same rule applies in the full-information dialog (`absorb()` in `info.ts`), where it also takes the action's numbers. Each reminder (`Reminder` in `mechData.ts`) carries its `kind` (frame, trait, core, core-power, core-bonus, talent, item, missing), its own `name`, where it's `from` ("Brawler I"), any `activation`, and `uncounted` for bonuses the stats leave out ("+10 hp, only when exposed.", then a dim "Not counted in the stats."). It leaves out frame lore, COMP/CON's repeated `synergies` hints, equipped items' rules (their cards show them) and pilot gear (only non-`pilot_*` bonuses count on a mech). Unknown expressions/effects stay manual and are not evaluated as code.
  - **Talent grants and mount choices:** integrated talent equipment appears automatically; exclusive grants upgrade to the highest owned rank, optional special equipment is selectable only while granted. Improved Armament, Integrated Weapon and Mount Retrofitting alter mounts; Auto-Stabilizing Hardpoints and Overpower Caliber target choices are per mech. Choices live in `sheet.mechs[id].core_mounts`; per-instance profile/prototype choices live in `weapon_options` keyed `mount:place` or `integrated:item-id`. New fields are included in GM change review. Lost mounts/talent ranks, invalid targets and stale profiles are rule-checked without silently deleting saved gear. AI capacity includes The Lesson of Shaping. `mechResources()` displays AI/Limited capacity, structure repair cost, overcharge costs and permanent check accuracy separately from numeric stats.
  - **Scope explicitly confirmed:** permanent character-building effects and readable combat reminders only. No current HP, heat, overshield, status toggles, expended charges, turn tracking or active-core-power state.
- **Rules text** (2026-10-31): LANCER's rules text is small HTML. `src/rulesText.ts` parses it into an allowlist (paragraphs, bold, italic, underline, lists, line breaks; no attributes, other tags dropped) and `RulesText.vue` draws it with Vue, never `v-html`, turning top-level line breaks into spaced paragraphs (`paragraphs()`), because imported packs are untrusted. Styled by `.rules-text` in `style.css` (bold keywords in bold white). `plainText()` flattens it for one-line picker summaries. Don't strip formatting with regexes elsewhere.
- **No dice** (the developer, 2026-10-31): this homebrew involves no dice at all. **Damage** is a flat number: LANCER's dice expression converted by taking its mean rounded **up** (1d6 → 4; 2d6+1 → 8). It is the damage, not an average: never label or describe it as "average" (`damage.ts`; item cards show "kinetic 4"). Shared item cards/pickers and explicit damage phrases in rules text use this. Overcharge heat (1 → 1d3 → 1d6 → 1d6+4, or a frame's own list) is converted the same way, so the default reads 1 → 2 → 4 → 8 (`mechResources()`). Other dice left in game text (movement, rolls, Limited 1d6+2 and so on) stay as they are: the developer will give instructions for each or edit them in the content editor once it exists, so don't invent conversions. Variable/unsupported expressions remain visible; no guessed values.

- **Pilot stats are custom.** LANCER's skill triggers ("narrative triggers") are replaced by five homebrew stats: **physicality, dexterity, perception, acuity and tech-fluency**.
  - Each **base stat starts at 2**, with **4 shared points** to allocate. Base stats stay within **2–4** and don't gain points with level. Biomod modifiers are applied afterwards and can take effective totals below 2 or above 4. Existing saved allocations are not silently rewritten: out-of-range or overspent bases are flagged for correction (developer's request, 2026-10-29).
  - They're public to every logged-in user now (2026-11-19, see "Characters").
- **Mech skills** (Hull, Agility, Systems, Engineering) gain allocation points with level. Pilot HP is 6 plus equipped gear bonuses; no level bonus.
- **LANCER rules compliance** (the developer's request, 2026-10-29): `docs/lancer-rules.md` records every character rule the site follows (licences, HASE points, mounts, Superheavy, Unique, AI, system points and so on), whether it's enforced, rule-checked, left to GMs or waiting on unbuilt features. The rules are in `src/rules.ts` (tested in `src/rules.test.ts`); `useCatalogue()` there gives the loaded game content in the shape the rule checks read, for the pilot sheet, mech page and change review. Keep that file current when rules change.
  - **HASE starts at 0** with 2 + level points (changed from the earlier "start at 1" for compliance; personal stats start at 2, with four shared extra points and a base maximum of 4). A one-line change in `sheetStats()` if the developer wants 1 back.
- **Homebrew levelling and gear** (decided by the developer, 2026-10-29; `docs/lancer-rules.md`, prices in `PRICES` in `src/rules.ts`):
  - **Level** is gained narratively only: GMs and owners set it. It raises **HASE points (2 + level)** and **biomod capacity, the mod limit (6 + level)**. Nothing else.
  - **Manna buys everything else:** licence ranks **600** each, biomods (bionics) at **their own price** (`bionics.manna_cost`, set in the content editor; existing ones were set to 500 on 2026-11-18 so no balance changed), talent ranks **300** each, and **mechs: the first is free, each one after it 500** (`PRICES.extraMech`; the developer, 2026-11-19; `mannaSpent(sheet, bionicPrices, mechs)` takes the mech count from the card's `mechs` list, so scrapping a mech refunds it and pilots who already had several mechs lost 500 per extra one; the hangar's `New mech` shows `New mech · 500` from the second and uses the blocked pattern with "Not enough manna"; GM change review counts an added mech in the cost of change like any purchase). **New pilots start with 1500 manna** (`STARTING_MANNA`, the column default from migration `20261119150000_starting_manna.sql`; existing pilots keep what they have). **GMS gear is free to print**, and licensed gear (frames, weapons, systems) is free once the pilot holds that licence rank.
  - **Licence level** is just the number of licence ranks bought (no separate number).
  - **Alternate frames** (2026-11-18; packs mark one with `variant` = the original's name and usually `license_id` = the original's id, e.g. Worldkiller Genghis, Empakaai): **one licence per original frame.** `alternateOf()` / `licensedFrames()` / `licenceFrames()` / `chosenFrame()` in `mechData.ts`; the licence picker, archives' Licences and manufacturer counts list originals only, and the alternate appears in the original's ladder at its own rank. The pilot picks which frame the licence gives (`sheet.frame_choices`, licence id → frame id, free; radios on the licence card once the rank is held, a "Chosen frame" line when read-only); the frame picker blocks the other (`frameBlockedBy()` in `rules.ts`, "Licence gives X"); `mechProblems()` and `pilotProblems()` flag a mech on the wrong frame and a licence still held under an alternate's id (never auto-rewritten; a GM moves its ranks). Change review shows a changed choice as an Updated line in licences. The frame form has an "Alternate of" select. Tested in `src/alternateFrames.test.ts`.
  - **Core bonuses:** one free pick for every **3 licence ranks** bought. Each non-GMS bonus also requires **3 ranks in its manufacturer**, across any of its licences (6 for a second bonus from that manufacturer, etc.). GMS bonuses have no manufacturer requirement. The picker blocks ineligible choices; the shared rule check flags existing selections that lose eligibility, including in GM reviews. No bonus can be taken twice. Existing selections are never silently removed.
  - **Where it's stored:** `character_sheets.level` and `character_sheets.manna` (manna *received*, in total). Both are GM-only: a trigger refuses changes from anyone else, even a player whose pilot is pending (migration `20261029022434_level_and_manna.sql`, which also dropped the old hand-set `mod_points`). What's **spent** is worked out from the sheet (`mannaSpent()`), so the balance (received minus spent) can't be faked, lowering a rank refunds it, and the pickers block anything the balance can't cover.
  - **GMs set them** in the **gm: pilots** roster (editable level, experience and total manna received) or on any pilot's review page ("GM controls", `Save rewards`). Every record links there for GMs. They save on their own button only: approving or sending back never needs them (the developer's request, 2026-10-29).
  - **Experience and the reward log** (2026-11-19, migration `20261119160000_rewards_and_experience.sql`, tested in `supabase/tests/rewards.test.sql`; **the hosted database needs it before the site is pushed**, or the roster and GM controls fail to load): a **GM-only** number per pilot, 0–1000, in `pilot_progress` (`character_id` primary key, `experience`, `updated_at`; no row means 0). At 1000 the pilot is "ready to level", but nothing is automatic: a GM raises the level. Every change to a pilot's **level, manna received or experience** is recorded in `pilot_reward_log` (`character_id`, `field`, `old_value`, `new_value`, `reason`, `changed_by`, `changed_at`), by **triggers** (`private.log_sheet_rewards()` on `character_sheets`, `private.log_experience()` on `pilot_progress`, both `security definer`), so a change made anywhere, the dashboard included, is logged (with no reason, and `changed_by` null when there is no logged-in user). **Both tables are GM-only** (RLS: GMs and owners read; nobody has a write grant; players and visitors get nothing, even for their own pilot), kept apart from `character_sheets` because players can read their own sheet. Writes go through two `security definer` functions that check `is_gm()` themselves: `award(target_character_id, new_level, new_manna, new_experience, reason)` (nulls leave a field unchanged; whole numbers, 0 or more, experience at most 1000; sets the reason as a transaction-local setting `app.reward_reason` that the triggers read, all in one go) and `level_up(target_character_id, reason)` (refused below 1000 experience; level + 1, experience − 1000, reason defaults to "Level up"). The roster and GM controls call them (`src/rewards.ts`: `award()`, `levelUp()`, `rewardsProblem()`, `describeReward()`, tested in `src/rewards.test.ts`); nothing on the site writes level or manna to `character_sheets` any more. Players see nothing new.
- **Bionics / enhancements raise pilot stats.** Decided: they're the **site's own content**, not LCP content. They're stored in Supabase next to the list of custom pilot stats.
  - Each bionic has a name, a description, the stat bonuses it gives, a **manna cost** and a **mod-point cost**. A bonus can only point at a stat that exists in the list. Since 2026-11-18 (migration `20261118120000_biomod_slot_effect_price.sql`, **the hosted database needs it before the site is pushed**): `manna_cost` is the biomod's real price (`mannaSpent(sheet, bionicPrices)`, `bionicPrices` from `useGameData()`; an unknown id costs 0; changing a price moves the balance of pilots who have it), plus a `slot` (where on the body: free text with suggestions, `BIONIC_SLOTS`; empty is a warning) and an `effect` (rules-text HTML). Since 2026-11-19 (migration `20261119090000_biomod_manufacturer.sql`, **the hosted database needs it too**) a biomod has a **manufacturer**: `bionics.source`, the id of one of the packs' manufacturers (null = none, listed under "Other"; `save_bionic` takes it as a last argument, `new_source`). A HORUS, NHC or Exotic biomod is **GM edit only** for everyone, GMs and owners included (the developer, 2026-11-19; `bionicOptions` in `PilotManageView.vue` folds HORUS/NHC into the Exotic rule for biomods only; reason "GM edit only") (see "GM-only content" under the frame, below); biomods have no tags. Owners create and edit them in the content editor (`BionicForm.vue`: name, slot, manufacturer (the same option list as the item forms; empty is a warning), price, mod points, stat bonuses, description, effect). The editor tab and every visible label say "biomods". Cards and the information show the slot and price in the facts line, the effect as rules, and the description as flavour (dim, italic, like lore).
  - **Mod points:** installed bionics can't cost more than the pilot's mod limit, which is 6 + level (homebrew, above). The sheet shows points used against the limit.
  - Installing a bionic is a normal pending change: add the bionic and pay the manna. Once installed, a bionic can only be swapped for a similar one. That rule isn't coded; GMs judge it when approving.
  - Bionics are public, like the rest of the sheet (2026-11-19).
  - Characters store bionic IDs, like any other item. Only owners can add or change bionics, and stats (stats only in the Supabase dashboard: the content editor no longer edits them). One that's in use can't be deleted.
  - To start, owners can add them in the Supabase dashboard's table editor. Anyone with dashboard access can change *everything*, so only trusted people get it. An owner-only form in the site can come later.
  - Why not LCP: `cc-lcp-editor` has no bonus that targets a specific stat, reusing an existing bonus ID would clash with official items, and a custom ID would have to be typed into the JSON by hand.
- **Mechs:** a pilot can have **several**. Each mech has:
  - a frame
  - a name, appearance description and image (all public)
  - a **manufacturer ID** the player makes up, in the format `XXXX-XXXX-XXXX` (assumed: letters and digits). It's **public**, and should be unique. Uniqueness isn't critical, so the site checks for duplicates and warns, rather than the database enforcing it.
  - weapons on the **mounts its frame provides** (for example, Blackbeard has Flex, Main and Heavy)
  - systems, shown as system points used against the total. System points are calculated, not stored.
- **Licence levels:** the pilot's licence ranks in each frame, bought with manna; licence level is their total (homebrew, above).
- **Talents and core bonuses:** included.
- **Pilot equipment:** only LANCER pilot gear (armour, weapons, kit) from the game data. No free-text items.
  - **Slots** (decided by the developer, 2026-10-29): **1 armour, 2 weapons and 3 gear**, laid out like COMP/CON's loadout.
- **The pilot page is modular.** Each category (mechs, equipment, talents, licences, core bonuses, mech gear and so on) is a section with a `[ + ]` box to add an item.
  - For game items, `[ + ]` opens a searchable picker of pre-made items from the imported LCPs. This is how most players add things, and the sheet stores only the item's ID.
  - Mechs are added with a small form (name, manufacturer ID, appearance, image).
  - Paragraph fields (appearance, personality, traits, backstory) use a rich-text editor (TipTap, which stores formatting as structured data rather than raw HTML, so players can't inject code into each other's pages; `RichTextEditor.vue`, extensions from `editorExtensions()` in `src/richText.ts`; the TipTap-free cleaning and reading side, `sanitiseDoc()` and `docText()`, is `src/richTextSafe.ts`, so read-only pages (lore, change review) don't download the editor). Its toolbar offers bold, italic and underline; small, normal and large font sizes; and bullet lists and small headings. The toolbar is the field's header strip (`--raised`, one bordered box with the writing area under it, outlined lilac while anything inside has focus): three segmented groups, B / I / U, S / M / L and the Lucide list and heading symbols, parted by thin `--rule` lines, `--tap` sized, each with an `aria-label`, `title` and `aria-pressed` (pressed: lilac text on a faint tint). On phones it stays one row and scrolls sideways. Headings and lists are whole blocks, so with text selected part-way through a paragraph the heading and list buttons first split the paragraph at the selection's edges (`splitAroundSelection()` in `src/richText.ts`, one undo step, the space at each cut dropped, never inside a list item) and only the selected words change; with just a cursor they act on the whole block. **No text colours** (the developer, 2026-11-16): each colour has one meaning site-wide, so player-picked colours would read as links, warnings or notes. Colour saved before then stays in the data (the editor's schema keeps the attribute, so a later save doesn't drop it) but is drawn as normal text in the editor and in `RichText.vue` (`sanitiseDoc()` no longer passes it on; tested in `src/richText.test.ts`). Short fields are plain inputs.
  - **No separate registration form.** `my pilot` shows an empty modular pilot page when you have no pilot, and every section (identity included) is filled in place. The first save creates the pending pilot.
  - Sections that need LANCER data (equipment, talents, licences and so on) show with their `[ + ]` boxes marked "module offline" until the packs are imported. Mechs work straight away.
  - Pilot stats and mech skills get their own section on the page, added once their starting values are decided.
- **Background:** a backstory the player writes as free text. LANCER's ready-made backgrounds aren't used. **Private by default; the player can make it public** (the developer, 2026-11-19), the only part of a pilot that is private from other players, and the only section whose privacy is shown and toggled.
  - **Storage:** the backstory stays in the private sheet (`sheet.backstory`). RLS is whole-row, so a public copy lives in its own table, `pilot_public_backstory` (`character_id` primary key cascading from `characters`, `backstory jsonb`, `updated_at`), readable by every logged-in user, with **no direct writes for anyone**. **A row exists only while the backstory is public.** Migration `20261119190000_public_backstory.sql`, tested in `supabase/tests/public_backstory.test.sql`.
  - **`set_backstory_public(target_character_id, make_public)`:** `security definer`, callable by the character's own player or a GM or owner, any status. `true` upserts the row from the current `character_sheets.sheet->'backstory'`, `false` deletes it. It touches neither `characters` nor `character_sheets`, so their `updated_at` and the "changed since" approval check don't move.
  - **Following the sheet:** an after-insert-or-update-of-`sheet` trigger on `character_sheets` (`private.sync_public_backstory()`) refreshes an existing public row from the new sheet. So the public copy is the pilot's real sheet (a pending pilot's live edits, an approved pilot's approved backstory after a change is approved) and never an unapproved draft change; a player with a draft change open sees their draft in the editor but others still read the approved text.
  - **Page** (`src/backstory.ts` `useBackstoryVisibility()`, `BackstoryVisibility.vue`, in `SheetField`'s `head` slot): the Backstory panel's head has a Private | Public segmented control (real buttons with `aria-pressed`, a lock on Private) that saves at once with its own `SaveStatus` and works in every status (a submitted pilot too); while public a dim line says "Everyone logged in can read this." The pilot's own player and GM edit mode can change it; GMs and owners on records they can't edit, and the player on a record opened through the registry, see the state read-only ("Private" with the lock, or "Public"). Viewers who can't read the whole sheet row (`canSeeBackstory` false: other players) see a Backstory panel only when a public copy exists (`RichText`).
- **Not used:** skill triggers (replaced by custom pilot stats), save target, sensors, LANCER backgrounds, bonds, and (not on the field list) reserves. **Weapon mods are used** (the developer, 2026-11-17: a core part of the game): see "Weapon mods" under the mech loadout below.
- **Manna:** the in-universe currency. It isn't in LANCER's data. GMs record how much each pilot has received (`character_sheets.manna`), and what's spent is worked out from the sheet (homebrew, above). Players never change it directly. It stays private to the pilot's player and GMs (the rest of the sheet and level went public 2026-11-19, manna did not).
- **GM-only: reputation.** Each character has a reputation level with each organisation. Even the character's own player can't see it, and players can read their own sheet, so reputation can't live in the sheet. It needs its own table, plus a list of organisations. Owners manage the organisations. GMs and owners set the levels. Levels are names, not numbers, and **fixed** (the developer, 2026-11-19): Hostile, Unfriendly, Neutral, Friendly, Allied, in that order (`reputation_levels.sort_order` 1 to 5, seeded idempotently by migration `20261119180000_reputation.sql`, which also adds `organisations.updated_at` for the editor's stale-save guard; the levels have no editor). **Factions** are the `organisations` rows: owners make, rename and delete them in the content editor's **Factions** tab (a site table like biomods, but simpler: a list and a pane with just the name, `FactionPane.vue`; `createFaction` / `saveFaction` / `deleteFaction` in `src/editorStore.ts`; saving is explicit, guarded by `updated_at`, through `checkWrite()` and `SaveStatus`; unsaved-changes guards as elsewhere; a name is required and unique ignoring capitals, `validateFaction()`, shown as an error that blocks Save; `Delete faction` asks "Delete {name}? Every pilot's reputation with it is removed. This can't be undone." through `confirmAction`, and the foreign key cascades the reputation rows). **The tracker** is `src/components/ReputationPanel.vue`, a "Reputation" panel tagged `GM only` on GM review (`GmReview.vue`, between GM controls and the reward history), for pending and approved pilots (not dead ones): a row per faction (name, then a select of the five levels with "Not set" first). A change saves at once with its own Saving / Saved / Not saved status and Retry (a level is an upsert with `updated_by` set to the GM, "Not set" deletes the row; each write ends in `.select()` through `checkWrite()`; a row is locked while it saves). With no factions it says "No factions yet." and, for owners, links to the Factions tab. RLS is unchanged (GMs read and write reputation, owners manage factions and levels, players nothing) and no player page reads these tables; tested in `supabase/tests/reputation.test.sql`.
