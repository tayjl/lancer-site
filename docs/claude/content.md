# Game data, LCP import, content editor, archives

Purpose: LANCER game data sources and licence, the LCP import, the owner content editor, the content page and the archives page. Read when a task touches game content, packs, the editor or the archives.

## LANCER game data

- Don't hand-type frames, weapons and talents. Use **Massif Press's own data** (https://github.com/massif-press).
- **Official content to enable** (each is a GitHub repo and an npm package):

  | Content | npm package |
  |---|---|
  | Core | `@massif/lancer-data` (its wiki documents the JSON format) |
  | Karrakin Trade Baronies | `@massif/ktb-data` |
  | Long Rim | `@massif/long-rim-data` |
  | Wallflower | `@massif/wallflower-data` |
  | Dustgrave | `@massif/dustgrave-data` |
  | Operation Solstice Rain | `@massif/osr-data` |
  | Operation Winter Scar | `@massif/ows-data` |
  | Shadow of the Wolf | `@massif/sotw-data` |
  | Siren's Song, A Mountain's Remorse | `@massif/ssmr-data` |

- **Licence:** every package above is **GPL-3.0-or-later** (checked in each repo's `package.json` on 2026-10-28). You can use the data freely, but software built on it that you share must also be shared as source under the same licence. This repo is public and is licensed **GPL-3.0-or-later** to match (see `LICENSE`).
- **LCP tools:** `cc-lcp-editor` (a tool for making LCPs) and `vscode-comp-con-content-authoring` (a VS Code extension that checks LCP data is formatted correctly).
- **Decided: characters store item IDs, not copies of items.** A character saves the ID of each frame, weapon, talent and so on (the IDs used in `lancer-data` and LCPs), and the site looks up names and stats from the game data when showing the sheet. Don't copy names or stats into the character. This makes homebrew and LCP import work, and means rules fixes in the data show up automatically.
- **Decided: the private character sheet is one JSON column (`jsonb`)**, not split across many tables.
  - Why: sheets are deeply nested (pilot, then mechs, then loadouts, then mounts). One column means fewer tables, one read and one write per sheet, and a pending change can hold a full proposed sheet in the same shape. COMP/CON exports are JSON too, which helps with import.
  - The cost: the database can't check that the item IDs inside it exist or that the shape is right, so the app has to validate it.
  - The public info (name, callsign, images and so on) stays in normal columns, apart from the sheet, because it has different visibility.
- COMP/CON (the official LANCER companion app) is built with Vue, so it's a useful reference for how to structure characters. It's GPL licensed, though: read it for ideas, but don't copy code wholesale.

## Homebrew and .LCP import

- **Decided:** owners add custom content by writing it in `cc-lcp-editor` and importing the `.lcp`, **or in the site's own content editor** (`/gm/content/editor`, below, added 2026-11-17: built in phases: 1 pilot gear, tags, core bonuses, bionics; 2 weapons, systems, mods, talents, manufacturers; 3 frames). Homebrew is mostly **new content** (frames, weapons, talents and so on). The rule changes are custom pilot stats, bionics, and no grit or save target (see "Character sheet contents"). Otherwise mech maths is standard LANCER. Bionics are not LCP content (see "Character sheet contents"). Because content is added while the site is running, it has to be **stored in Supabase**, not only in the app's code.
- An `.lcp` file (Lancer Content Package) is just a renamed `.zip` of JSON files, in the same format as `lancer-data`. It must contain an `lcp_manifest.json` at the top level, and subfolders are ignored.
- Things to plan for:
  - Characters refer to items by **ID**. If an item goes missing, every character using it breaks. So imported data must be **kept**, and deleting items that characters use must be blocked: `remove_pack` refuses while any pilot or open change uses an item of the pack.
  - Unzipping can happen in the browser, so this still doesn't need a backend.
- Suggested, not decided: import the official packs through the same LCP import as homebrew. One feature then covers official content, homebrew and future expansions.
- **The content editor** (2026-11-17; owners only, the existing "Owners manage content items" RLS, nothing widened; mockup `docs/redesign/editor/`, Option A):
  - **Imported content is editable, and edits survive pack updates.** `content_items.edited` (jsonb, null = the pack's original) holds the campaign's version; `import_lcp` only ever writes `data` (`on conflict ... set data`), so an update never touches `edited` (pgTAP-tested in `supabase/tests/content_editor.test.sql`). `loadKind()` in `src/catalogue.ts` selects `edited` and hands every consumer `edited ?? data` as `data`, so every page sees edits with no other change. A check constraint keeps `edited->>id = id` and a name. The editor shows an **Edited** badge, a `Revert to original` action (sets `edited` to null after an "are you sure?") and an **Original** tab in the preview. The content page's update preview says how many of the pack's items have campaign edits and that they're kept (an info notice; `planLcp()` counts `edited`, and the page reads a cheap `edited->>id` alias, never the edit itself).
  - **New items go in one site-owned pack, `Campaign homebrew`** (`HOMEBREW_PACK`), made the first time an owner makes an item (`homebrewPack()` in `src/editorStore.ts`, a minimal valid manifest). Homebrew items live in `data` (not `edited`) and **start as drafts** (`content_items.draft`, default false): `loadKind()` leaves drafts out, so no picker, archive or sheet offers them (not secret, no RLS). `Publish item` (after an "are you sure?", only when nothing is unsaved) makes them live; a trigger (`private.keep_published()`) refuses a published item going back to a draft. Official items have no draft state.
  - **Saving is explicit** (`Save changes`, not autosave), because a save changes other pilots' sheets, and follows the site's save rules: every write ends in `.select()` through `checkWrite()`; `content_items`, `bionics` and `pilot_stats` have an `updated_at` (moddatetime) and updates are guarded with `.eq('updated_at', <raw string last loaded or saved>)`, so a newer save elsewhere shows `ConflictNotice` and stops saving; status via `SaveStatus` (`useSaveStatus`); `Discard changes` drops unsaved edits; `Save changes` uses the blocked pattern ("Fix 1 problem first."); leaving with unsaved changes asks first (route guard, in-page switches and `beforeunload`). `invalidateCatalogues()` runs after every write, so the rest of the site sees changes without a reload.
  - **"Used by":** `item_usage(item_id, is_bionic)` (owner-only `security definer`, same matching as `pack_usage`: the id as a quoted JSON string in a sheet or open change; bionics, being numbers in a list, are matched exactly) names the pilots. The pane shows "Used by WARDEN, LANTERN and 3 more." and "Saving changes their sheets." (an info notice). `delete_content_item(id)` (owners only, refused while used, **homebrew items only**: official items are removed with their pack, or reverted) is a danger-zone `Delete item` with the blocked pattern while used. Bionics and personal stats have no delete (no grant, as before): a bionic is **retired**.
  - **Bionics** (a site table) save through `save_bionic(...)`, an invoker-security function, so the bionic and its stat bonuses save all-or-nothing and a stale save is refused; a bonus must point at a stat that exists (the foreign key; the form only offers existing stats, one bonus per stat).
  - **Page** (`src/views/ContentEditorView.vue`, `src/components/editor/`, route `/gm/content/editor`, `meta.owner`, `section: 'gm-content'`; linked as `Open editor` on the content page): the archives' list + pane machinery (`useListPane`, the `.list-pane` styles, `SheetTabs` for the kinds with counts, a search). Tabs: Frames, Weapons, Systems, Weapon mods, Pilot gear, Talents, Core bonuses, Tags, Manufacturers, then the site tables Biomods, Factions and Commendations (wave 2, built on the faction pane's pattern, see the pilot profile section) (a faction is just a name: `FactionPane.vue`, see "GM-only: reputation"; the list grouping by manufacturer is biomods only) (the personal stats tab was removed 2026-11-19: they're edited in the Supabase dashboard; the `pilot_stats` table and everything reading it stay). URL state `?cat=` and `?item=` (`new` for a new one). The list is a box per pack, Campaign homebrew first (always, with `New <kind>`), official packs showing 40 until `Show N more` (a search shows every match); rows show name, facts and a `Draft` or `Edited` badge. The pane (`EditorPane.vue`, keyed per item): a sticky bar (name, Draft/Published/Edited, status, `Discard changes`, `Publish item`, `Save changes`), then notices (the official-content note with `Revert to original`, used-by, and the problems, each with the word "Error" or "Warning"), the form, `Advanced: raw data`, the danger zone, and beside it on wide panes (a container query at 54rem) the **live preview** (`EditorPreview.vue`: Item card | Full information | Original), built with the site's own builders (`itemInfo`, `frameInfo`, `talentInfo`, `coreBonusInfo`, `bionicInfo`, `manufacturerInfo`, `ItemDetails`) from the unsaved form state. Phones: the list is a page, an item a page with a back link and Edit | Preview tabs.
  - **Every kind is editable through "Advanced: raw data"** (`RawDataField.vue`, a collapsed JSON box in mono sharing one object with the form; broken JSON is `--danger` with the word "Error" and blocks Save). **Forms exist for pilot gear, tags, core bonuses and bionics (phase 1), weapons, systems, weapon mods, talents and manufacturers (phase 2, 2026-11-17) and frames (phase 3, 2026-11-18, below)**: every kind now has a form. Validation is one pure module, `src/contentEditor.ts` (tested in `contentEditor.test.ts` and `contentEditorForms.test.ts`): the id must stay the same, a name is required, a gear type, tags that take a value (`{VAL}` in the name) need a number, bonus formulas must parse (`bonusValue`), damage must be a number or dice (`flatDamage`; the flat number is shown as "Players see 6 flat", never "average"), ranges and actions. Unknown tags, bonus ids and activations, and an action with no rules text (cards only draw actions that say what they do), are **warnings**, not errors. A new item's id is `hb_` + a kind code + the name's slug, unique-checked against every id and read-only (`newId()`); a **manufacturer's id is the short code you type** (`CHI`, letters, digits, `-`, `_`, `.`), fixed once created. **The first listed item opens by itself on desktop** (written once into `?item=` so a later search can't swap it under unsaved edits; phones keep the list page). **Problems carry the field they belong to** (`Problem.field`, a path into the data such as `profiles.1.range.0.val`): the list at the top stays, and the input also gets the danger outline, `aria-invalid` and an "Error: …" line under it (`Field.vue` and `FieldError.vue`, fed by `provideProblems()` / `useProblems()` in `useFields.ts`, so a form only names the path; a folded entry with a problem says "Needs fixing").
  - **Reusable fields** (`src/components/editor/`; the frame form is built from these too): `Field` (label, the input in its slot, a hint, the problem marking; `block` for rules text editors and radio groups), `FoldPanel` (a folding section panel with a one-line summary and "Needs fixing" while folded, for long forms), `RepeatList` (grouped entries as folding boxes, the first open, with up, down, remove and "Add", `fixed` for a talent's three ranks; the weapon's profiles, actions, deployables and ranks all use it), `ActionListField` (`ActionChip` beside the activation), `DeployableListField` (name, kind, size, HP, evasion, e-defence, armour, rules, its own actions; a `path` prop), `DamageField` (range or damage, `path` and `noun` props), `TagListField` and `BonusListField` (`path` props; only the ids the build maths counts, `BONUS_TYPES`, plus personal stats; a `replace` toggle; extra keys kept), `ChoiceField` (one of a few as real radio inputs: licence rank, mount size), `ToggleChips` (several of a list as neutral `aria-pressed` chips with a tick), `ItemIdListField` (existing items by id through `ItemPicker`), `ColourField` (hex text and a picker), `ItemBasics` (name, id, manufacturer, licence and rank, system points, a slot for more: shared by weapons, systems and mods; the manufacturer select, here and in the frame, core bonus and biomod forms, always ends with the built-in **Exotic** option, id `EXOTIC`: `EXOTIC_MAKER` in `src/archive.ts`, a constant and not a content row), `RawDataField`, `EditorPreview` (the border is a manufacturer's own colour, never lilac) and `useFields` (typed accessors over one data object that's replaced whole on every change). Inputs and selects in `.ed-form` fill their field's width (`style.css`).
  - **The phase 2 forms** (same shapes as `@massif/lancer-data` `lib/*.json`; fields with no input, such as `skirmish`, `no_mods`, `synergies` and a deployable's `activation`, are kept untouched and reachable through the raw box):
