# Gm pages

Covers: gm: pilots, GM review, GM controls, danger zone and death.
See also: [registry.md](registry.md), [approval.md](approval.md), [levelling-and-manna.md](levelling-and-manna.md), [reputation.md](reputation.md).

- **gm: pilots** (`src/views/GmPilotsView.vue`, titled "GM pilots": each section a `.panel` with a left-aligned `.panel-head`):
  - **Waiting for review:** `ReviewQueue.vue`: a centred grid of `PilotCard`s ("Player: x", then "Waiting 3d 4h") with a plain count `.badge` beside the heading, oldest submission first (waiting time counts from `submitted_at`), linking to GM review. Submitted pilots only. With none waiting, the `.empty` state. Drafts and sent-back pilots stay in the roster (see Pilot records below) until their player submits again.
  - **Pilot records:** a full-width, scrollable table of every pilot (including dead), searchable by callsign, pilot name or player. Keep records compact in consistent single rows; on narrow screens the table scrolls horizontally within its container. Show callsign, name, player, status, level, licence level, manna received, manna left, mech names and a link to the full sheet. **Only level, experience and total manna received are editable**, saved when leaving the field through `award` (no reason; the row re-reads the pilot after each save); an **Experience** column after Level holds the number, a slim `.meter-bar` (0–1000) under it and, at 1000, a neutral `Ready to level` `.badge` with a small `Level up` button (after an "are you sure?", `level_up`); callsign and name are read-only. No give/take controls: they duplicate editing manna. Balance is received minus calculated spending; spending shows as small dim text under it (and on hover). Status is a `.badge` variant (an unsubmitted pending pilot is `Draft`, `.draft`; "Sent back" uses `.rejected` and shows the GM's note on hover); numbers are mono and right-aligned; the header row sticks while the table scrolls; each row shows "Saving…" and "Saved" (dim) or "Not saved: …" (`--danger`), like every other save status; `Open sheet` is a link drawn as a small button. Invalid numbers are refused and failed numeric saves restore the saved value. These are the developer's updated preferences (2026-10-29).
- **GM review** (`/gm/pilots/:id`, the read-only pilot page plus `src/components/GmReview.vue` at the bottom), opened from gm: pilots or any record:
  - **GM controls** after review: level, manna received and experience, plus an optional **Reason** (e.g. "Mission 3"), as `label.field`s, saved with `Save rewards` (`award`: only the fields that changed are sent, and "Nothing has changed." otherwise). At 1000 experience a `Ready to level` badge and a `Level up` button (`level_up`, with the reason) appear. Below it, a **Reward history** panel (`RewardHistory.vue`, tagged `GM only`, shown for every status): the log newest first, each line the date, the GM's name, the change in the change review's style ("Manna 1,500 → 2,000", + in `--ok` for raised and − in `--danger` for lowered, symbol plus a screen-reader word) and the reason dim; the latest 20 with `Show all`. Pending-pilot decision boxes omit the reward fields; GMs can set starting values in the pilot records roster.
  - While the pilot is pending, the "Decision" panel (a plain `.panel`, no lilac border): a "Note to the player" `label.field`, the rule check, then **Approve pilot** (`.primary`) (after an "are you sure?"; runs `approve_pilot`, which saves the note, sets the status to approved and `approved_at` in one go, and refuses if the pilot changed since the page loaded it: it compares the later of `characters.updated_at` and `character_sheets.updated_at` to the millisecond) or **Send back** (`.danger`; a note is required; runs `send_back_pilot(target_character_id, note)`, which saves the note and makes the pilot a draft again in one go). Both buttons only show once the pilot is submitted; a draft's panel says "Not submitted yet." and `approve_pilot` refuses it. Saved and sent-back messages are a `.notice.ok`. Both decisions save the entered note to `character_sheets.review_note`, shown at the top of the player's sheet. Approval notes are optional and persist after approval; the player can dismiss their own with `[ clear note ]`, using `dismiss_approval_note(target_character_id, expected_note)` (migration `20261029052117_dismiss_approval_note.sql`, deployed to the hosted project). The RPC only clears the currently displayed note on an approved pilot owned by the caller; stale requests and pending/refusal-note dismissals are refused. It changes no sheet, level or manna fields; only sent-back pilots get a resubmit button. No level or manna inputs in the pending decision box (developer's request, 2026-10-29).
  - On an approved pilot, `Mark pilot dead` (`.danger`, see Death below).
  - **Owners only, any status (dead too):** a "Danger zone" panel (faint red border, like the pilot sheet's) with `Delete pilot` (`.danger`, through `confirmAction`). It deletes the `characters` row (the sheet, mechs, changes and reputation cascade), checks the delete returned a row (RLS turns a refused delete into zero rows, not an error) and goes to `/gm/pilots`; errors show in the panel. GMs never see it.
- **Death** (in scope, the developer's choice): a player marks their own approved pilot dead from the "danger zone" panel at the end of my pilot's file, after an "are you sure?"; GMs can do it from GM controls. Both run `mark_dead()` (database), which can't be undone and withdraws any waiting change. The pilot moves to the memorial (read-only record, a dim "dead" badge), and the player gets the register form for a new pilot.
