# LANCER Campaign Site

## What this is
A website for one big LANCER (tabletop RPG) campaign and roleplay, run on a Discord server with a few GMs and many players. It tracks characters. It is not a VTT (no game board).
- **Players** create and manage their LANCER character.
- Player edits don't go live straight away. They become **pending changes**.
- **GMs** see characters and pending changes, can edit characters, and approve or reject changes. GMs can also have characters of their own.
- The campaign uses a **homebrew** version of LANCER: official content plus custom content the GMs add.
- **Scope (decided by the developer, 2026-10-29): character management only.** Pilots and their content: a clean submission → approval and change → approval pipeline, easy manna spending for players, easy levelling for GMs, and the game content pilots need (LCP import and editors, owners only). Visually clear and simple over stylised. **Out of scope for now:** reputation. (Browsing game content came back into scope on 2026-10-31 as the **archives** tab, below. **Lore** came back on 2026-11-16: GM-written entries, built as option A, a list + reading pane like the archives, chosen from the mockups in `docs/redesign/lore/`. Drafts are GM-only; published entries are visible to every logged-in user.) The reputation tables still exist in the database (decided design, unused); nothing on the site uses them.

## How the pieces fit
- The browser (Vue app hosted on Cloudflare) talks to Supabase. There's nothing in between.
- Security is enforced **in the database** with Row Level Security (RLS), never only in the frontend code, because anyone can tamper with code running in their browser.
- The one exception to "no backend": small **database functions inside Supabase** (written in SQL) for actions that must happen all-or-nothing, such as approving a change. Vue calls them with `supabase.rpc()`. They're not a server, and there should only be one or two.

## Users and roles (decided)
- **No campaigns table.** Everything belongs to the one campaign.
- Anyone can sign up, using **"Log in with Discord"** through Supabase Auth. New accounts need no GM approval (decided by the developer, 2026-11-17); email signup should be off in the hosted dashboard so Discord is the only way in.
- A **profiles** table holds one row per user: Discord name and role. New users are players. The name is the first non-blank of Discord's display name, username and name, else "Unknown pilot" (`private.discord_name()`, migration `20261117155935_profile_names.sql`, tested in `supabase/tests/profiles.test.sql`): Discord sends an empty display name for accounts without one. GMs and owners are set by hand in the Supabase dashboard.
- **Three roles:**
  - **Player:** manages their own character through pending changes.
  - **GM:** everything except managing LCP content. Edits any character, approves or rejects changes, and can have their own characters, which they edit directly without approval. GMs can't delete characters.
  - **Owner:** everything a GM can do, plus managing LCP content (importing, updating and removing packs) and deleting any character.
- Players have **one living character** at a time. When it dies, they can make a new one. GMs and owners can have several. Enforce this in the database, not just the page: the insert policy checks it, and a trigger takes a per-player lock so two requests at once can't both pass.

## Characters (decided unless marked)
- Three tabs: **Pending**, **Approved** and **Dead**.
- **New character:** the player fills in a template and submits it, and it shows as pending. When a GM approves it, it moves to Approved.
  - Suggested in `docs/database-sketch.md`: a new character is a normal character with status pending, which the player edits directly until a GM approves it. Pending changes are only for approved characters.
- **Every logged-in user can see every character (pending, approved and dead), but only the public parts:**
  - Pilot: name, callsign, age, gender, sexuality, height, weight, eye colour, hair colour, appearance description and image, personality, and traits (narrative: what the character is good at).
  - Mech: name, appearance, image, manufacturer ID.
  - Everything else (stats, loadouts and so on) is for the character's player and GMs only. It must be **really secret** (enforced by the database, not just hidden on the page), but it isn't critical, so keep the solution simple.
- **Death:** GMs, owners, or the character's own player can mark a character dead. Everyone can see the Dead tab. Dead characters can't come back (a database trigger refuses any change away from dead, even from GMs and owners).
  - A player marking their own character dead needs **no GM approval**, just a "are you sure?" confirmation on the page.
  - Players can't update the characters table directly, so this needs a small database function. It checks that the caller owns the character (or is a GM or owner), and refuses to change a dead character back. A flash clone counts as a new character, which the player submits for approval as usual.
- **Images:** store uploads in Supabase Storage (1 GB on the free tier). Discord attachment links expire after about a day, so pasted Discord links won't work. Pending characters are visible to everyone, so an uploaded image is public before a GM has reviewed it.
- **COMP/CON import:** wanted, if it's not too hard. It only pre-fills the new-character form, and the result still goes through normal approval. Build it after the core features work.

## Character sheet contents

  - Pilot stats: physicality, dexterity, perception, acuity, tech-fluency.
  - Mech skills: hull, systems, agility, engineering.
  - Also: licences, weapons and equipment (pilot gear only), bionics/bodymods, backstory.
  - Mechs (added in a follow-up answer): several per pilot, each with a name, appearance description, image, weapons on the frame's mounts, a manufacturer ID, and systems with system points.
  - Confirmed as staying, though not on the list: talents, core bonuses, licence level, pilot HP, manna and mod points.
- **It's a general character manager, not a combat tracker.** It doesn't track current HP, structure, stress or heat.
- **Pilot combat stats (updated 2026-10-29):** HP 6, armour 0, speed 4 and **e-defence 10** before permanent equipment/talent/core bonuses. **Pilots have no evasion** (latest developer correction); ignore `pilot_evasion` bonuses and omit them from equipment cards. Keep pilot e-defence and normal mech evasion. No grit, save target or sensors. Stats are private, calculated and have source disclosures.
- **Mech stats:** structure, stress, HP, heat cap, armour, evasion, speed, e-defence, tech attack, repair cap, system points and size. Speed gains floor(Agility / 2); e-defence and tech attack each gain Systems; evasion uses the normal frame + Agility formula (no pending rework). Grit, save target and sensors remain excluded. Values are calculated, never stored.
  - **Permanent build effects (2026-10-29):** `mechEffects()` collects frame traits, passive core bonuses, equipped weapons/systems (including integrated items), pilot gear, owned core bonuses and purchased talent ranks. `bonuses.ts` handles safe arithmetic (known licence/HASE/size variables, no JavaScript evaluation), replacements and highest overrides. `mechStats()` and rule checks share these effects. Armour normally caps at 4, with `armor_max` modifiers; Fomorian Frame increments size up to 3. `equipment.ts` applies matching weapon range/damage bonuses, Hunter II Thrown, selected profiles, Limited bonuses (including floor(Engineering/2)) and drone/deployable modifiers. Damage dice are converted to the flat homebrew number (rounded up) once, after modifiers. `coreRules.ts` explicitly supplements permanent core check modifiers omitted from the pinned dataset's structured bonuses; `mechEffects()` adds a supplement entry only when the frame's (or core bonus's) own structured bonuses don't already carry it (newer data gives Exposed Reactor its bonus), so it never counts twice. Conditional abilities and active core powers are readable reminders, never treated as permanently active. The mech page's "other effects and conditions" list (2026-10-31) holds frame traits and their actions, the core passive and active power, core bonuses, talent ranks and bonuses not counted in the stats, in plain wording. An action named like its trait or core power (COMP/CON's data often has both) is listed once, under the parent, with the action's chip and text (trigger and effect); the same rule applies in the full-information dialog (`absorb()` in `info.ts`), where it also takes the action's numbers. Each reminder (`Reminder` in `mechData.ts`) carries its `kind` (frame, trait, core, core-power, core-bonus, talent, item, missing), its own `name`, where it's `from` ("Brawler I"), any `activation`, and `uncounted` for bonuses the stats leave out ("+10 hp, only when exposed.", then a dim "Not counted in the stats above."). It leaves out frame lore, COMP/CON's repeated `synergies` hints, equipped items' rules (their cards show them) and pilot gear (only non-`pilot_*` bonuses count on a mech). Unknown expressions/effects stay manual and are not evaluated as code.
  - **Talent grants and mount choices:** integrated talent equipment appears automatically; exclusive grants upgrade to the highest owned rank, optional special equipment is selectable only while granted. Improved Armament, Integrated Weapon and Mount Retrofitting alter mounts; Auto-Stabilizing Hardpoints and Overpower Caliber target choices are per mech. Choices live in `sheet.mechs[id].core_mounts`; per-instance profile/prototype choices live in `weapon_options` keyed `mount:place` or `integrated:item-id`. New fields are included in GM change review. Lost mounts/talent ranks, invalid targets and stale profiles are rule-checked without silently deleting saved gear. AI capacity includes The Lesson of Shaping. `mechResources()` displays AI/Limited capacity, structure repair cost, overcharge costs and permanent check accuracy separately from numeric stats.
  - **Scope explicitly confirmed:** permanent character-building effects and readable combat reminders only. No current HP, heat, overshield, status toggles, expended charges, turn tracking or active-core-power state.
- **Rules text** (2026-10-31): LANCER's rules text is small HTML. `src/rulesText.ts` parses it into an allowlist (paragraphs, bold, italic, underline, lists, line breaks; no attributes, other tags dropped) and `RulesText.vue` draws it with Vue, never `v-html`, turning top-level line breaks into spaced paragraphs (`paragraphs()`), because imported packs are untrusted. Styled by `.rules-text` in `style.css` (bold keywords in bold white). `plainText()` flattens it for one-line picker summaries. Don't strip formatting with regexes elsewhere.
- **No dice** (the developer, 2026-10-31): this homebrew involves no dice at all. **Damage** is a flat number: LANCER's dice expression converted by taking its mean rounded **up** (1d6 → 4; 2d6+1 → 8). It is the damage, not an average: never label or describe it as "average" (`damage.ts`; item cards show "kinetic 4"). Shared item cards/pickers and explicit damage phrases in rules text use this. Other dice left in game text (movement, rolls, Limited 1d6+2 and so on) stay as they are: the developer will give instructions for each or edit them in the content editor once it exists, so don't invent conversions. Variable/unsupported expressions remain visible; no guessed values.

Biomod modifiers are applied afterwards and can take effective totals below 2 or above 4. Existing saved allocations are not silently rewritten: out-of-range or overspent bases are flagged for correction (developer's request, 2026-10-29).

The rules are in `src/rules.ts` (tested in `src/rules.test.ts`). Keep that file current when rules change.

  - **Level** is gained narratively only: GMs and owners set it. It raises **HASE points (2 + level)** and **biomod capacity, the mod limit (6 + level)**. Nothing else.
  - **Manna buys everything else:** licence ranks **600** each, biomods (bionics) **500** each, talent ranks **300** each. **GMS gear is free to print**, and licensed gear (frames, weapons, systems) is free once the pilot holds that licence rank.
  - **Licence level** is just the number of licence ranks bought (no separate number).
  - **Core bonuses:** one free pick for every **3 licence ranks** bought. Each non-GMS bonus also requires **3 ranks in its manufacturer**, across any of its licences (6 for a second bonus from that manufacturer, etc.). GMS bonuses have no manufacturer requirement. The picker blocks ineligible choices; the shared rule check flags existing selections that lose eligibility, including in GM reviews. No bonus can be taken twice. Existing selections are never silently removed.
  - **Where it's stored:** `character_sheets.level` and `character_sheets.manna` (manna *received*, in total). Both are GM-only: a trigger refuses changes from anyone else, even a player whose pilot is pending (migration `20261029022434_level_and_manna.sql`, which also dropped the old hand-set `mod_points`). What's **spent** is worked out from the sheet (`mannaSpent()`), so the balance (received minus spent) can't be faked, lowering a rank refunds it, and the pickers block anything the balance can't cover.

Every record links there for GMs. They save on their own button only: approving or sending back never needs them (the developer's request, 2026-10-29).

  - Each bionic has a name, a description, the stat bonuses it gives, a **manna cost** and a **mod-point cost**. A bonus can only point at a stat that exists in the list. (Every biomod now costs 500 manna, so the table's own `manna_cost` is unused.)

  - Characters store bionic IDs, like any other item. Only owners can add or change bionics or stats. One that's in use can't be deleted.

- **Talents and core bonuses:** included.

Its toolbar offers bold, italic and underline; small, normal and large font sizes; and bullet lists and small headings. The toolbar is the field's header strip (`--raised`, one bordered box with the writing area under it, outlined lilac while anything inside has focus): three segmented groups, B / I / U, S / M / L and the Lucide list and heading symbols, parted by thin `--rule` lines, `--tap` sized, each with an `aria-label`, `title` and `aria-pressed` (pressed: lilac text on a faint tint). On phones it stays one row and scrolls sideways. Headings and lists are whole blocks, so with text selected part-way through a paragraph the heading and list buttons first split the paragraph at the selection's edges (`splitAroundSelection()` in `src/richText.ts`, one undo step, the space at each cut dropped, never inside a list item) and only the selected words change; with just a cursor they act on the whole block. **No text colours** (the developer, 2026-11-16): each colour has one meaning site-wide, so player-picked colours would read as links, warnings or notes.   - **No separate registration form.** `my pilot` shows an empty modular pilot page when you have no pilot, and every section (identity included) is filled in place. The first save creates the pending pilot.

## Pending approval workflow (decided: option 2)
- The approved character stays **untouched** while a change is pending.
- Proposed changes are stored **separately** (a pending-changes table) until a GM approves or rejects them.
- Players keep a usable sheet while they wait, and the GM can see exactly what changed.
- **One pending change per character at a time.** The player can **edit or withdraw** it until a GM reviews it. Once it's **submitted**, a database trigger locks it: players can only take it back to a draft (`submitted_at` back to null, "Edit change") or withdraw it, and can never change its status, review fields or `based_on`.
- **Watch out:** if a GM edits a character directly while the player has a pending change, approving that change could overwrite the GM's edit, because the change was based on the older sheet. The approval function should catch this, for example by checking that the character hasn't changed since the pending change was made.
- GMs approve or reject a **whole** change, with no partial approval. Rejecting needs a **reason**, and the player then submits a new change. `review_reason` holds the GM's note for either outcome (required when rejecting, optional when approving), and the player sees it.
- Approving means (1) applying the change to the character and (2) marking the pending change as approved. Both must happen in **one database function** (all-or-nothing), so a failed request can't leave half-applied data: `approve_change(change_id, expected_submitted_at, note)` (refuses if the player resubmitted since the GM opened it) and `reject_change(change_id, reason)` for changes, and `approve_pilot(target_character_id, expected_updated_at, note)` for new pilots (migration `20261116225551_approval_hardening.sql`, which also holds the triggers above).
- **History** is wanted, kept simple. Suggested: don't delete reviewed changes. Keep each one with its status (approved or rejected), who reviewed it, when, and the reason. Those rows are the history.
- **Built** (2026-10-29):
  - **Saving is trustworthy** (2026-11-17; `useMyPilot` in `src/myPilot.ts`, `checkWrite()` in `src/lib/supabaseClient.ts`, tested in `src/myPilot.test.ts` and `src/lib/supabaseClient.test.ts`): saves run one at a time and each sends the **whole** card, sheet or draft as it is on screen when it runs (never a copy taken when it was queued), so two quick edits can't undo each other and a later save carries an earlier failed one. A failed save never reloads: the edit stays on screen, the status reads red "Not saved: …" with a small `Retry` that re-sends what's still unsaved (the error stays until a save succeeds), and `Submit for review` / `Resubmit` refuse while an edit is unsaved. Every `.update()`, `.upsert()` and `.delete()` ends in `.select()` and goes through `checkWrite()`, because RLS turns a refused write into "0 rows, no error": it reports "Not saved: you don't have permission to change this, or it no longer exists." **Never trust a write that doesn't check its rows.** The same shape applies to the pilot sheet, mech pages, GM edit mode (`GmEditBar` has the Retry too), the lore editor (every save sends the whole entry) and the GM pilots roster (typed numbers stay in the field).
  - **Newer saves are never overwritten (optimistic locking):** the card (`characters`), the sheet (`character_sheets`), the player's draft (`pending_changes`) and lore entries are updated with `.eq('updated_at', <the raw string this page last loaded or saved>)` and the page stores the new `updated_at` each save returns (never re-serialised through `Date`). When the write touches no row because the row moved on (checked with a second read, so a permission failure isn't mistaken for it), saves stop for that page and `ConflictNotice.vue` shows "Not saved: this changed somewhere else" with a `Reload` button (a full page reload). The sheet's `updated_at` only moves when `sheet` itself changes (the trigger), so a GM setting level, manna or a note doesn't cause conflicts. The first sheet save (no row yet) is an upsert, unguarded. `pending_changes.updated_at` (migration `20261116235409_pending_changes_updated_at.sql`, moddatetime like the other tables, pgTAP-tested in `approval.test.sql`) is new: **the hosted database needs this migration before the site is pushed**, or draft saves fail.
  - **Profile and session** (`src/auth.ts`, `App.vue`): if the profile can't be loaded (network, a paused free Supabase project) the page area shows "Couldn't load your profile" with the paused-project hint and `Retry` (`profileError`, `loadProfile()`), instead of sitting on "Loading…". When the session ends while the site is open (signed out in another tab, expired), `App.vue` sends you to `/login`.
  - **Drafts:** a change starts as a draft (`pending_changes.submitted_at` is null, migration `20261029024308_pending_change_drafts.sql`). It lives in the database, so it works across devices. Only submitted changes reach the GM queue, and `approve_change` refuses a draft.
  - **Player** (`src/myPilot.ts`, top strip of `PilotManageView.vue`): an approved pilot shows `[ propose changes ]`, which copies the pilot into a new draft. While a draft is open, the page and the mech pages show it and every save goes into it instead of the pilot, so they needed no changes of their own. `[ submit for review ]` puts it in the queue. A rejected change shows its reason (below); an approved one shows the GM's note, if any, as a "Note from the GM" notice with a `Clear note` that hides it on this device only (localStorage per change id). Once submitted, the sheet is read-only, with `[ edit change ]` (back to a draft, out of the queue) and `[ withdraw ]` (deletes it). A rejected change shows its reason above `[ propose changes ]`. Buying with manna in a draft spends from the same balance.
  - **"Changed since" check:** `based_on` is set by the database when the draft is created (a trigger, so players can't fake it) to when the pilot last changed (`private.pilot_last_changed()`: the later of the card's and the sheet's `updated_at`); it never changes afterwards. The sheet's `updated_at` now only moves when the sheet itself changes, so a GM setting level, manna or a note doesn't block approval. A real edit to the pilot after the draft was made does: the review page warns and disables approve, and `approve_change` refuses it too.

## Security rules (critical)
- **Players must NOT be able to update the characters table directly.** They can only add pending changes for their own characters. Otherwise anyone could skip GM approval using browser developer tools.
- Only GMs (or the approval function) can change approved characters.
- **Only owners can delete characters** (it cascades to their sheet, changes and reputation). Players can still withdraw their own pending pilot. GMs can't delete any.
- **Players must NOT be able to change their own role** in the profiles table, or anyone could make themselves a GM.
- **Only owners can add, change or remove LCP content.**
- **Reputation is GM-only.** Only GMs and owners can read reputation or change its levels, and only owners can change the list of organisations. The character's own player can't see it either.
- Players can see and edit their own things, and can see only the public parts of other characters. GMs and owners can see everything.
- **RLS works on whole rows, not fields.** If a player can read a character's row, they can read every field in it with developer tools, even the ones the page doesn't show. The private parts must be secret, so the public parts have to be stored apart from them (for example, in their own table).
- Test the rules by trying to break them while logged in as a player.
- Supabase has two keys. The **public** one ("anon" or "publishable") is safe in the browser. The **secret** one ("service_role" or "secret") bypasses every rule. It must never go in the frontend or be committed to git.

## Gotchas
- **Vite environment variables:** only variables starting with `VITE_` reach the browser, and those are public. Only the public Supabase key goes in a `VITE_` variable. Keep `.env` files out of git.
- **Hosting + Vue Router:** with clean URLs like `/characters/42`, refreshing the page can show a 404 unless the host sends every unknown path to `index.html`. That's `not_found_handling` in `wrangler.jsonc`.
- **Supabase free tier pauses projects after 1 week of inactivity.** No data is lost, and you restore it from the dashboard. Expect this during campaign breaks. Limits: 2 active free projects and a 500 MB database, which is plenty for this.
  - **Keep-alive** (`.github/workflows/keep-alive.yml`): every 3 days (and by hand from the Actions tab) a GitHub Action reads one row of `content_items` through the REST API with the publishable key, so the project never idles for a week. A permission-denied answer counts (it still comes from a running Postgres); a 5xx or no answer fails the job. It needs two repository **variables** (Settings → Secrets and variables → Actions → Variables): `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. GitHub switches scheduled workflows off after 60 days without repo activity.
- **Supabase returns at most 1,000 rows per request** (`max_rows` in `supabase/config.toml`), silently cutting longer lists. Any list that can grow (game content, packs) is read with `fetchAll()` in `src/lib/supabaseClient.ts`: it pages with `.range()` (the query must `.order()` by something unique) and returns all the rows or an error, never a partial list (tested in `supabaseClient.test.ts`).
- **Game content is read once per browser session** (`src/catalogue.ts`): `loadKind(kind)` gives every `content_items` row of one kind through `fetchAll()`, and `cached(key, load)` keeps the promise, so `useGameData()`, `useMechData()`, `useManufacturers()` and the tag names share one fetch each across pages (bionics and pilot stats too). A failed read is not kept, so the next page that asks retries. `invalidateCatalogues()` (`gameData.ts`) clears the cache after an owner imports or updates a pack (`ContentView.vue`), so new content shows without a reload. A failure sets `catalogueError`; the pilot sheet, mech page, archives and GM change page each show it once as `<CatalogueNotice />` ("Game content didn't load: …", a `.notice.warn`), so an empty picker is never silent. New catalogue reads go through `cached()`/`loadKind()`, not straight to Supabase.
- **Pages load on demand** (`src/router.ts`): every route is `component: () => import('./views/X.vue')` except the login view, which stays eager for first paint. Keep new routes lazy.
- **Don't charge players or add ads.**
- **New tables may not be reachable from the app automatically.** Depending on the project's Data API settings, each new table needs an explicit `grant` to the `authenticated` role, on top of RLS. Every migration that creates a table should enable RLS and grant only what's needed.

## Homebrew and .LCP import
- **Decided:** owners add custom content by writing it in `cc-lcp-editor` and importing the `.lcp`. There's no item editor in the site. Homebrew is mostly **new content** (frames, weapons, talents and so on). The rule changes are custom pilot stats, bionics, and no grit or save target (see "Character sheet contents"). Otherwise mech maths is standard LANCER. Bionics are not LCP content (see "Character sheet contents"). Because content is added while the site is running, it has to be **stored in Supabase**, not only in the app's code.
- An `.lcp` file (Lancer Content Package) is just a renamed `.zip` of JSON files, in the same format as `lancer-data`. It must contain an `lcp_manifest.json` at the top level, and subfolders are ignored.
- Things to plan for:
  - Characters refer to items by **ID**. If an item goes missing, every character using it breaks. So imported data must be **kept**, and deleting items that characters use must be blocked.
  - Unzipping can happen in the browser, so this still doesn't need a backend.
- Suggested, not decided: import the official packs through the same LCP import as homebrew. One feature then covers official content, homebrew and future expansions.
