# LANCER Campaign Site

## What this is
A website for one big LANCER (tabletop RPG) campaign and roleplay, run on a Discord server with a few GMs and many players. It tracks characters. It is not a VTT (no game board).
- **Players** create and manage their LANCER character.
- Player edits don't go live straight away. They become **pending changes**.
- **GMs** see characters and pending changes, can edit characters, and approve or reject changes. GMs can also have characters of their own.
- The campaign uses a **homebrew** version of LANCER: official content plus custom content the GMs add.
- **Scope (decided by the developer, 2026-10-29): character management only.** Pilots and their content: a clean submission → approval and change → approval pipeline, easy manna spending for players, easy levelling for GMs, and the game content pilots need (LCP import and editors, owners only). Visually clear and simple over stylised. **Reputation came back into scope on 2026-11-19** as a GM-only tracker (below). (Browsing game content came back into scope on 2026-10-31 as the **archives** tab, below. **Lore** came back on 2026-11-16: GM-written entries, built as option A, a list + reading pane like the archives, chosen from the mockups in `docs/redesign/lore/`. Drafts are GM-only; published entries are visible to every logged-in user.) Reputation is behind the scenes: players never see or read it.

## Tech stack (decided)

- **Database, logins and security rules:** Supabase (free tier).
- **Hosting:** Cloudflare (decided by the developer, 2026-11-16). **Cloudflare builds and deploys from the GitHub repo on every push**, so pushing is going live: ask before pushing.
  - **Set up as a Cloudflare Worker serving static files** (Workers & Pages → Create → Import a repository). `wrangler.jsonc` serves `dist/` and sends unknown paths to `index.html` (`not_found_handling: "single-page-application"`); `.node-version` pins Node 24 for the build (Vite 8 needs 20.19+).
  - **Build settings in the dashboard:** build command `npm run build`, deploy command `npx wrangler deploy` (the default).
  - **Build variables:** `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` must be set under the Worker's Settings → Build → Variables and secrets (build-time, not runtime: Vite bakes them into the files). Never the secret key.
  - **Discord login:** the login sends people back to the page's own address (`redirectTo: window.location.origin`), so add the Cloudflare address (`https://lancer-site.<account>.workers.dev`, and any custom domain) to Supabase → Authentication → URL Configuration (Site URL and Redirect URLs). Otherwise login returns to the old address or fails.
  - After the first deploy: refresh a deep link like `/registry` (should not 404) and log in once.
  - **The site's domain is `hor-os.party`** (the developer, 2026-11-17), attached to the Worker as a custom domain (Settings → Domains & Routes). Supabase's Site URL is `https://hor-os.party`, and its Redirect URLs list `https://hor-os.party` and `https://hor-os.party/**` (plus localhost for local testing).
- **No custom backend API.** The Vue app talks straight to Supabase using `supabase-js`. Keep it simple.

## How the pieces fit
- The browser (Vue app hosted on Cloudflare) talks to Supabase. There's nothing in between.
- Security is enforced **in the database** with Row Level Security (RLS), never only in the frontend code, because anyone can tamper with code running in their browser.
- The one exception to "no backend": small **database functions inside Supabase** (written in SQL) for actions that must happen all-or-nothing, such as approving a change. Vue calls them with `supabase.rpc()`. They're not a server, and there should only be one or two.

## Users and roles (decided)
- **No campaigns table.** Everything belongs to the one campaign.
- Anyone can sign up, using **"Log in with Discord"** through Supabase Auth. New accounts need no GM approval (decided by the developer, 2026-11-17); email signup should be off in the hosted dashboard so Discord is the only way in.
- A **profiles** table holds one row per user: Discord name and role. New users are players. The name is the first non-blank of Discord's display name, username and name, else "Unknown pilot" (`private.discord_name()`, migration `20261117155935_profile_names.sql`, tested in `supabase/tests/profiles.test.sql`): Discord sends an empty display name for accounts without one. GMs and owners are set by hand in the Supabase dashboard.
- **Three roles:**
  - **Player:** manages their own character through pending changes.
  - **GM:** everything except managing LCP content. Edits any character, approves or rejects changes, and can have their own characters, which they edit directly without approval. GMs can't delete characters.
  - **Owner:** everything a GM can do, plus managing LCP content (importing, updating and removing packs) and deleting any character.
- Players have **one living character** at a time. When it dies, they can make a new one. GMs and owners can have several. Enforce this in the database, not just the page: the insert policy checks it, and a trigger takes a per-player lock so two requests at once can't both pass.

## Characters (decided unless marked)
- Three tabs: **Pending**, **Approved** and **Dead**.
- **New character:** the player fills in a template and submits it, and it shows as pending. When a GM approves it, it moves to Approved. **Submission is up to the player** (the developer, 2026-11-19): a new pilot is a **draft** (`characters.submitted_at` null) until they press `Submit pilot`, and only submitted pilots reach the GM queue and the Pending tab. Starting to write is never submitting.
  - Suggested in `docs/database-sketch.md`: a new character is a normal character with status pending, which the player edits directly until a GM approves it. Pending changes are only for approved characters.
- **Every logged-in user can see every character (pending, approved and dead), but only the public parts:**
  - Pilot: name, callsign, age, gender, sexuality, height, weight, eye colour, hair colour, appearance description and image, personality, and traits (narrative: what the character is good at).
  - Mech: name, appearance, image, manufacturer ID.
  - Everything else (stats, loadouts and so on) is for the character's player and GMs only. It must be **really secret** (enforced by the database, not just hidden on the page), but it isn't critical, so keep the solution simple.
- **Death:** GMs, owners, or the character's own player can mark a character dead. Everyone can see the Dead tab. Dead characters can't come back (a database trigger refuses any change away from dead, even from GMs and owners).
  - A player marking their own character dead needs **no GM approval**, just a "are you sure?" confirmation on the page.
  - Players can't update the characters table directly, so this needs a small database function. It checks that the caller owns the character (or is a GM or owner), and refuses to change a dead character back. A flash clone counts as a new character, which the player submits for approval as usual.
- **Images (built 2026-11-17):** pilot portraits and mech images, uploaded by whoever can edit the page (the player on their own pending pilot or draft change, GMs in edit mode). Pasted links aren't supported (Discord attachment links expire). The browser shrinks each picture first (`src/images.ts`: long side at most 1024px, WebP at 0.85 quality, JPEG on Safari; inputs over 20 MB refused; animated GIFs become still) and uploads it to the `character-images` Storage bucket as `<uploader's user id>/<random id>.webp` (`.jpg`). The bucket is **public to read** (pending pilots' public cards are visible to every logged-in user anyway), 1 MB, WebP and JPEG only; uploads are immutable (no update policy): users insert into their own folder only and delete from it, GMs and owners delete anywhere (migration `20261117180750_image_uploads.sql`, tested in `supabase/tests/images.test.sql`). **The card stores the path, never a URL** (`characters.pilot_image`, and `image` in each `characters.mechs` entry); `imageUrl(path)` builds the public link with no network and returns null for anything not matching `IMAGE_PATH` (a database check constraint enforces the same shape on `pilot_image`), so a tampered value can't point the page at an outside site.
- **Frame art (2026-11-19):** official frames have artwork bundled from Massif's frame images (the files COMP/CON shows, which lancer-data's `image_url` points to on Massif's CDN, not in the COMP/CON repo; GPL-3.0, credited in the README): `src/assets/frames/<frame id>.webp`, 53 files for the frames in core and the eight expansion packs the site supports (long side at most 640px, quality 82, about 4.2 MB in all; frames whose pack art is a `nodata` placeholder, Sagarmatha and Chomolungma, have none). `frameArt(frame, frames)` in `src/images.ts` says which picture a frame shows: an owner's upload (the frame's own `image` field, an `IMAGE_PATH` path in the `character-images` bucket, never a URL, separate from the pack's ignored `image_url`), else the bundled art by frame id, else, for an alternate, its original's (tested in `src/images.test.ts`). Bundled art is `import.meta.glob(..., { query: '?url' })` without `eager`, so each image is its own lazy chunk and downloads only when shown; `FrameArt.vue` resolves it (`frameArtUrl()`) and draws the `<img>` (classes go on it; its slot shows while there's none). `images.ts` imports `auth` only inside `uploadImage()`, so its pure parts load in tests without a browser. Owners upload in the frame form (below). **A mech with no image of its own shows its frame's** in the hangar card, the mech page's Image panel (`Portrait.vue`'s `fallback` prop, captioned "Frame image. Upload your own to replace it.") and, as the overview's picture, only for viewers of the private sheet (`canSeePrivate`; the frame is private, so other players see just an uploaded image or the empty frame). The mech plate has no thumbnail, so nothing to do there. An upload always wins.
- **COMP/CON import:** dropped (the developer, 2026-11-19). Not planned.

## Character sheet contents
- **The full field list** (from the developer, 2026-10-28):
  - Profile: name, callsign, age, gender, eye colour, height, weight, sexuality, hair colour, personality, appearance description, appearance image, and traits.
  - Pilot stats: physicality, dexterity, perception, acuity, tech-fluency.
  - Mech skills: hull, systems, agility, engineering.
  - Also: licences, weapons and equipment (pilot gear only), bionics/bodymods, backstory.
  - Mechs (added in a follow-up answer): several per pilot, each with a name, appearance description, image, weapons on the frame's mounts, a manufacturer ID, and systems with system points.
  - Confirmed as staying, though not on the list: talents, core bonuses, licence level, pilot HP, manna and mod points.
- **It's a general character manager, not a combat tracker.** It doesn't track current HP, structure, stress or heat.
- **Pilot combat stats (updated 2026-10-29):** HP 6, armour 0, speed 4 and **e-defence 10** before permanent equipment/talent/core bonuses. **Pilots have no evasion** (latest developer correction); ignore `pilot_evasion` bonuses and omit them from equipment cards. Keep pilot e-defence and normal mech evasion. No grit, save target or sensors. Stats are private, calculated and have source disclosures.
- **Mech stats:** structure, stress, HP, heat cap, armour, evasion, speed, e-defence, tech attack, repair cap, system points and size. Speed gains floor(Agility / 2); e-defence and tech attack each gain Systems; evasion uses the normal frame + Agility formula (no pending rework). Grit, save target and sensors remain excluded. Values are calculated, never stored.
  - **Permanent build effects (2026-10-29):** `mechEffects()` collects frame traits, passive core bonuses, equipped weapons/systems (including integrated items), pilot gear, owned core bonuses and purchased talent ranks. `bonuses.ts` handles safe arithmetic (known licence/HASE/size variables, no JavaScript evaluation), replacements and highest overrides. `mechStats()` and rule checks share these effects. Armour normally caps at 4, with `armor_max` modifiers; Fomorian Frame increments size up to 3. `equipment.ts` applies matching weapon range/damage bonuses, Hunter II Thrown, selected profiles, Limited bonuses (including floor(Engineering/2)) and drone/deployable modifiers. Damage dice are converted to the flat homebrew number (rounded up) once, after modifiers. `coreRules.ts` explicitly supplements permanent core check modifiers omitted from the pinned dataset's structured bonuses; `mechEffects()` adds a supplement entry only when the frame's (or core bonus's) own structured bonuses don't already carry it (newer data gives Exposed Reactor its bonus), so it never counts twice. Conditional abilities and active core powers are readable reminders, never treated as permanently active. The mech page's "other effects and conditions" list (2026-10-31) holds frame traits and their actions, the core passive and active power, core bonuses, talent ranks and bonuses not counted in the stats, in plain wording. An action named like its trait or core power (COMP/CON's data often has both) is listed once, under the parent, with the action's chip and text (trigger and effect); the same rule applies in the full-information dialog (`absorb()` in `info.ts`), where it also takes the action's numbers. Each reminder (`Reminder` in `mechData.ts`) carries its `kind` (frame, trait, core, core-power, core-bonus, talent, item, missing), its own `name`, where it's `from` ("Brawler I"), any `activation`, and `uncounted` for bonuses the stats leave out ("+10 hp, only when exposed.", then a dim "Not counted in the stats."). It leaves out frame lore, COMP/CON's repeated `synergies` hints, equipped items' rules (their cards show them) and pilot gear (only non-`pilot_*` bonuses count on a mech). Unknown expressions/effects stay manual and are not evaluated as code.
  - **Talent grants and mount choices:** integrated talent equipment appears automatically; exclusive grants upgrade to the highest owned rank, optional special equipment is selectable only while granted. Improved Armament, Integrated Weapon and Mount Retrofitting alter mounts; Auto-Stabilizing Hardpoints and Overpower Caliber target choices are per mech. Choices live in `sheet.mechs[id].core_mounts`; per-instance profile/prototype choices live in `weapon_options` keyed `mount:place` or `integrated:item-id`. New fields are included in GM change review. Lost mounts/talent ranks, invalid targets and stale profiles are rule-checked without silently deleting saved gear. AI capacity includes The Lesson of Shaping. `mechResources()` displays AI/Limited capacity, structure repair cost, overcharge costs and permanent check accuracy separately from numeric stats.
  - **Scope explicitly confirmed:** permanent character-building effects and readable combat reminders only. No current HP, heat, overshield, status toggles, expended charges, turn tracking or active-core-power state.
- **Rules text** (2026-10-31): LANCER's rules text is small HTML. `src/rulesText.ts` parses it into an allowlist (paragraphs, bold, italic, underline, lists, line breaks; no attributes, other tags dropped) and `RulesText.vue` draws it with Vue, never `v-html`, turning top-level line breaks into spaced paragraphs (`paragraphs()`), because imported packs are untrusted. Styled by `.rules-text` in `style.css` (bold keywords in bold white). `plainText()` flattens it for one-line picker summaries. Don't strip formatting with regexes elsewhere.
- **No dice** (the developer, 2026-10-31): this homebrew involves no dice at all. **Damage** is a flat number: LANCER's dice expression converted by taking its mean rounded **up** (1d6 → 4; 2d6+1 → 8). It is the damage, not an average: never label or describe it as "average" (`damage.ts`; item cards show "kinetic 4"). Shared item cards/pickers and explicit damage phrases in rules text use this. Overcharge heat (1 → 1d3 → 1d6 → 1d6+4, or a frame's own list) is converted the same way, so the default reads 1 → 2 → 4 → 8 (`mechResources()`). Other dice left in game text (movement, rolls, Limited 1d6+2 and so on) stay as they are: the developer will give instructions for each or edit them in the content editor once it exists, so don't invent conversions. Variable/unsupported expressions remain visible; no guessed values.

- **Pilot stats are custom.** LANCER's skill triggers ("narrative triggers") are replaced by five homebrew stats: **physicality, dexterity, perception, acuity and tech-fluency**.
  - Each **base stat starts at 2**, with **4 shared points** to allocate. Base stats stay within **2–4** and don't gain points with level. Biomod modifiers are applied afterwards and can take effective totals below 2 or above 4. Existing saved allocations are not silently rewritten: out-of-range or overspent bases are flagged for correction (developer's request, 2026-10-29).
  - They're **private**: players see only their own.
- **Mech skills** (Hull, Agility, Systems, Engineering) gain allocation points with level. Pilot HP is 6 plus equipped gear bonuses; no grit or level bonus.
- **LANCER rules compliance** (the developer's request, 2026-10-29): `docs/lancer-rules.md` records every character rule the site follows (licences, HASE points, mounts, Superheavy, Unique, AI, system points and so on), whether it's enforced, rule-checked, left to GMs or waiting on unbuilt features. The rules are in `src/rules.ts` (tested in `src/rules.test.ts`); `useCatalogue()` there gives the loaded game content in the shape the rule checks read, for the pilot sheet, mech page and change review. Keep that file current when rules change.
  - **HASE starts at 0** with 2 + level points (changed from the earlier "start at 1" for compliance; personal stats start at 2, with four shared extra points and a base maximum of 4). A one-line change in `sheetStats()` if the developer wants 1 back.
- **Homebrew levelling and gear** (decided by the developer, 2026-10-29; `docs/lancer-rules.md`, prices in `PRICES` in `src/rules.ts`):
  - **Level** is gained narratively only: GMs and owners set it. It raises **HASE points (2 + level)** and **biomod capacity, the mod limit (6 + level)**. Nothing else.
  - **Manna buys everything else:** licence ranks **600** each, biomods (bionics) at **their own price** (`bionics.manna_cost`, set in the content editor; existing ones were set to 500 on 2026-11-18 so no balance changed), talent ranks **300** each, and **mechs: the first is free, each one after it 500** (`PRICES.extraMech`; the developer, 2026-11-19; `mannaSpent(sheet, bionicPrices, mechs)` takes the mech count from the card's `mechs` list, so scrapping a mech refunds it and pilots who already had several mechs lost 500 per extra one; the hangar's `New mech` shows `New mech · 500` from the second and uses the blocked pattern with "Not enough manna"; GM change review counts an added mech in the cost of change like any purchase). **New pilots start with 1500 manna** (`STARTING_MANNA`, the column default from migration `20261119150000_starting_manna.sql`; existing pilots keep what they have). **GMS gear is free to print**, and licensed gear (frames, weapons, systems) is free once the pilot holds that licence rank.
  - **Licence level** is just the number of licence ranks bought (no separate number).
  - **Alternate frames** (2026-11-18; packs mark one with `variant` = the original's name and usually `license_id` = the original's id, e.g. Worldkiller Genghis, Empakaai): **one licence per original frame.** `alternateOf()` / `licensedFrames()` / `licenceFrames()` / `chosenFrame()` in `mechData.ts`; the licence picker, archives' Licences and manufacturer counts list originals only, and the alternate appears in the original's ladder at its own rank. The pilot picks which frame the licence gives (`sheet.frame_choices`, licence id → frame id, free; radios on the licence card once the rank is held, a "Chosen frame" line when read-only); the frame picker blocks the other (`frameBlockedBy()` in `rules.ts`, "Licence gives X"); `mechProblems()` and `pilotProblems()` flag a mech on the wrong frame and a licence still held under an alternate's id (never auto-rewritten; a GM moves its ranks). Change review shows a changed choice as an Updated line in licences. The frame form has an "Alternate of" select. Tested in `src/alternateFrames.test.ts`.
  - **Core bonuses:** one free pick for every **3 licence ranks** bought. Each non-GMS bonus also requires **3 ranks in its manufacturer**, across any of its licences (6 for a second bonus from that manufacturer, etc.). GMS bonuses have no manufacturer requirement. The picker blocks ineligible choices; the shared rule check flags existing selections that lose eligibility, including in GM reviews. No bonus can be taken twice. Existing selections are never silently removed.
  - **Where it's stored:** `character_sheets.level` and `character_sheets.manna` (manna *received*, in total). Both are GM-only: a trigger refuses changes from anyone else, even a player whose pilot is pending (migration `20261029022434_level_and_manna.sql`, which also dropped the old hand-set `mod_points`). What's **spent** is worked out from the sheet (`mannaSpent()`), so the balance (received minus spent) can't be faked, lowering a rank refunds it, and the pickers block anything the balance can't cover.
  - **GMs set them** in the **gm: pilots** roster (editable level, experience and total manna received) or on any pilot's review page ("GM controls", `Save rewards`). Every record links there for GMs. They save on their own button only: approving or sending back never needs them (the developer's request, 2026-10-29).
  - **Experience and the reward log** (2026-11-19, migration `20261119160000_rewards_and_experience.sql`, tested in `supabase/tests/rewards.test.sql`; **the hosted database needs it before the site is pushed**, or the roster and GM controls fail to load): a **GM-only** number per pilot, 0–1000, in `pilot_progress` (`character_id` primary key, `experience`, `updated_at`; no row means 0). At 1000 the pilot is "ready to level", but nothing is automatic: a GM raises the level. Every change to a pilot's **level, manna received or experience** is recorded in `pilot_reward_log` (`character_id`, `field`, `old_value`, `new_value`, `reason`, `changed_by`, `changed_at`), by **triggers** (`private.log_sheet_rewards()` on `character_sheets`, `private.log_experience()` on `pilot_progress`, both `security definer`), so a change made anywhere, the dashboard included, is logged (with no reason, and `changed_by` null when there is no logged-in user). **Both tables are GM-only** (RLS: GMs and owners read; nobody has a write grant; players and visitors get nothing, even for their own pilot), kept apart from `character_sheets` because players can read their own sheet. Writes go through two `security definer` functions that check `is_gm()` themselves: `award(target_character_id, new_level, new_manna, new_experience, reason)` (nulls leave a field unchanged; whole numbers, 0 or more, experience at most 1000; sets the reason as a transaction-local setting `app.reward_reason` that the triggers read, all in one go) and `level_up(target_character_id, reason)` (refused below 1000 experience; level + 1, experience − 1000, reason defaults to "Level up"). The roster and GM controls call them (`src/rewards.ts`: `award()`, `levelUp()`, `rewardsProblem()`, `describeReward()`, tested in `src/rewards.test.ts`); nothing on the site writes level or manna to `character_sheets` any more. Players see nothing new.
- **Bionics / enhancements raise pilot stats.** Decided: they're the **site's own content**, not LCP content. They're stored in Supabase next to the list of custom pilot stats.
  - Each bionic has a name, a description, the stat bonuses it gives, a **manna cost** and a **mod-point cost**. A bonus can only point at a stat that exists in the list. Since 2026-11-18 (migration `20261118120000_biomod_slot_effect_price.sql`, **the hosted database needs it before the site is pushed**): `manna_cost` is the biomod's real price (`mannaSpent(sheet, bionicPrices)`, `bionicPrices` from `useGameData()`; an unknown id costs 0; changing a price moves the balance of pilots who have it), plus a `slot` (where on the body: free text with suggestions, `BIONIC_SLOTS`; empty is a warning) and an `effect` (rules-text HTML). Since 2026-11-19 (migration `20261119090000_biomod_manufacturer.sql`, **the hosted database needs it too**) a biomod has a **manufacturer**: `bionics.source`, the id of one of the packs' manufacturers (null = none, listed under "Other"; `save_bionic` takes it as a last argument, `new_source`). A HORUS or NHC biomod is **GM-only** (the biomod picker blocks it for players, "GM only"); an Exotic one (source `EXOTIC`) is **GM edit only** (see "GM-only content" under the frame, below); biomods have no tags. Owners create and edit them in the content editor (`BionicForm.vue`: name, slot, manufacturer (the same option list as the item forms; empty is a warning), price, mod points, stat bonuses, description, effect). The editor tab and every visible label say "biomods". Cards and the information show the slot and price in the facts line, the effect as rules, and the description as flavour (dim, italic, like lore).
  - **Mod points:** installed bionics can't cost more than the pilot's mod limit, which is 6 + level (homebrew, above). The sheet shows points used against the limit.
  - Installing a bionic is a normal pending change: add the bionic and pay the manna. Once installed, a bionic can only be swapped for a similar one. That rule isn't coded; GMs judge it when approving.
  - Bionics are **private**, like stats.
  - Characters store bionic IDs, like any other item. Only owners can add or change bionics, and stats (stats only in the Supabase dashboard: the content editor no longer edits them). One that's in use can't be deleted.
  - To start, owners can add them in the Supabase dashboard's table editor. Anyone with dashboard access can change *everything*, so only trusted people get it. An owner-only form in the site can come later.
  - Why not LCP: `cc-lcp-editor` has no bonus that targets a specific stat, reusing an existing bonus ID would clash with official items, and a custom ID would have to be typed into the JSON by hand.
- **Mechs:** a pilot can have **several**. Each mech has:
  - a frame
  - a name, appearance description and image (all public)
  - a **manufacturer ID** the player makes up, in the format `XXXX-XXXX-XXXX` (assumed: letters and digits). It's **public**, and should be unique. Uniqueness isn't critical, so the site checks for duplicates and warns, rather than the database enforcing it.
  - weapons on the **mounts its frame provides** (for example, Blackbeard has Flex, Main and Heavy)
  - systems, shown as system points used against the total. System points are calculated, not stored.
- **Licence levels:** the pilot's licence ranks in each frame, bought with manna; licence level is their total (homebrew, above).
- **Talents and core bonuses:** included.
- **Pilot equipment:** only LANCER pilot gear (armour, weapons, kit) from the game data. No free-text items.
  - **Slots** (decided by the developer, 2026-10-29): **1 armour, 2 weapons and 3 gear**, laid out like COMP/CON's loadout.
- **The pilot page is modular.** Each category (mechs, equipment, talents, licences, core bonuses, mech gear and so on) is a section with a `[ + ]` box to add an item.
  - For game items, `[ + ]` opens a searchable picker of pre-made items from the imported LCPs. This is how most players add things, and the sheet stores only the item's ID.
  - Mechs are added with a small form (name, manufacturer ID, appearance, image).
  - Paragraph fields (appearance, personality, traits, backstory) use a rich-text editor (TipTap, which stores formatting as structured data rather than raw HTML, so players can't inject code into each other's pages; `RichTextEditor.vue`, extensions from `editorExtensions()` in `src/richText.ts`; the TipTap-free cleaning and reading side, `sanitiseDoc()` and `docText()`, is `src/richTextSafe.ts`, so read-only pages (lore, change review) don't download the editor). Its toolbar offers bold, italic and underline; small, normal and large font sizes; and bullet lists and small headings. The toolbar is the field's header strip (`--raised`, one bordered box with the writing area under it, outlined lilac while anything inside has focus): three segmented groups, B / I / U, S / M / L and the Lucide list and heading symbols, parted by thin `--rule` lines, `--tap` sized, each with an `aria-label`, `title` and `aria-pressed` (pressed: lilac text on a faint tint). ## Pending approval workflow (decided: option 2)
- The approved character stays **untouched** while a change is pending.
- Proposed changes are stored **separately** (a pending-changes table) until a GM approves or rejects them.
- Players keep a usable sheet while they wait, and the GM can see exactly what changed.
- **One pending change per character at a time.** The player can **edit or withdraw** it until a GM reviews it. Once it's **submitted**, a database trigger locks it: players can only take it back to a draft (`submitted_at` back to null, "Edit change") or withdraw it, and can never change its status, review fields or `based_on`.
- **Watch out:** if a GM edits a character directly while the player has a pending change, approving that change could overwrite the GM's edit, because the change was based on the older sheet. The approval function should catch this, for example by checking that the character hasn't changed since the pending change was made.
- GMs approve or **send back** a **whole** change, with no partial approval. Sending back needs a **note**. `review_reason` holds the GM's note for either outcome (required when sending back, optional when approving), and the player sees it. **Sending back never loses the player's work** (2026-11-19, after a player lost hours of writing): `reject_change(change_id, reason)` marks the change `rejected` (the history row; the enum value stays `rejected`) and, in the same transaction, inserts a **new draft** for the same character with the same card and sheet, `submitted_by`, `based_on` stamped with the pilot's last change at send-back (`private.pilot_last_changed()`: the GM has just reviewed the change against the pilot as it is, so a GM edit made before sending back can't leave the draft stale for ever, while any edit after it still blocks approval) and the note in `review_reason`. A draft with a `review_reason` is a **sent-back** draft. Submitting it clears the note from the draft (a trigger; the history row keeps it), like submitting a sent-back pilot. Players still can't set `review_reason` or `based_on`. Migration `20261119130000_send_back_changes.sql` also backfills a draft for every approved pilot whose latest change was rejected and has no open change.
- Approving means (1) applying the change to the character and (2) marking the pending change as approved. Both must happen in **one database function** (all-or-nothing), so a failed request can't leave half-applied data: `approve_change(change_id, expected_submitted_at, note)` (refuses if the player resubmitted since the GM opened it) and `reject_change(change_id, reason)` for changes, and `approve_pilot(target_character_id, expected_updated_at, note)` for new pilots (migration `20261116225551_approval_hardening.sql`, which also holds the triggers above). **New pilots use the same draft → submit flow as changes** (migration `20261119120000_pilot_submission.sql`, tested in `supabase/tests/approval.test.sql`; `submitPilot()` / `reopenPilot()` in `src/myPilot.ts`): the player may only set `characters.submitted_at` null → now() (the database stamps the time, and clears the GM's sent-back note) or back to null, only while pending; while it's set the player can't change the pilot's card or sheet (GMs and owners can, so GM edit mode still works). `approve_pilot` refuses an unsubmitted pilot, and a GM sending back (`send_back_pilot`) clears it. A sent-back pilot is a draft with the GM's note.
- **History** is wanted, kept simple. Suggested: don't delete reviewed changes. Keep each one with its status (approved or rejected), who reviewed it, when, and the reason. Those rows are the history.
- **Built** (2026-10-29):
  - **Saving is trustworthy** (2026-11-17; `useMyPilot` in `src/myPilot.ts`, `checkWrite()` in `src/lib/supabaseClient.ts`, tested in `src/myPilot.test.ts` and `src/lib/supabaseClient.test.ts`): saves run one at a time and each sends the **whole** card, sheet or draft as it is on screen when it runs (never a copy taken when it was queued), so two quick edits can't undo each other and a later save carries an earlier failed one. ## Security rules (critical)
- **Players must NOT be able to update the characters table directly.** They can only add pending changes for their own characters. Otherwise anyone could skip GM approval using browser developer tools.
- Only GMs (or the approval function) can change approved characters.
- **Only owners can delete characters** (it cascades to their sheet, changes and reputation). Players can still withdraw their own pending pilot. GMs can't delete any.
- **Players must NOT be able to change their own role** in the profiles table, or anyone could make themselves a GM.
- **Only owners can add, change or remove LCP content.**
- **Picker rules checked at submit** (2026-11-19, migration `20261119170000_enforce_picker_rules.sql`, `private.guard_submit_rules()`, tested in `supabase/tests/submit_rules.test.sql`). When a **player** submits (a new pilot: `characters.submitted_at` null to set; a change: `pending_changes.submitted_at` null to set) the database refuses it if:
  - it **newly adds GM-only content** (HORUS or NHC source, or an item or licence of a HORUS or NHC frame; biomods by `bionics.source`) or **Exotic content** (source `EXOTIC`, the `tg_exotic` tag, biomod source `EXOTIC`; any case). "Newly" means in the proposed sheet but not in the approved sheet (a new pilot has no approved sheet, so everything is new), so items a GM granted can stay and a held GM-only licence can be raised. Content is read as `coalesce(edited, data)` like `loadKind()`. Ids are found by matching them as quoted strings in the sheet text (as `pack_usage` does), which also catches licence and talent keys; biomods are numbers in `sheet->'bionics'`. A false match (an id typed as a whole quoted string) only blocks.
  - it **overspends manna**: spending is more than `character_sheets.manna` received. SQL mirrors `mannaSpent()`: licence ranks, talent ranks, each biomod's `manna_cost` (a repeated one twice), and mechs after the first, counted from the proposed card for a change and `characters.mechs` for a pilot. The three prices are constants at the top of the function and `PRICES` in `src/rules.ts` points at them (`rules.test.ts` reads the SQL and compares).
  - Errors reach the page as "Not submitted: Exotic items need a GM to add them: Plasma Maul." / "GM-only items need a GM to add them: …" / "This spends 2,100 manna, but only 1,500 was received." (`NOT_SUBMITTED` in `src/saveStatus.ts`; `SaveStatus.vue` shows it as written, without Retry). Several problems come in one message.
  - Drafts save freely. **GMs and owners are never checked** (their submits, direct edits and approvals), nor are writes by the database owner.
  - **Still page-only** (the sheet is one JSON column; these need the rules from game data): licence requirements, loadout slots, mounts, system points, Unique, AI capacity, core bonus eligibility and the rule check generally. Also page-only: **Exotic for a GM on their own character outside GM edit mode**. The database can't tell a GM's edit mode from a GM writing, so it is the picker alone. GM review remains the backstop for everything above.
  - Known edge: a pilot a GM edited directly while it was still pending, then sent back, counts everything as new when the player resubmits, so GM-granted restricted items would block it until a GM removes them or approves it from their side.
- **Experience and the reward log are GM-only** (`pilot_progress`, `pilot_reward_log`, see "Homebrew levelling and gear"): players can't read or write them, even for their own pilot, and they live in their own tables because RLS works on whole rows and players read their own sheet.
- **Reputation is GM-only.** Only GMs and owners can read reputation or change its levels, and only owners can change the list of organisations. The character's own player can't see it either.
- Players can see and edit their own things, and can see only the public parts of other characters. GMs and owners can see everything.
- **RLS works on whole rows, not fields.** If a player can read a character's row, they can read every field in it with developer tools, even the ones the page doesn't show. The private parts must be secret, so the public parts have to be stored apart from them (for example, in their own table).
- Test the rules by trying to break them while logged in as a player.
- Supabase has two keys. The **public** one ("anon" or "publishable") is safe in the browser. The **secret** one ("service_role" or "secret") bypasses every rule. It must never go in the frontend or be committed to git.

## Gotchas
- **Vite environment variables:** only variables starting with `VITE_` reach the browser, and those are public. Only the public Supabase key goes in a `VITE_` variable. Keep `.env` files out of git.
- **Hosting + Vue Router:** with clean URLs like `/characters/42`, refreshing the page can show a 404 unless the host sends every unknown path to `index.html`. That's `not_found_handling` in `wrangler.jsonc`.
- **Supabase free tier pauses projects after 1 week of inactivity.** No data is lost, and you restore it from the dashboard. Expect this during campaign breaks. Limits: 2 active free projects and a 500 MB database, which is plenty for this.
  - **Keep-alive** (`.github/workflows/keep-alive.yml`): every 3 days (and by hand from the Actions tab) a GitHub Action reads one row of `content_items` through the REST API with the publishable key, so the project never idles for a week. A permission-denied answer counts (it still comes from a running Postgres); a 5xx or no answer fails the job. It needs two repository **variables** (Settings → Secrets and variables → Actions → Variables): `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. GitHub switches scheduled workflows off after 60 days without repo activity.
- **Supabase returns at most 1,000 rows per request** (`max_rows` in `supabase/config.toml`), silently cutting longer lists. Any list that can grow (game content, packs) is read with `fetchAll()` in `src/lib/supabaseClient.ts`: it pages with `.range()` (the query must `.order()` by something unique) and returns all the rows or an error, never a partial list (tested in `supabaseClient.test.ts`).
- **Game content is read once per browser session** (`src/catalogue.ts`): `loadKind(kind)` gives every `content_items` row of one kind through `fetchAll()`, and `cached(key, load)` keeps the promise, so `useGameData()`, `useMechData()`, `useManufacturers()` and the tag names share one fetch each across pages (bionics and pilot stats too). A failed read is not kept, so the next page that asks retries. `invalidateCatalogues()` (`gameData.ts`) clears the cache after an owner imports or updates a pack (`ContentView.vue`), so new content shows without a reload. A failure sets `catalogueError`; the pilot sheet, mech page, archives and GM change page each show it once as `<CatalogueNotice />` ("Game content didn't load: …", a `.notice.warn`), so an empty picker is never silent. New catalogue reads go through `cached()`/`loadKind()`, not straight to Supabase.
- **Pages load on demand** (`src/router.ts`): every route is `component: () => import('./views/X.vue')` except the login view, which stays eager for first paint. Keep new routes lazy.
- **Don't charge players or add ads.**
- **New tables may not be reachable from the app automatically.** Depending on the project's Data API settings, each new table needs an explicit `grant` to the `authenticated` role, on top of RLS. Every migration that creates a table should enable RLS and grant only what's needed.

- **Decided:** owners add custom content by writing it in `cc-lcp-editor` and importing the `.lcp`, **or in the site's own content editor** (`/gm/content/editor`, below, added 2026-11-17: built in phases: 1 pilot gear, tags, core bonuses, bionics; 2 weapons, systems, mods, talents, manufacturers; 3 frames). - **Readability and usability come first** (the developer, 2026-11-16). This rule outranks everything else in this section:
  - Everything should be **readable at a glance**: the same kind of thing always uses the same symbol and colour, so players can tell what something is without reading the words. Each colour has **one job**, and colour is never the only signal (always a symbol or word too).
  - **Standardised and clean:** one way to draw each kind of thing (button, card, tab, stat, tag, notice), reused everywhere. Compare against COMP/CON, LANCER's own app, for how game things are usually shown, and follow its conventions unless there's a reason not to (without copying its code).
  - The **terminal styling is flavour, not structure.** Where it costs readability or usability, drop it.

## Site text (standardised 2026-11-19)
The developer asked for one wording per kind of message, short text, and nothing explaining behind-the-scenes workings. Follow these for every new string. (Login, home boot text and `ThirdPartyNotice.vue` are exempt.)
- **Short and plain.** A hint is one short sentence at most; a notice is a title plus one or two short sentences. Say what the user sees or should do, never how the site stores or works it out (no packs updating, catalogues, databases, conversions, drafts' internals). No semicolons, no em-dashes, no "so that"/"which means" justifications, no hint that repeats its label. Drop a hint rather than pad it.
- **Sentence case** everywhere (CSS uppercases labels and buttons). A full sentence ends with a full stop; a label, badge, status word or blocked reason doesn't. After a colon, a full sentence starts with a capital ("Not saved: A pilot needs a name.").
- **Plurals are worked out in code**, never "(s)". Counts: `{shown} of {total}` in pickers, `{shown} of {total} pilots` in lists.
- **Status:** `Loading…` (never "Loading pilots…"), `Saving…`, `Uploading…`, `Importing…`, `Saved` (no full stop), `Not saved: {Reason.}`, likewise `Not deleted: …`, `Not removed: …`. An edit not sent yet is `Unsaved changes`. `Retry` re-sends or re-loads; `Reload` is only the conflict notice's full reload. Conflict notice: title `Not saved`, body "Someone else changed this. Reload to see their version."
- **Empty states:** `No {things} yet.` where someone is expected to add some; `No {things}.` where they're simply absent; a search miss is always `Nothing matches that search.` A missing frame is always `Choose a frame first.`
- **Badges** are the status word alone, capitalised: pilots `Draft` (not submitted yet), `Pending` (submitted), `Approved`, `Sent back`, `Dead`; changes `Draft`, `Submitted`, `Approved`, `Sent back` (a draft carrying a GM's note; the history status `rejected` is shown as `Sent back` too). The sentence beside a badge explains it. A GM **sends back** a pilot (button `Send back`) and a change (button `Send back change`, note required).
- **Blocked reasons** (beside a disabled button, no full stop): `Needs {thing}` ("Needs IPS-N Drake II", "Needs an empty mount"), `Not enough {resource}` ("Not enough manna", "Not enough system points", "Not enough mod points"), `Already on this mech` (Unique), `Fits {types} only`, `GM only`, `Fix {n} problem first` / `Fix {n} problems first`, `Save your changes first`.
- **Problems:** the word is "problem", never "rule" or "issue". Rule-check titles: `{n} problem(s)`, on your own draft `Fix {n} problem(s) before you submit`; editor: `Fix {n} problem(s) before saving`. Each line is a third-person sentence about the item, capital first, full stop ("LANTERN: Superheavy weapon needs a second empty mount."). Content that isn't loaded: `{Name} isn't in any loaded pack.` / `Unknown item ({id})`; in reminders `Missing {kind}. Its bonuses aren't counted.`
- **Confirms:** the title stays "Are you sure?". The message names the thing without quotes, says what happens in one sentence, and ends `This can't be undone.` when it can't. The confirm button is always verb + noun (`Remove licence`, `Withdraw change`, `Publish entry`, `Delete pilot`, `Mark dead` excepted as it already names the act). Danger-zone sentences use the same pattern and "This can't be undone." (never "for good").
- **Buttons** are verb + noun, except `Swap` / `Remove` on an item card's foot and `Choose` / `Add` on a picker row, where the item is right there. `Add {thing}` puts existing content on the sheet; `New {thing}` creates something; `Remove` takes it off a list; `Delete` destroys it; `Withdraw` takes back a submission; `Clear` empties a field, search or note; `Discard changes` drops unsaved edits; `Revert to original` drops campaign edits to official content; `Close` closes information, `Done` closes something you changed, `Cancel` backs out of a confirm.
- **Words:** licence, armour, biomod (never "bionic" on screen), manufacturer (not "maker" on screen), system points (not "SP" in sentences), Heat cap / Repair cap, HP, E-defence, "Owner only" / "GM only", `Unknown player` for a missing name, `None` for an optional empty select and `Choose…` for a required one. Access denied: "Only GMs can see this page." / "Only owners can see this page." Whole numbers: "{Field} must be a whole number, 0 or more." (or "from 0 to {max}"). Stat sources: `Base: {n}`, `{Source}: +{n}`, `{Source}: sets to {n}`. Editor hints: id fields "Fixed once created."; flavour fields "Flavour text."
